## 非IT精通者向け：今日から意識したい運用方法

- **For You に出る広告の「入り方」が今日から本番で変わりました。** 8/28 に「新設されたが既定オフ」と報告した新しい広告差し込み方式（`multi_risk`）が、**本日づけで既定値になりました**（下記①）。これまでは「安全と確認済みの投稿」に挟まれた場所にしか広告を置けませんでしたが、今日からは**「まだ安全確認が終わっていない普通の投稿」の間にも広告が入り得ます**。
- **これは「際どい投稿を見ている人だけの話」ではありません。** X の内部判定では、**Grokの安全性審査がまだ通っていない投稿は自動的に「中リスク」に分類されます**（下記①-2）。さらに **2026年5月12日以降に投稿されたものは、追加レビュー済みの印が付くまで一律「中リスク」**です。つまり**投稿直後の新しい投稿はほぼ全部が「中リスク」側**にいます。したがって今回の切り替えは、ほぼ全ユーザーの For You に効きます。
- **体感として「広告が増えた」と感じる可能性があります。** 従来は「安全確認済みの投稿の本数 ÷ 2」が広告本数の上限になっていて、これが実質的なブレーキでした。今日からは中リスク投稿もスロットとして使えるため、このブレーキが外れます（下記①-3）。ただし増えるのは**「リスク隣接を許容する設定にした広告主」の広告だけ**です。
- **クリエイター側には小さな追い風です。** これまで「中リスク」に分類された投稿（＝審査未了の新しい投稿を含む）は広告の隣に置けず、フィードの「埋め草」側に回されていました。今日からは、**中リスク投稿のうちスコア上位のものが広告の直前・直後という目立つ位置に引き上げられます**（下記①-4）。投稿の並び順を決めるスコア自体は変わっていませんが、配置の面で不利がひとつ減りました。
- **「高リスク」判定の投稿は今日も広告の隣には出ません。** アダルト・残虐表現・PDNA などの明確なラベルが付いた投稿は、新方式でも広告の隣接から完全に除外されます（下記①-5）。この線引きは変わっていません。
- **投稿の見え方・隠され方（安全フィルタ）は今日は一切変わっていません。** VF（可視性フィルタ）は 10ファイル削除・3ファイル新設という大規模な作り直しが入りましたが、**ルールの数・順番・判定条件はすべて同じ**で、それを保証するテストが新たに追加されています（下記②）。表示・非表示の体感は変わりません。
- **投稿の仕方を変える必要はありません。** いいね・返信・滞在時間などの配点（ランキング重み）は今日も無変更です。

## 変更サマリ

- **稼働中の実挙動を変える変更は1件、ただしそれが大きい**：広告ブレンダーの既定値が `partition_organic_low_risk` → `multi_risk` に切り替わった。8/28 に新設された「中リスク投稿の間にも高リスク許容広告を挿す」方式が既定になった。
- 可視性フィルタ（VF）のルール実装が**宣言的テーブル（`RuleSpec`）方式へ全面移行**。ルール定義10ファイルを3ファイルへ集約したが、**ルール名・順序・判定内容は完全同値**で、順序を固定するテストが追加された。挙動変化ゼロ。
- Phoenix の**検索クエリ埋め込みの取り扱いにバグ修正**。従来は候補スロット全体（パディング含む）にクエリベクトルを複製していたが、**実候補の本数ぶんだけ複製**するよう修正。検索経由のランキング品質に効く。
- 学習側に **SID（セマンティックID）の「再構成モード」** を新設（`sid_embedding_mode="recon"`）。学習済みコードブックから埋め込みを復元する方式。既定は従来の `learned` で**未使用**。
- 広告プロダクト情報（DPA）の proto に `sid_codes` を追加。商品広告にセマンティックIDを持たせる準備。**配線なし**。
- インフラ：学習チェックポイントの暗号化まわりの安全弁（暗号化から復元したら平文保存を拒否）、StableHLO バンドルのエクスポート機構（既定オフ・634行新規）、grox の Kafka 認証を環境変数パスワード方式からマルチリージョンプロデューサへ移行。**推薦結果は不変**。

## 変更点ごとの詳細

### ① 広告ブレンダー既定値の切り替え `partition_organic_low_risk` → `multi_risk`【影響度：大（全ユーザーの For You に効く）】

#### メカニズム

フィーチャースイッチのミラーで既定値だけが書き換わった。差分は実質この2行のみ。

```rust
// home-mixer/params/param.rs:908-913
param!(
    AdsBlenderType,
    String,
    "rust_home_mixer_ads_blender",
    "multi_risk"          // ← 前回まで "partition_organic_low_risk"
);
```

この値は広告差し込みの実装を選ぶディスパッチにそのまま渡る（`home-mixer/selectors/blender_selector.rs:53-69`）。`"multi_risk"` のアーム自体は 8/28 に追加済みで、今日は**既定値が到達するアームだけが変わった**。

#### ①-2 「中リスク」の中身 — 未審査の投稿は自動的に中リスク

新方式を理解する鍵は、投稿のブランドセーフティ判定 `BrandSafetyVerdict` の付き方にある（`home-mixer/models/brand_safety.rs:45-72`）。

```rust
// home-mixer/models/brand_safety.rs:57-66
let scored_by_grok = labels.contains_key(&SafetyLabelType::GROK_SFA)
    || labels.contains_key(&SafetyLabelType::GROK_NSFA_LIMITED);
if !scored_by_grok {
    return BrandSafetyVerdict::MediumRisk;      // ← 未審査＝中リスク
}

if tweet_id >= PTOS_CUTOFF_TWEET_ID && !labels.contains_key(&SafetyLabelType::PTOS_REVIEWED) {
    return BrandSafetyVerdict::MediumRisk;      // ← カットオフ以降の未レビューも中リスク
}
```

- `PTOS_CUTOFF_TWEET_ID = 2_054_275_414_225_846_272`（`brand_safety.rs:43`）は Snowflake ID で、**2026-05-12 19:00 UTC** に相当する。
- v2 判定（`compute_verdict_v2`、`brand_safety.rs:99-128`）も同じ2つのフォールバックを持ち、v2 は既定オン（`param.rs:916-920` `rust_home_mixer_ads_bs_v2_exp_enabled = true`）。
- 引用元・祖先投稿の VF 照会に失敗した場合も中リスクへ倒れる（`home-mixer/candidate_hydrators/ads_brand_safety_vf_hydrator.rs:84,94`）。
- 明確なNSFW/残虐/PDNAラベル、および広告用NSFW著者フラグは**高リスク**（`brand_safety.rs:15-22`、`ads_brand_safety_vf_hydrator.rs:105`）。

つまり「中リスク」は**際どい投稿だけの箱ではなく、審査が追いついていない新しい投稿の受け皿**でもある。これが今回の切り替えの影響範囲を全ユーザーに広げている。

#### ①-3 広告本数の上限が実質的に外れる

**旧（`partition_organic`）**（`home-mixer/ads/partition_organic_blender.rs:38-45`）:

```rust
let safe_count = scored_posts.iter().filter(|p| !has_avoid(p)).count();  // Medium/High を除外
let max_from_safe = safe_count / 2;
let actual_ads = ads.len().min(expected_from_spacing).min(max_from_safe);
```

`has_avoid()` は Medium と High の両方を弾く（`home-mixer/ads/util.rs:24-29`）。したがって**未審査の新しい投稿はすべて広告スロットに使えず**、`safe_count / 2` が広告本数の強いブレーキになっていた。

**新（`multi_risk`）**（`home-mixer/ads/multi_risk_blender.rs:43-55`）:

```rust
let safe_count = scored_posts.iter().filter(|p| !is_medium_risk(p) && !is_high_risk(p)).count();
let medium_count = scored_posts.iter().filter(|p| is_medium_risk(p)).count();
let max_safe_slots = safe_count / 2;
let max_medium_slots = medium_count / 2;
let safe_budget = num_ads.min(spacing_cap).min(max_safe_slots);
...
let any_bsr_high = ads.iter().any(is_bsr_high_ad);
if safe_budget == 0 && !(any_bsr_high && max_medium_slots > 0 && spacing_cap > 0) {
    return posts_to_feed_items(scored_posts);   // 安全枠ゼロでも中リスク枠があれば続行
}
```

- `is_bsr_high_ad`（`home-mixer/ads/util.rs:89-95`）= 広告主が `ad_adjacency_control.brand_safety_risk == BsrHigh`、つまり**リスク隣接を許容する設定にした広告**。
- BSR-High 広告は中リスク投稿のペア枠に入る（`multi_risk_blender.rs:101-125`）。
- 全体の上限は `spacing_cap`（＝投稿本数 ÷ 要求間隔、`multi_risk_blender.rs:38-41, 97-99`）のみ。

結果：**`safe_count / 2` というブレーキが、BSR-High 広告がある限り効かなくなる。**

テストがこの差を直接固定している（`home-mixer/ads/tests/multi_risk_blender_tests.rs:162-172`）:

```rust
let posts: Vec<_> = (1..=8).map(make_avoid_post).collect();  // 全部が中リスク
let with_high = blend_impl(posts.clone(), vec![make_bsr_high_ad(100)], 5);
assert_eq!(ad_count(&with_high), 1);      // multi_risk: 広告1本入る（旧方式では0本）
let with_normal = blend_impl(posts, vec![make_normal_ad(100)], 5);
assert_eq!(ad_count(&with_normal), 0);    // 通常広告は従来どおり入らない
```

#### ①-4 中リスク投稿の「配置」が変わる

両方式とも、広告スロットに使われなかった投稿は「埋め草（filler）」としてスコア順にソートされ、広告ブロックの間に均等配分される（`multi_risk_blender.rs:187-232`）。

- **旧**：中リスク投稿は例外なく filler 側。広告の直前・直後という目立つ位置には絶対に来ない。
- **新**：中リスクプールの**スコア上位から順に** `medium_opts[medium_pair_idx * 2]` として取り出され（`multi_risk_blender.rs:101-103`）、広告ブロックの先頭（＝各ブロックの一番上）に配置される。

広告ブロックは `[上の投稿][広告][下の投稿][埋め草…]` の順で先頭から並ぶため（`multi_risk_blender.rs:205-227`）、スロットに選ばれることは**フィード上の位置が前に来ること**を意味する。ランキングスコアは変わらないが、最終的な表示位置は中リスク投稿にとって有利側に動く。

#### ①-5 変わらない線引き

高リスク投稿は新方式でも広告に隣接しない。分類の時点で `high` プールへ隔離され（`multi_risk_blender.rs:61-71`）、スロット候補に一切使われない。テストが明示（`multi_risk_blender_tests.rs:148-159` `high_risk_never_adjacent_including_bsr_high`）。広告主ハンドル・キーワードによる隣接除外（`should_drop_handle` / `keyword_matches`）も中リスク枠に同様に適用される（`multi_risk_blender.rs:105-118`）。

#### Xユーザー/クリエイターへの影響

| 対象 | 影響 |
| --- | --- |
| 一般閲覧者 | For You の広告本数が増え得る。特に**新しい投稿が多く並ぶタイムライン**（フォロー数が多い／速報性の高い話題を追っている人）で顕著。増えるのは BSR-High 設定の広告のみ。 |
| クリエイター（一般） | 投稿直後は「中リスク」扱いのため、**投稿直後の投稿が広告の隣という目立つ位置に上がる可能性**が生まれた。スコアは不変。 |
| クリエイター（際どい内容） | 従来は広告隣接から一律排除されていたが、中リスク帯なら配置対象に復帰。ただし高リスクラベルが付けば従来どおり完全除外。 |
| 広告主 | `ad_adjacency_control` を BSR-High にすると在庫（配信機会）が増える。BSR-Normal のままなら従来どおりの安全枠のみ。 |

### ② 可視性フィルタ（VF）ルールの宣言的テーブル化【影響度：小（挙動不変）】

#### メカニズム

ルール定義10ファイル（`nsfw_age_gating.rs` / `nsfw_interstitial.rs` / `nullcast_rule.rs` / `socialgraph_rules.rs` / `tes_rules.rs` / `tweet_flag_rules.rs` / `tweet_label_drops.rs` / `user_label_drops.rs` / `user_rules.rs` ほか）を削除し、3ファイルへ集約した。

- `visibility-filtering/rules/rule_spec.rs`（89行・新規）— ルールを `Tweet` / `Author` / `Custom` の3形態の**データ**として表す `RuleSpec` enum。`exempt_author`（投稿者自身は除外）・`exempt_follower`（フォロワーは除外）・センシティブメディア用インタースティシャルの共通ロジックがここに一本化された。
- `visibility-filtering/rules/tweet_rules.rs`（1,125行・新規）／ `author_rules.rs`（354行・新規）— ルール本体を `const` テーブルとして宣言。
- `registry.rs` はテーブルを連結するだけになった（`visibility-filtering/rules/registry.rs:83-115`）。
- NSFW年齢ゲート対象国リストの受け渡しが、ルール個別の `Arc` 保持から `RuleContext` 経由に変更（`visibility-filtering/rules/context.rs:55-57`、`registry.rs:42,60`）。

#### 挙動同値の根拠

新テスト `wired_rule_order_matches_pre_migration_sequence`（`registry.rs:222-296`）が、TimelineHome の28ルールと TimelineHomeRecommendations の追加26ルールについて**名前と順序を移行前の並びそのままで固定**している。VF はルールを順に評価する構造なので、名前と順序が一致すれば評価順序は同一。

判定条件も同一であることをスポット確認した。例：年齢未申告ユーザー向けドロップは新旧で完全に同じ条件式（新 `tweet_rules.rs:238-250` / 旧 `nsfw_age_gating.rs:83-95`）。古い投稿のドロップ（`tweet_rules.rs:283-284`）、ヌルキャスト投稿のドロップ（`tweet_rules.rs:252-257`）、NSFW著者インタースティシャル（`tweet_rules.rs:186-191`）も同条件。

#### Xユーザー/クリエイターへの影響

**なし。** 表示・非表示・センシティブ警告の出方は今日も同じ。ただし今後の運用面では、ルールがデータ化されたことで**新ルールの追加・条件変更が数行の差分で行えるようになった**。今後の日次監視では `tweet_rules.rs` / `author_rules.rs` の `const` テーブルの差分を重点的に見る必要がある。

### ③ 検索クエリ埋め込みの複製範囲を修正【影響度：小〜中（検索経由のランキング）】

#### メカニズム

**旧**：候補バッファ構築時に、検索クエリのベクトルを `candidate_seq_len × dim` のバッファへ複製して保持していた。

**新**：`InputBuffer` は**クエリベクトルを1本だけ**保持する（`phoenix/crates/common/xai-recsys/src/util.rs:451-463`）。複製はモデル入力を組み立てる直前に、**実在する候補の本数ぶんだけ**行う。

```rust
// phoenix/crates/serving/xai-recsys-engine/src/python.rs:2049-2058
let src = &input_buffer.candidate_search_query_embeddings;
if src.len() == search_query_embedding_dim {
    let n_rep = input_buffer.num_real_candidates(num_item_hashes, candidate_seq_len);
    xai_recsys::util::repeat_query_into(search_query_emb_row, src, n_rep);
}
```

`num_real_candidates`（`util.rs:346-356`）は候補ハッシュ列を先頭から走査し、ハッシュ 0（＝パディング）に当たった時点で打ち切る。`repeat_query_into`（`util.rs:334-345`）は書き込んだ先だけを埋め、末尾は触らない（テスト `util.rs:1782-1788`）。

つまり従来は**パディングスロットにも検索クエリのベクトルが入っていた**のが、今後は入らない。

#### Xユーザー/クリエイターへの影響

検索結果ランキングのモデル入力から、実体のないスロットに混入していたクエリ信号が除かれる。**検索タブの結果の精度が理論上わずかに改善する方向**。ただし旧実装で実害がどの程度出ていたかはコードからは判断できない（要確認）。For You には影響しない。

### ④ SID（セマンティックID）再構成モードの新設【影響度：なし（既定オフ・未使用）】

#### メカニズム

`phoenix/xrex/models/recsys_sid.py`（72行・新規）が、safetensors 形式の学習済みコードブック（`stages` + 2層デコーダ `dec_w0/b0/w1/b1`）から投稿の意味埋め込みを復元する。復元後に L2 正規化し、**勾配を止めて**（`jax.lax.stop_gradient`、`recsys_sid.py:60`）学習可能な射影行列だけを通す。

有効化は `sid_embedding_mode="recon"`（`phoenix/xrex/models/recsys_model.py:546`）。**既定は `"learned"`**（従来の学習可能SIDテーブル）で、設定側の既定も同じ（`phoenix/xrex/configs/xrecsys.py:631-632`）。`recon` を選ぶには `sid_decoder_path` の指定が必須で、`feature_prep` 経路・`sid_hash_level`・`sid_cross_attn` とは併用禁止（アサーション、`recsys_model.py:621-634`）。

`recon` 時は履歴側のSID埋め込みが `block_history_reduce` に渡されず、**リデュース後に加算**される経路に変わる（`recsys_model.py:2691,2707-2708`）。

#### Xユーザー/クリエイターへの影響

**現時点でなし。** 意味合いとしては、「投稿の話題を表す固定の意味ベクトル」を凍結した外部辞書から持ち込む方式が用意されたということ。将来有効化されれば、**学習データが少ない新しい話題・新しい投稿でも話題の近さが安定して効く**方向に働き得るが、現状は準備段階。

## 不確実な点（要確認）

1. **`multi_risk` の実配信範囲** — `param.rs` はフィーチャースイッチの**既定値のミラー**であり、実際の配信では実験バケットごとに上書きされ得る。既定値が切り替わったこと自体は 100%（コード上の事実）だが、「全ユーザーに 100% 適用されているか」は本リポジトリからは判定できない。過去の例（8/26 のランキング重み変更など）では既定値の切り替えが実運用の切り替えと一致していた。
2. **BSR-High 広告の在庫比率** — 広告主のうち何割が `ad_adjacency_control.brand_safety_risk = BsrHigh` を選んでいるかは本リポジトリに情報がない。この比率が低ければ、①の広告本数への実効影響は小さくなる。
3. **中リスク投稿の実際の割合** — 「Grok未審査＝中リスク」「2026-05-12 以降の未レビュー＝中リスク」というフォールバックが実運用でどれだけ発火しているかは、審査パイプラインのスループット次第で本リポジトリからは分からない。審査がほぼリアルタイムで追いついているなら、①の影響は「際どい投稿中心のタイムライン」に限定される。追いついていないなら全ユーザーに効く。
4. **`should_drop_bsr_low` の意図** — BSR-Low/IAS 広告を `BrandSafetyVerdict::LowRisk` の投稿の隣で落とす条件（`home-mixer/ads/util.rs:97-117`）は、名前から素直に読める意味と逆に見える。新旧ブレンダー共通で今回の差分に含まれないため本レポートの結論には影響しないが、解釈は保留する。
5. **検索クエリ埋め込みの旧実装の実害** — パディングスロットにクエリベクトルが入っていたことがモデル出力にどの程度影響していたかは、モデル側のマスク処理次第でコードからは判断できない。
6. **`ScoringWeights` の据え置き期間** — `home-mixer/scorers/` は 8/26 以降 7日連続で無変更。ランキング配点は安定している。
