## 非IT精通者向け：今日の差分を踏まえた運用方法のまとめ

今日の最重要点は、**ミュートキーワードが通知にも効くようになった**ことです。これは実験フラグではなく、**ルールそのものに直接追加された即時適用の変更**です（この変更だけはON/OFFスイッチがありません）。

- **自分のミュートキーワードが、メンション通知とリプライ通知にも適用されます。**
  これまでミュートキーワードの判定は通知の本番ルールに入っていませんでしたが、今日からメンション／リプライの通知ルールに組み込まれました（`visibility-filtering/rules/levels.rs:260`、`:266`）。
  → **読む側（受信側）には歓迎すべき変更です。** 設定でキーワードを登録し、適用範囲に「通知」を選んでおけば、そのキーワードを含むメンション・リプライは通知に出なくなります。ネタバレ・特定の政治ワード・荒らしの定型文などを避けられます。
  → **書く側（投稿する側）には新しいリスクです。** あなたがリプライやメンションで誰かに話しかけても、**相手がそのキーワードをミュートしていれば、相手に通知が届きません**（相手には届かなかったことも分かりません）。炎上しがちな語・流行の攻撃的な語を含むリプライは、届かない率が上がります。
  → 注意点：**写真でのタグ付け通知（media tagged）は対象外**です。メンションとリプライだけが対象です。
  → 一致は**単語単位**です。「spoiler」をミュートしても「spoilers ahead」は通知に残ります（`visibility-filtering/models/viewer.rs:247`、テスト `muted_keyword_inside_a_longer_word`）。日本語のような分かち書きのない言語での挙動は公開コードから断定できません（**要確認**）。
  → 「フォロー中のアカウントは除外」オプションを付けたキーワードは、**フォローしていない人からのメンションだけ**を落とします。ただし**除外なしのキーワードを1つでも併用していると、フォロー中の相手からでも落ちます**（テスト `muted_keyword_excluding_followed_beside_one_that_does_not`）。
  → 自分自身の投稿は対象外です（`audience: NonAuthors`）。

- **「リプライ乞食」「拡散希望」「クリック誘導」を自動検知して、その種類の評価だけ無効化する仕組みが入りました（既定OFF）。**
  投稿に `PROMOTES_REPLIES` / `PROMOTES_SHARES` / `PROMOTES_CLICKS` という安全性ラベルが付いていると、その投稿は**リプライ予測・共有予測・クリック予測の「対象外（ineligible）」としてランカーに渡される**ようになりました（`home-mixer/scorers/vm_ranker_engagement_labels.rs:17`、`home-mixer/scorers/vm_ranker_debias_payload.rs:61`）。
  → 狙いは明確です。**「リプで教えて」「RTで拡散して」「詳細はリンクから」といった行動を煽る投稿が、その煽った行動の分だけスコアを稼げなくする**仕組みです。種類ごとにピンポイントで無効化されます（リプライを煽った投稿はリプライ分だけ失い、いいねや滞在時間の分は残ります）。
  → 今日時点では既定OFF（`home-mixer/params/param.rs:664` が `false`）なので挙動は変わりません。ただし**実装が完成して本番配線済み**なので、いつONになってもおかしくない段階です。
  → 行動指針：**エンゲージメントを明示的に要求する定型文は、割に合わなくなる方向**です。「リプ欄で教えて」と書かずに、自然にリプライしたくなる内容にする——という当たり前の方針が、今回は技術的にも裏付けられました。
  → 対象は**スコア上位200件まで**（`home-mixer/params/param.rs:670`）。取得は80ms でタイムアウトし、失敗時は「ラベル無し」扱い（安全側＝罰しない）です。

- **フォロワーが多いアカウントの「自動制裁されない特権」が、個別に外せるようになりました。**
  これまで自動の制裁システムには**絶対的な上限（ceiling）**があり、フォロワー数がその値以上のアカウントには自動処置が一切実行されませんでした。今日から、制裁の種類（head）ごとに**その上限を引き上げられる**ようになりました（上限値は最大10億、`abuse-enforcement-service/types/src/action_control.rs:34`）。
  → 平たく言えば、**大きなアカウントも自動処置の対象にできるようになった**ということです。
  → 誤操作防止は厚めです。設定時に数値を2回書く＋確認文字列が必須（`abuse-enforcement-service/service-lib/src/action_control.rs`、`follower_limit_unconfirmed`）、記録のスキーマ版が9に上がって古いサーバーは受け付けない、設定差分には「**他の全headがスキップするアカウントに対して処置する**」という警告が出る（`safety_checks.rs:481`）という三重の歯止めです。
  → 行動指針：**フォロワー数の多さは、ルール違反に対する盾として以前より頼りにならない**という前提で見てください。ただし**実際に引き上げられているかは公開コードからは分かりません**（**要確認**。公開コード内の閾値 `12.34` / `12345.67` は明らかに伏せられたダミー値です）。

- **本番モデルの予測値が、全ユーザー分・常時記録されるようになりました（既定ON）。**
  これまで「教師モデル」用の記録は既定OFF＋サンプリング制でしたが、今日から**既定ONで、サンプリングなし**になりました（`home-mixer/params/param.rs:1270` が `true`）。記録されるのは21種類の行動予測値です（`:1276`）。
  → おすすめの出方そのものは変わりません。ただし**学習データの収集量が桁で増える**ので、今後のモデル更新サイクルが速くなる可能性があります。「アルゴリズムの変化が以前より頻繁に感じられる」ことへの備えという意味での注意点です。

- **「昔よく見ていた人」を覚えておく仕組みの土台が入りました（既定OFF）。**
  視聴者ごとに「長期的に関わりのある著者」のリスト（見た投稿数・強い反応の回数・最後に反応してからの経過秒・平均滞在時間）を学習データに載せる配管が追加されました（新規ファイル `phoenix/xrex/data/recsys/long_term_author_profile.py`）。集計の種類にも `DENSE_WITH_LONG_DWELL_AUTHOR_PROFILE` が追加されています（`phoenix/crates/serving/xai-recsys-proto/proto/recsys.proto:2059`）。
  → 現状は既定OFF（`long_term_author_profile_size = 0`）で、モデルがまだ使っていません。将来有効化されると、**直近の反応だけでなく「過去に長く読んでいた著者」が復活しやすくなる**方向です。
  → 行動指針：**一度つかんだ読者は、少し間が空いても戻ってくる余地が広がる**方向の変更です。長期的に同じテーマで書き続けることの価値が上がります。

- **編集した投稿が一時的に消える不具合が直りました。**
  投稿が「古い版」と判定される条件が修正されました（`visibility-filtering/models/tweet.rs:92`）。以前は編集チェーンの情報が一瞬ずれただけで最新版が非表示になりえましたが、今は**自分より新しい版が実際に存在する時だけ**非表示になります。
  → 編集直後に投稿が見えなくなる事象が減ります。編集機能を使いやすくなった、という小さな改善です。

## 変更サマリ

1. **ミュートキーワードがメンション／リプライ通知に適用開始**（フラグなしの即時適用。写真タグ付け通知は対象外、単語単位一致、投稿者本人は免除）。
2. エンゲージメント誘導ラベル（`PROMOTES_REPLIES` / `_SHARES` / `_CLICKS`）を**ヘッド単位の無効化フラグ**としてランカーへ渡す機構を新設（既定OFF、上位200件）。
3. 自動制裁サービスの**フォロワー数「絶対上限」を制裁種別ごとに引き上げ可能**に（最大10億、二重確認＋スキーマ版9＋差分警告付き）。
4. 本番モデル予測値の記録（teacher cache）が**既定ON・サンプリングなし**に変更。別クラスタへの追加推論呼び出しは廃止し、serving 時のスコアをそのまま記録する方式へ簡素化。
5. 視聴者ごとの**長期著者プロフィール**（長時間滞在ベース）を学習データに載せる配管を新設（既定OFF）。
6. 編集済み投稿の誤非表示を修正（`!=` → `>`）。広告の均等配置オプション（既定OFF）、新広告特徴 `advertiser_first_delivery_ms`、Grox の高PageRank判定に30分キャッシュ。

### 1. ミュートキーワードが通知（メンション／リプライ）に適用開始 【フラグなし／即時適用】

**メカニズム**

新ルール `MUTED_KEYWORD_DROP_UNSPECIFIED` が追加されました（`visibility-filtering/rules/tweet_rules.rs:28`）:

```rust
pub(super) const MUTED_KEYWORD_DROP_UNSPECIFIED: Rule = Rule {
    id: RuleId::MutedKeyword,
    audience: NonAuthors,
    when: any![
        ViewerHasMatchingMutedKeyword,
        all![ViewerHasMatchingMutedKeywordExcludingFollowed, !ViewerFollowsAuthor]
    ],
    action: drop_post(DropAs::UnspecifiedReason),
};
```

これが `NOTIFICATIONS_WRITER_V2_MENTION` のルール群に追加され（`visibility-filtering/rules/levels.rs:260`）、`NOTIFICATIONS_WRITER_V2_REPLY` は同じ定義のエイリアスなので（`:266`）**メンションとリプライの両方**に効きます。

`Rule` 構造体には機能スイッチ用のフィールドがありません（`visibility-filtering/rules/rule_spec/rule.rs:16`）。したがって**この変更は実験フラグ経由ではなく、デプロイと同時に全ユーザーに効きます**。

キーワードの前処理は `visibility-filtering/models/viewer.rs:207` の `NotificationMutedKeywords::of()`:

- `MuteSurface::Notifications` を含むキーワードだけを採用（`MuteSurface::HomeTimeline` 指定のみのキーワードは通知には効かない。テスト `muted_keyword_on_home_timeline_only` が「表示される」ことを固定）。
- `MuteOption::ExcludeFollowingAccounts` の有無で2群に分割し、前者は「フォローしていない相手からのみ」適用。
- 一致判定は `TweetTokenizer` でトークン化してから（`:243`）。部分文字列一致ではありません。

投稿本文は `TweetFeatures.text`（新フィールド、`visibility-filtering/models/tweet.rs:31`）として TES から読み込まれます。**VF のキャッシュ行には本文を保存しない**設計です（テスト名 `a_cached_row_reads_as_its_tweet_without_its_text`）。本文の読み取りに失敗した通知は「失敗」扱いになります（`filter_notifications/tests.rs` の `"post"` ケースで3種すべて `Seen::Failed`）。フォロー関係の読み取り失敗時は通知を落とす側に倒れます（`rules/rule_spec/laws.rs:228` の `FAILS_THE_NOTIFICATION`）。

**Xユーザー／クリエイターへの影響**

- 受信側（全ユーザー）: ミュートキーワードが通知にも効くようになり、通知欄の制御性が上がります。ネタバレ回避、特定トピックの回避、定型的な荒らしの回避に使えます。
- 発信側（特にリプライで交流するユーザー）: **リプライやメンションが相手の通知に届かないケースが新たに発生します。** 届かなかったことは送信側には分かりません。返信が来ないことを「無視された」と解釈しづらくなります。
- クリエイター: リプライでの交流が主な導線になっているアカウントは、**攻撃的／流行語／ネタバレ性の高い語を含むリプライで到達率が落ちる**可能性があります。
- 写真タグ付け通知は影響を受けません（`filter_notifications/tests.rs` の `media_tagged` が `Seen::Allowed`）。

### 3. 自動制裁のフォロワー数上限を制裁種別ごとに引き上げ可能に 【運用設定次第】

**メカニズム**

従来の二段構えは「①head ごとの `follower_threshold`（この値以上のフォロワーを持つ著者は当該 head をスキップ）」＋「②全 head 共通の絶対上限 `FOLLOWER_CEILING`（これ以上は何があってもスキップ）」でした。

今日の変更（`abuse-enforcement-service/service-lib/src/safety_checks.rs:460`）:

```rust
pub fn follower_ceiling(self) -> f64 {
    self.follower_floor().max(*FOLLOWER_CEILING_COUNT)
}
```

`first_page_stop` が共通の `ceiling_stops` ではなく head 固有の `stops_at(facts, true, skips.follower_ceiling())` を呼ぶようになり（`:511`）、**head が絶対上限より大きい `follower_threshold` を設定すると、その head だけ上限が上がる**（＝より大きなアカウントにも自動処置が及ぶ）構造になりました。上限の上限は `FOLLOWER_THRESHOLD_MAX = 1_000_000_000`（`types/src/action_control.rs:34`）。

付随する変更:
- `follower_threshold: 0`（＝「フォロワースキップOFF」）の意味が「スキップ無効」から「`ceiling - 1` と同じ」に変わりました（`safety_checks.rs:452`、テスト `a_stored_zero_threshold_reads_as_one_below_the_ceiling`）。実際に判定が変わるのは**ちょうど `ceiling - 1` 人のアカウント1点だけ**で、以前は処置可能、今はスキップされます。
- 投稿側の「著者信頼度プリチェック免除」（`skip_author_credibility_prechecks`）では**引き上げた上限は越えられません**（テスト: `"the producer waiver can't lift the raised limit"`）。
- 安全装置: `confirm_follower_limit` に同じ数値を再掲＋`confirm` 文字列の両方が必要（`service-lib/src/action_control.rs`、エラーコード `follower_limit_unconfirmed`）。記録のスキーマ版が7→9に上がり、古いサーバーは該当レコードを拒否（`types/src/action_control.rs:6`, `:546`）。設定差分には「`X+ から Y+` に上限を引き上げ、**他の全headがスキップするアカウントに処置する**」という警告文が出ます（`safety_checks.rs:481`）。

**Xユーザー／クリエイターへの影響**

- 大きなアカウントの「自動処置に対する事実上の免除」が、**運営の判断で制裁種別ごとに解除可能**になりました。影響の実体は設定値次第です。
- 公開コード中の閾値（`cred.follower_count >= 12.34`、`>= 12345.67`）は**明らかに伏せられたダミー値**で、実際の人数は分かりません（**要確認**）。
- 影響を受ける層: フォロワー数が多いアカウント。ただし実際に引き上げが設定されているかどうかは公開コードから判断できません。

**Xユーザー／クリエイターへの影響**

- 現時点では影響なし（学習データの器を作った段階）。
- 将来有効化された場合: **「直近の反応」だけでなく「過去に長く読んでいた著者」が評価軸に入る**方向です。経過秒（`age_sec`）が特徴として入っているので、「しばらく見ていないが以前よく読んでいた著者」を明示的に扱えます。
- 影響を受ける層（将来）: 投稿頻度が低いが読者の滞在が長いクリエイター、一度離れた読者を抱えるアカウント。長期的に同じ読者層に向けて書き続けることの価値が上がる方向です。

### 6. 編集済み投稿の誤非表示修正

**メカニズム**

`visibility-filtering/models/tweet.rs:92`:

```rust
pub fn is_superseded_edit(&self, tweet_id: u64) -> bool {
    self.latest_edit_tweet_id
        .is_some_and(|latest| latest > tweet_id)   // 旧: latest != tweet_id
}
```

編集の各版は新しい投稿IDを持ち、IDは単調増加します。旧実装では `latest_edit_tweet_id` が自分より**小さい**値（＝編集チェーン情報が古い／反映遅れ）でも「古い版」と判定され、`stale_tweet/drop/unspecified` で落とされていました。新実装では**自分より新しい版が実際に存在するときだけ**落とします。新しいテストケース `edit_ahead_of_its_chain`（`tweet_id: 3`, `latest_edit_tweet_id: Some(2)` → `allow`）がこれを固定しています（`visibility-filtering/rules/golden_corpus/tweet_state.rs:143`）。

**Xユーザー／クリエイターへの影響**

- 投稿を編集した直後に、編集後の投稿が一時的に見えなくなる／タイムラインから落ちる事象が減ります。
- 影響を受ける層: 投稿の編集機能を使うユーザー（Premium系）。小さいが確実な改善です。

### 7. その他（小）

- **広告の均等配置オプション**（既定OFF）: 従来の間引きは「等間隔のスロットを作ってから確率的に抜く」方式で、抜けた分だけ間隔が不均一になっていました。`AdsUserLoadEvenSpread`（`home-mixer/params/param.rs:1154`）をONにすると「先に残す本数を決めてから等間隔に配置」する方式になります（`home-mixer/ads/slot_spread_blender.rs:101`、`home-mixer/ads/user_load.rs:177`）。広告の本数は変わらず、**間隔のばらつきだけが減る**変更です。
- **新しい広告特徴**: `AdInfo.advertiser_first_delivery_ms`（広告主が初めて配信した時刻、`recsys.proto:1825`）。新規広告主の識別に使えます。学習メトリクスに `fresh_dpa`（新鮮なダイナミック商品広告）スライスも追加（`phoenix/xrex/models/recsys_model.py:2638`）。
- **Grox の高PageRank判定に30分キャッシュ**（`grox/core/data_loaders/strato_loader.py:66`、`TTLCache(maxsize=100_000, ttl=30*60)`）: Grox が著者の「高PageRank（高信頼）」状態を参照する際、最大30分古い値を使うようになります。高信頼状態になった／外れた直後の反映が最大30分遅れます。
- **学習データ品質の修正**: 検索／retrieval 用のグローバルネガティブサンプリングで、`created_at` 列が無い／24時間以内の投稿が0件のスナップショットを使った場合、以前は空集合になりうる実装でした。今はスナップショット全体にフォールバックし警告を出します（`phoenix/xrex/data/parquet_recsys.py:111`、`:2551`）。
