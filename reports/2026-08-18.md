## 1. 非IT精通者向け:今日から意識するとよいこと

- **「最初の1いいね」が確実にカウントされるようになりました。** 従来は、投稿が初めていいねされた瞬間に検索・推薦用インデックスへ登録される処理が、内部のカウンタ更新の遅れ(競合)で取りこぼされることがありました。今回それが修正されています。**フォロワーの少ないアカウントほど恩恵が大きい**変更です。投稿直後に1件でもいいねが付くこと自体の価値が、これまでより安定して効きます。
- **「同じ話題の投稿が連続で並ぶこと」を、AIが認識できるようになりました。** これまでは「同じ**著者**が何回目に出てきたか」しか見ていませんでしたが、今回から「同じ**話題**が何回目に出てきたか」もモデルに渡されます。将来的に、同一トピックの連投がおすすめ欄で薄まる方向に働く可能性があります(**現時点ではモデルに渡しているだけで、明示的な減点処理は入っていません — 要確認**)。
- **フォロワー数そのものが、ランキングAIの入力になりました。** 従来は「あなたがその著者をフォローしているか」という関係性だけが渡されていましたが、今回から**著者の生のフォロワー数**が追加されています。大きいほど有利とは限りません(モデルが学習した通りに使われます)が、**フォロワー数がランキング判断の材料に入った**のは事実です。
- **フォロワー3万〜4万人規模のアカウント**が、AIによる返信ランキングの対象から外れ、代わりにリプライスパム検知の対象になりました。この規模の方の**返信欄の見え方が変わる**可能性があります。
- **成人向け判定に「AIによる再確認」の工程が追加**されました。2種類の判定器の結論が食い違ったとき、より高性能なモデルが再判定し、**多くの場合は判定を緩める方向(ハード→ソフト)に倒します**。誤って強い成人向け扱いを受けるケースが減る見込みです。
- **「フォロー中」タブが1ページあたり100件→110件に増え、「新しいポスト」の通知バーが出やすくなりました。** 表示上の細かな改善です。
- **Grokとの会話を共有した投稿**について、その会話内容がモデレーションAIの読み取り対象になりました。共有した会話の中身も安全性判定の材料になります。

## 2. 変更サマリ

- **セマンティックID(投稿内容から生成される階層的な話題コード)ベースの重複コンテキストが、ランキングモデルの入力に追加**された。L1〜L3の3階層それぞれについて「同じ話題が上位に何件あったか」「直前の同話題投稿との順位差」を算出して渡す。
- **著者のフォロワー数と、著者NSFWフラグ(安全性ビットマスク)が Phoenix モデルの入力特徴量に追加**された。
- **検索インデックス投入(`1fav`)の競合バグが修正**された。いいねイベントで発火するにもかかわらず「いいね数≥1」を再確認していたため、カウンタ更新の遅れで初回いいねを取りこぼしていた。同様にマルチモーダル埋め込みのメタデータ出力も無条件化。
- **広告ブランドセーフティ判定の v2 実装が追加**(`compute_verdict_v2`)。Grok の v2 系ラベル体系へ移行し、v1 由来の重複ラベルを除去する。**既定はオフ**(実験フラグ制御)。
- **grox の返信スパム検知/返信ランキングの発動フォロワー閾値が 30,000 → 40,000 に引き上げ**られた。あわせて返信ランキングが独立した Kafka ストリーム(v3トピック)へ分離され、パーティション単位の QPS レート制限機構が追加。
- **成人向けコンテンツの Grok 4.5 によるクロスバリデーション判定タスクが新設**された。safemodel と PTOS の結論が不一致のとき再判定し、不一致解消時は Soft へ緩和する。
- **bdsm(ボット検知)の最小アクション数ゲートも公開版では伏字化**(30 → `999999`)。公開コードでは是正措置ノートが一切発火しない状態になった。

## 3. 変更点ごとの詳細:メカニズム → Xユーザー/クリエイターへの影響

### 3.1 話題(セマンティックID)レベルの重複コンテキストをモデル入力へ追加 — 影響度: **中**(将来的に大)

**メカニズム**:
- `home-mixer/scorers/ranking_scorer.rs:647-702` の `compute_slate_contexts` が拡張された。従来は候補をスコア降順に並べ、**著者ID単位**で「何回目の登場か(`k`)」「直前の同一著者との順位差(`pool_rank_gap`)」を記録するだけだった。
- 今回、**セマンティックIDの階層プレフィックス単位**の同等統計が追加(`ranking_scorer.rs:661-680`):
  ```rust
  let sids = candidates[idx].semantic_ids.as_deref().unwrap_or(&[]);
  let sid_known = !sids.is_empty();
  let mut prefix = 0u64;
  for (level, &code) in sids.iter().take(3).enumerate() {
      prefix = (prefix << 20) | (code as u32 as u64 & 0xFFFFF);
      sid_k[level] = sid_counts[level].get(&prefix).copied().unwrap_or(0);
      sid_gap[level] = last_sid_rank[level].get(&prefix).map(|last| rank - last);
      ...
  }
  ```
  L1(最も粗い話題)→L3(細かい話題)まで、プレフィックスを 20 ビットずつ積み上げながら独立に集計する。
- セマンティックIDとは何か:`phoenix/reference/README.md:38` および `phoenix/README.md:244` によれば、各投稿を**残差量子化(RQ)した6階層のコード**で表したもの。内容(テキスト・画像・動画の埋め込み)から導出される「話題の住所」に相当する。L1 が最も粗い分類、階層が下るほど細分化される。
- 追加された7フィールドは `SlateContext` に格納され(`home-mixer/models/candidate.rs:84-90`)、`to_proto` 経由で **Phoenix 推論エンジンへ送られる**(`candidate.rs:166-179`)。
- **重要な限定**:Rust 側の多様性減衰処理 `author_diversity_multipliers`(`ranking_scorer.rs:707-720`)は**依然として著者カウント `k` のみ**を使っており、`sid_*` を掛け算に使う実装は入っていない。つまり現時点では「モデルへの入力特徴量として渡している」段階。
- `SlateContext` はログ出力フラグ `rust_home_mixer_log_slate_context`(`param.rs:240-245`、既定 `false`)も持ち、学習データ収集の系統に乗っている。

**Xユーザー/クリエイターへの影響**:
- **即時の体感変化は限定的**。モデルがこの特徴量をどう使うかは学習済み重みに依存し、コードからは決定できない(**要確認**)。
- ただし方向性は明確で、**「同じ著者の連投」に加えて「同じ話題の連投」が抑制対象になり得る**設計が敷かれた。話題単位の飽和が効き始めると、**特定ジャンルに特化したアカウント同士が同じ枠を奪い合う**構図になる。例えばあるニュースに対する類似投稿が10件並んだ場合、上位1〜2件以外が沈みやすくなる。
- **クリエイター視点の含意**:「バズっている話題に乗る」戦術の期待値が下がる方向。先行者(その話題で最初に上位に入った投稿)が有利で、後発の類似投稿は `sid_k` が積み上がった状態でモデルに渡る。
- **`sid_known` フラグの存在**に注意。セマンティックIDが未付与の投稿(新規投稿でコード化が間に合っていない等)は `sid_known=false` で渡り、話題重複の判定対象から外れる。これが有利に働くか不利に働くかはモデル次第(**要確認**)。

### 3.2 著者フォロワー数と著者NSFWフラグをモデル入力へ追加 — 影響度: **中**

**メカニズム**:
- `home-mixer/models/candidate.rs:234-238`:`AuthorInfo` に `followers` フィールドが追加された。
  ```rust
  followers: if self.retweeted_user_id.is_none() {
      self.author_followers_count.map(|c| c.max(0) as u64)
  } else {
      None

  ```
  従来この構造体は `..Default::default()` で埋められており、`author_id` / `is_followed_by_user` / `is_following_user` しか渡していなかった。**リポストの場合は `None`**(リポスト実行者のフォロワー数を元投稿の評価に混ぜない配慮)。
- `candidate.rs:202-208`:`TweetInfo.safety_label_mask` に、著者がNSFW判定を受けている場合のビット `SAFETY_BIT_AUTHOR_NSFW` が立てられるようになった。こちらもリポストは対象外。
- そのフラグの供給元 `home-mixer/candidate_hydrators/gizmoduck_hydrator.rs:139-150` に `nsfw_author_phoenix` が新設された:
  ```rust
  u.safety.nsfw_user || u.safety.nsfw_admin

  ```
  既存の `nsfw_author` / `nsfw_author_ads` とは別系統の、Phoenix モデル入力専用フラグとして定義されている(3系統が並存)。

**Xユーザー/クリエイターへの影響**:
- **フォロワー数がランキングモデルの直接の入力になった**。これは「フォロワーが多いほど有利」を意味しない — モデルは「フォロワー1万人の投稿にいいね1000件」と「フォロワー1000万人の投稿にいいね1000件」を区別できるようになるので、**むしろ規模で正規化される(小規模アカウントの高エンゲージメントが正当に評価される)方向にも働き得る**。どちらに効くかは学習結果次第(**要確認**)。
- 確実に言えるのは、**フォロワー数の増減がランキング挙動に影響を与える経路が1本増えた**こと。フォロワーを買う・大量相互フォローで水増しする等の行為は、この特徴量を通じて予測値を歪める可能性がある。
- **NSFW著者フラグがランキングモデルに渡る**ようになった。従来は表示可否のフィルタ(VF)と広告出稿判定に使われていたが、今回から**通常のおすすめランキングのスコア計算にも材料として入る**。NSFW判定を受けたアカウントは、フィルタで落とされずに残った投稿についても、モデル側でスコアが変わり得る。
- **リポスト時の除外設計は一貫している**。リポストされた投稿は「元投稿の著者」の属性で評価され、リポスト実行者のフォロワー数やNSFW状態は混入しない。**大規模アカウントによるリポストで数字を底上げする**効果は、少なくともこの経路では発生しない。

### 3.3 「初いいね」でのインデックス投入取りこぼしを修正 — 影響度: **中**(小規模アカウントには大)

**メカニズム**:
- `phoenix-rankall-strato/columns/phoenix_rank_all/phoenixRankAllCandidateProcessor.strato:78-89` の `build1FavIndex`。変更前は「いいね数が1以上か」を確認してからインデックス投入イベントを発火していた:
  ```
  if(ec.favoriteCount.getOrElse(0) >= 1) { ... insert ... }
  ```
- 変更後はチェックを撤廃し、**無条件に投入**。代わりにカウンタが0だったケースを計測用に記録する:
  ```
  if (candidate.engagementCount.flatMap { ec => ec.favoriteCount }.getOrElse(0) == 0) {
    stats.counter("1fav_uec_count_race").incr(1)
  }
  ```
- **なぜこれが正しいか**:呼び出し元(`.strato:447-449`)を見ると、この関数は `eventSource == Fav`(いいねイベント)の分岐でしか呼ばれない。つまり「いいねが発生した」ことは確定しており、`favoriteCount` の再確認は冗長だった。にもかかわらず、いいねイベントの到着がカウンタ集計の反映より速いと `favoriteCount == 0` と読めてしまい、**その投稿の初回いいねによるインデックス投入が丸ごと落ちていた**。カウンタ名 `1fav_uec_count_race`(uec = user engagement count)がこの競合の計測用。
- 同じ趣旨で `buildMMEmbMetadataDump`(`.strato:339-366`)からも「いいね数≥1」の外側チェックが外れ、マルチモーダル埋め込み(v3 / v5_1 / v6_dev)のメタデータ出力が全対象で走るようになった。NSFW動画の分岐(`.strato:442`)でも同関数が呼ばれる。
- なお `build32FavIndex`(いいね32件以上の高エンゲージメント用インデックス)は**変更なし** — こちらは閾値チェックが本来必要なので当然。

**Xユーザー/クリエイターへの影響**:
- **投稿が推薦候補プールに入る「入口」の信頼性が上がった**。従来は運悪くタイミングが噛み合った投稿が、初いいねを獲得しながらインデックスに載らず、For You の検索系候補生成から漏れていた。
- **恩恵はフォロワーの少ないアカウントに偏る**。フォロワーが多い投稿は短時間に何十件もいいねが付くため、たとえ1件目を取りこぼしても2件目・3件目のイベントで投入される。一方、**1日に数件しかいいねが付かない投稿は、その1件目を落とすと候補入り自体を失う**。今回の修正で、その取りこぼしがなくなる。
- **実務的な行動指針**:「投稿直後に最初の1いいねを付けてもらう」ことの効果が、これまでより**安定して**効くようになった。ただし効果の大きさが増したのではなく、**取りこぼしがなくなっただけ**である点は正確に理解しておきたい。
- マルチモーダル埋め込みメタデータの収集対象が広がったことで、**画像・動画投稿の内容理解の学習データが増える**。中長期的には視覚コンテンツのマッチング精度向上につながる方向。

### 3.4 広告ブランドセーフティ判定 v2(既定オフ) — 影響度: **小**(有効化時は中)

**Xユーザー/クリエイターへの影響**:

- 実質的な意味は「Grok による安全性判定が v2 世代のラベル体系へ移行しつつある」こと。`GROK_NSFA_EXPANDED_V2` という**適用範囲を拡げた判定**が中リスク集合に新設されている点は、将来的に**広告が載らない(=収益化されない)投稿の範囲が広がる**方向を示唆する(**要確認** — Expanded の具体的な判定基準はコードから読めない)。
- 従来どおり、`GROK_SFA_V2` 等による**明示的な安全判定を受けていない投稿は、既定で中リスク扱い**(`brand_safety.rs:125-129`)。また `PTOS_CUTOFF_TWEET_ID`(`brand_safety.rs:39`)以降の投稿は `PTOS_REVIEWED` ラベルがなければ中リスク。**新しい投稿ほど「審査済み」の印がないと広告面で不利**という構造は維持されている。

### 3.5 grox 返信フローの閾値引き上げと構成変更 — 影響度: **中**

**メカニズム**:
- **閾値の引き上げ**(`grox/flows/reply_spam/task_filter.py`):
  - `TaskSpamFilter.FOLLOWER_COUNT_THRESHOLD_FOR_SPAM_DETECTION`:30,000 → **40,000**(`task_filter.py:17`)
  - `TaskReplyRankingFilter.FOLLOWER_COUNT_THRESHOLD_FOR_REPLY_RANKING`:30,000 → **40,000**(`task_filter.py:185`)
- **両者は相補的**である点が重要。スパム検知は「返信先の著者**と**スレッド起点の著者が**両方とも**閾値以下」のとき発動(`task_filter.py:79-84`)。返信ランキングは逆に「**どちらかが**閾値超」のとき発動(`task_filter.py:214-224`、閾値以下なら `low_blast_radius` として除外)。
  → **境界が 30k から 40k へ動いたことで、フォロワー3万〜4万人規模のアカウントが「返信ランキング」対象から「スパム検知」対象へ移った**。
- 前回(8/15)は 15,000 → 30,000 だったので、**2回連続の引き上げ**であり、返信ランキングの適用範囲は継続的に絞られている。
- **返信ランキングの独立ストリーム化**(`grox/flows/reply_spam/generators.py:16-32`):従来 `PostStreamTaskGenerator` が `PlanSpamComment` / `PlanReplyRanking` / `PlanCoordinatedSpam` の3プランを同一ストリーム(`content-understanding-realtime-unified-posts`)に注入していたが、`PlanReplyRanking` が新設の `ReplyRankingTaskGenerator` へ分離され、**別トピック `content-understanding-realtime-unified-posts-v3`** から読むようになった。
- **レート制限機構の新設**(`grox/core/data_loaders/kafka_loader.py:107-144`):設定 `max_qps_per_partition`(`grox/config/config.py:124`、既定 `None`=無制限)に基づき、割り当てパーティション数 × QPS の固定窓レートリミッタでポーリングを絞る。上限到達時は `yield None` して処理をスキップする。

**Xユーザー/クリエイターへの影響**:
- **フォロワー3万〜4万人規模のアカウントの返信欄の見え方が変わる**。この帯の投稿への返信は、**AIによる返信ランキング(質の高い返信を上に出す整列)の対象から外れ**、代わりにリプライスパム検知の対象になる。返信欄が「整列される」から「スパムが落とされる」へ性格が変わる。
- **返信で伸ばす戦術**の観点では、返信ランキングの対象が**フォロワー4万人超のアカウントのスレッドに限定**された。中堅アカウントの投稿に良質な返信をしても、AIによる引き上げは受けにくくなる。
- **レート制限の新設は運用側の負荷制御**であり、直接の体験変化はない。ただし上限に当たった場合、**リアルタイム性が下がる(返信スパム判定が遅れる)可能性**はある(**要確認** — 本番の設定値は公開コードにない)。

### 3.6 成人向けコンテンツの Grok 4.5 クロスバリデーション — 影響度: **中**

**メカニズム**:
- 新規ファイル `grox/flows/ptos/task_safety_ptos_adult_content_cross_validation.py`(162行)。
- 従来 `task_safety_ptos_safemodel_sex_nudity.py` の中で行っていた「safemodel の判定 vs PTOS の判定」の突き合わせ(`_compare_outcome`)を**独立タスクへ切り出し**、`PlanSafetyPtos` のフロー最終段に配置した(`grox/flows/ptos/plan_safety_ptos.py:48-55`。結果書き込みタスクがこの新タスクに依存する形に変更)。
- **不一致時の再判定**(`task_safety_ptos_adult_content_cross_validation.py:81-88`):`deluxe` フローで判定が食い違った場合(`safemodel_only_positive` または `ptos_only_positive`)、`SafetyPtosAdultContentCrossValidationJudge` が **Grok 4.5(`EAPI_GROK_4_5_X_ALGO`、`grox/config/config.py:92` で新設)** に再判定させる。
- **緩和方向のバイアス**(同ファイル:132-159):再判定が `AdultContentSexualHard` でなければ、当該投稿の成人向け違反を **`AdultContentSexualSoft` へ書き換え**、`safemodel_sex_nudity.positive` を `False` に落とす。理由文字列は `"Grok 4.5 Cross Validation disagreed"`。逆に Hard と判定された場合は `return` して**何もしない**(元の判定を維持)。
  → つまりこの機構は**厳しい判定を緩める方向にのみ作用し、緩い判定を厳しくすることはない**。
- **重複処理の回避**:既に NSFW フラグが立っている投稿は再判定をスキップ(`_post_is_already_flagged_nsfw`、同:90-102)。同じチェックが `task_safety_ptos_safemodel_sex_nudity.py:89-93` にも追加され、判定済み投稿への無駄な推論を省く。
- **失敗時の安全側動作**:判定器の呼び出しが失敗した場合は元の判定を維持する(同:47-52、124-131)。回路ブレーカー(`grox/flows/ptos/classifier.py:85-93`、失敗率50%/600秒窓)付き。

**Xユーザー/クリエイターへの影響**:
- **成人向け「ハード」判定の誤検知が減る方向**。ハード判定は表示制限・広告除外の影響が大きいため、境界的なコンテンツ(芸術的なヌード、医療・教育的な内容、水着・下着の投稿など)を扱うクリエイターにとっては**有利な変更**。
- ただし**緩和は Soft への格下げであり、無罪放免ではない**。`AdultContentSexualSoft` として成人向け違反の記録自体は残る。
- **`deluxe` フローのみが対象**。標準フローでは計測(compare メトリクス)のみで再判定は走らない(同:81)。どの投稿が deluxe に回るかはコードから読めない(**要確認**)。おそらく高リーチ・高影響の投稿に限定されると推測されるが、根拠は取れていない。
- **判定に使うモデルが Grok 4.5 世代へ**。安全性判定の精度そのものが上がる方向で、**判定の一貫性(同じ投稿が日によって違う扱いを受ける現象)の改善**も期待できる。

### 3.7 bdsm(ボット検知)の最小アクション数ゲートも伏字化 — 影響度: **小**(公開版の解釈上は重要)

**メカニズム**:
- `bdsm/runtime/sink_policy.yaml:15` の `min_actions_for_enforcement` が **30 → `999999`** に変更された。
- 同様に `bdsm/runtime/score_results_sink_focal.py:223` のベイクイン既定値も `999999`。
- `build_enforcement_note` はハードコードの `30` を捨て、**引数 `min_actions` を受け取る形に変更**(同:100-115)。ロングクールダウンの閾値も、CLI 未指定時はポリシーの値へフォールバックする(同:1504-1508)。
- テストにも `assert pol.min_actions_for_enforcement > 10_000`(`bdsm/tests/test_sink_policy.py:33`)が追加され、**伏字状態であること自体が検証対象**になっている。
- README(`bdsm/README.md:106-124`)が明記する伏字化の理由:「アカウント規模の下限(これ未満では判定が一切発火しない)を公開することは、敵対者に検知回避の境界を渡すことになる」。

**Xユーザー/クリエイターへの影響**:
- **本番の挙動は変わらない**(本番値は内部設定)。変わったのは**公開コードの読み方**である。
- **前回(8/15)レポートで「bdsm の是正措置ノートが30アクション以上のゲートで実装された」と記述した点は、今回の変更により公開コード上では確認できなくなった**。`999999` は「どんな行動履歴でも到達しない」値であり、公開版をそのまま動かしても是正措置ノートは永久に生成されない。
- 実務上の含意:**ボット判定には「一定回数以上の行動履歴」という下限が存在する**という構造自体は README で明言されている。新規アカウントや行動量の少ないアカウントは、そもそもボット判定の俎上に載らない。具体的な下限値は不明(**要確認・意図的に非公開**)。

### 3.8 タイムライン表示の細かな変更 — 影響度: **小**

**メカニズム**:
- **「フォロー中」タブの1ページ件数**:`home-mixer/params/config.rs:24` の `FOLLOWING_MAX_RESULT_SIZE` が **100 → 110**。広告枠9件を差し引いた投稿取得数(`FOLLOWING_POST_FETCH_SIZE`)も 91 → **101** へ連動する。**広告枠数(`FOLLOWING_ADS_TOP_K = 9`)は据え置き**なので、**1ページあたりの広告比率は 9% → 8.2% へ微減**。
- **「新しいポスト」通知バー(ピル)の表示条件**:`home-mixer/util/urt/new_tweets_pill.rs:20-43` に引数 `require_full_facepile` が追加された。従来はアイコン3個(`NUM_AVATARS = 3`)分の投稿者が揃わなければピル自体を出さなかったが、
  - **For You**(`home-mixer/util/urt/mod.rs:54`)は `true` を渡し、**従来どおり3人揃わなければ出さない**。
  - **フォロー中(逆時系列)**(`home-mixer/util/urt/reverse_chron_following/mod.rs:38`)は `false` を渡し、**アイコンが揃わなくてもピルを表示する**ようになった。
- **クライアントイベントの投稿数カウント**:`home-mixer/side_effects/client_events_kafka_side_effect.rs:104-119` に `conversation_post_count` が追加され、返信スレッドの候補について**起点投稿と直前の親投稿も件数に算入**するようになった。ログ・計測系の変更であり表示には影響しない。

**Xユーザー/クリエイターへの影響**:
- **「フォロー中」タブの1回のスクロールで見られる投稿が10件増え、広告比率がわずかに下がった**。フォロー中タブを主に使うユーザーには小さな改善。
- **フォロー中タブで「新しいポスト」バーが出やすくなった**。フォロー数が少ないユーザー、または更新頻度の低いタイムラインでも、新着があれば通知される。**投稿から短時間での再訪が促されやすくなる**ため、フォロワーの再訪タイミングを狙う投稿(定時投稿など)には追い風。

### 3.9 Grok共有会話のモデレーション入力化 — 影響度: **小**

**メカニズム**:
- `grox/core/data_loaders/data_types.py:390-410` に `GrokShare` モデルが新設され、`Post.grok_share_metadatas` として保持される(同:668)。
- `grox/core/lm/post.py:82-88` で、レンダリング時に「この投稿には共有された Grok の会話が含まれます」という説明とともに**送信者と本文がモデル入力へ展開**される。
- あわせて `LegacyCard.to_convo`(`data_types.py:369-388`)がリファクタされ、**中身が空のカードは `[Card]` ヘッダーごと出力しない**ようになった(従来は空でもヘッダーだけ出ていた)。Grok共有カードの処理はこの新しい `GrokShare` 経路へ移管。
- Strato 経路(`grox/core/data_loaders/post_mapper.py:122-127, 315-320`)にも同等のマッピングが追加された。

**Xユーザー/クリエイターへの影響**:
- **Grokとの会話を共有した投稿は、その会話内容まで含めて安全性・スパム判定を受ける**。共有した会話に問題のある内容が含まれていれば、投稿本文が無害でも判定に影響し得る。
- 逆に、**投稿本文だけでは文脈がわからない共有投稿が、正しく理解されるようになった**という側面もある。従来は会話内容がモデルに渡らず、判断材料が不足していた。
- 空カードのヘッダー出力抑制は、**モデルに渡るノイズの削減**。判定精度の地味な改善。

### 3.10 その他の技術的変更 — 影響度: **小**

- **`grox/flows/ptos/state.py:91`**:`SafemodelResult` に `scored` フラグが追加。「判定を実行したが陰性」と「そもそも判定していない」を区別できるようになり、3.6 のクロスバリデーションが**判定を実行した投稿だけを対象にする**ための前提になっている。

## 5. 不確実な点(要確認)

1. **`sid_*` 特徴量を推論モデルが実際にどう使っているか**は、公開されている Rust コードからは決定できない。Rust 側に明示的な減点処理はなく、モデルの学習済み重みに依存する。「話題の連投が沈む」と断定はできない。
2. **`followers` 特徴量が有利に働くか不利に働くか**も同様。モデル入力に入ったことは確実だが、方向性はコードから読めない。
3. **`GROK_NSFA_EXPANDED_V2` の判定基準**が不明。名称から適用範囲の拡大が読めるが、具体的にどのようなコンテンツが新たに中リスク判定を受けるかはコード上に情報がない。
4. **成人向けクロスバリデーションの `deluxe` フローの対象範囲**が不明。どの投稿が deluxe として処理されるかを決めるロジックは公開コードにない。
5. **grox の `max_qps_per_partition` の本番設定値**が不明(既定 `None`=無制限)。実際にレート制限が効いているか、効いているなら判定の遅延がどの程度かは判断できない。
6. **bdsm の `min_actions_for_enforcement` の本番値**は意図的に非公開(`999999` は伏字センチネル)。ボット判定の下限アカウント規模は判断できない。
7. **`1fav` インデックス投入の競合がどの程度の頻度で発生していたか**は、追加された `1fav_uec_count_race` カウンタの実測値がなければわからない。修正のインパクトの大きさは定量化できない。
8. **`nsfw_author` / `nsfw_author_ads` / `nsfw_author_phoenix` の3系統が並存している**理由と、それぞれの判定基準の差分は部分的にしか読めない。`nsfw_author_phoenix` が `NSFW_HIGH_PRECISION` と `POSSIBLY_NSFW_ACCOUNT` の両方を含む点は確認できたが、他系統との厳密な比較は未実施。
