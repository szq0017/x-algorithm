## 非IT精通者向け・運用方法のまとめ（行動指針）

> 今回は **22ファイル・約1,400行**の小〜中規模の回です。**ただし既定値（スイッチ）の変更が2件あり、どちらも本日からフィード上で実際に効きます。** 特に①は「誰の投稿が候補に入るか」という供給側の変更で、昨日まで0件だったものが一気に稼働します。

- **① 【最重要・既定で有効・本日から稼働】「人気投稿」経路のスイッチが入りました（後述1）。**
  - 昨日まで `false`（＝1件も配信されていない）だった `EnablePopularPostsSource` が **`true`** になりました（`home-mixer/params/param.rs:944-948`）。
  - 中身は**「全ユーザー共通の人気投稿リスト（最大500件）」**です。直近24時間の投稿のうち、**閲覧数を経過時間で割り戻した「勢い」スコア**の上位を、5分ごとのバッチジョブが選んで作ります。対象著者は**「直近7日に投稿した人のうちフォロワー数上位 0.005%」**です。
  - **あなたへの意味**：フォロー外（OON）の候補枠に、**大手アカウントの“今バズっている原投稿”が毎リクエスト最大500件、追加で混ざってくる**ようになりました。「同じ有名人の投稿がやたら目に入る」という体感が出た場合、これが原因である可能性が高いです。
  - **ただし“押し込み”ではありません**。候補に加わるだけで、順位は従来と同じモデルがあなた個人向けに点数を付けて決めます（枠の確保・優先挿入はコード上存在しません）。興味がなければ点数が低くなり、表示されません。
  - **クリエイター向け**：フォロワー数上位0.005%に入っていないアカウントは、**OON枠の競争相手が一気に増えました**。逆に上位0.005%に入るアカウントは、**投稿後の最初の数時間で閲覧数を伸ばせるかどうか**が追加露出の有無を決めます（勢いスコアの半減期は8時間）。**返信・リポストは対象外で、原投稿のみ**です。

```rust
    (_, fetched @ (NotFound(_) | Failed(_))) => Some(fetched),
    (Self::Evaluated(state), _) => Some(*state),      // ← Filtered も上書きされていた
    (Self::NotEvaluated | Self::Failed, _) => None,
}
```

**差分の本質**：変更前は、投稿ストアが **`Filtered`（＝「この投稿は出せません」＋理由）** を返していても、VF の `Evaluated` 判定がそれを**上書き**していました。変更後は `Filtered` がそのまま保持され、**VF の判定が勝つのは投稿ストアが `Found` を返したときだけ**になります。新しいテスト名がこれを明示しています：`evaluate_tweets_loopback_overrides_only_a_tweetypie_found`（`visibility-filtering/server.rs:190`）、テストケースに `(tweet(1, None), protected(), Some(protected()))`（＝`FilteredReason::AuthorIsProtected` が保持される）が追加されています（`server.rs:204-217`）。

**(b) VF が投稿を解決できなかった場合の扱い**（`visibility-filtering/evaluate_tweets.rs:156-167`）：

変更後：
```rust
match evaluations.get(&TweetId(tweet.tweet_id)) {
    Some(evaluation @ Evaluation::Complete { .. }) => {
        evaluated_outcome(evaluation.verdict(), safety_level, &policies)
    }
    Some(
        Evaluation::NotFound(_)
        | Evaluation::Partial { .. }
        | Evaluation::Failed(_),
    )
    | None => Outcome::Failed(vf_pb::Failed {}),
}
```

変更前は `Evaluation::NotFound(_)` も `Complete` と同じ扱いで、**`Verdict::not_found()`（＝却下判定）がクライアントに返されていました**（`visibility-filtering/models/verdict.rs:176-179` の `Self::NotFound(_) => &NOT_FOUND`）。変更後は **`Outcome::Failed`（＝判定できなかった）**として返されます。

**(a)(b) を合わせた一貫した原則**：
> 投稿ストア（tweetypie）が「この投稿を出せるか」について自分の答えを持っているなら、その答えが最終。VF の判定は、投稿ストアが「出せます（Found）」と答えた投稿にだけ適用される。

#### Xユーザー/クリエイターへの影響

| ケース | 変更前 | 変更後 | ユーザーへの意味 |
|---|---|---|---|
| **鍵アカウント（保護）の投稿が非フォロワーに混ざった** | 投稿ストアの `Filtered(AuthorIsProtected)` が VF の判定で上書きされ得た | `Filtered(AuthorIsProtected)` が**保持される** | **安全側の修正。** 判定のすれ違いで鍵アカウントの投稿が表に出る経路が1つ閉じた |
| **削除済み投稿** | VF の「見つからない」理由で却下 | 投稿ストアの `NotFound` をそのまま返す | **表示上の結果は同じ**（表示されない）。返る理由コードが変わるだけ |
| **投稿ストアは取得できたが VF が投稿を解決できなかった** | VF の却下判定が適用され、**投稿は却下** | `Failed` → 上書きなし → **投稿ストアの `Found` が使われる** | **緩和方向の変化。** VF側のデータ欠損時に、安全性判定が適用されないまま配信される可能性がある（下記「不確実な点」参照） |

#### 影響度評価：**中**

理由：既定で有効な実挙動の変更で、プライバシー（鍵アカウント）に直接関係します。方向としては「投稿ストアの判断を尊重する」一貫した整理で、主効果は**安全側**です。ただし VF 側のデータ欠損時の扱いが**緩和方向**に動いているため、両面があります。

### 4. 【影響度：小（将来は中）・既定オフ】検索ランキング学習の語一致特徴量のリーク修正

#### メカニズム（コード根拠）

**問題**：Phoenix の学習では「ネガティブサンプル（ハズレ例）」を他のユーザーの候補から借りてきて作ります（`phoenix/xrex/data/recsys/recsys_batch.py:1193` の `apply_negative_sampling`）。このとき、**検索語との語一致を表す2つの特徴量**——
- `exactPhraseSeq`（検索フレーズの完全一致、カテゴリ特徴 index 16：`feature_config.py:21`）
- `matchedWordFractionSeq`（検索語のうち本文に一致した語の割合、float特徴 index 1：`feature_config.py:55`）

——が**元の（別の検索語に対する）値のまま貼り付いてしまっていました**。ネガティブサンプルは別の検索語とペアになるため、これは**誤ったラベル**です。

**修正**（`recsys_batch.py:1476-1486`）：
```python
negative_slots = new_post_hashes[:, :, 0] != 0
negative_slots[:, :max_candidate_post_action_pairs] = False
if has_search_query and clear_negative_word_match:
    clear_word_match(new_categorical_features, new_float_features, negative_slots)
if has_search_query and lexical is not None:
    compute_word_match(
        new_categorical_features, new_float_features, negative_slots,
        new_lexical_text, new_lexical_query, new_lexical_author,
    )
```

- **`clear_word_match`**（`negative_word_match.py:11-21`）：ネガティブスロットの両特徴量を **0 にクリア**。
- **`compute_word_match`**（`negative_word_match.py:24-47`）：新規列 `lexicalTextSeq` / `lexicalQuerySeq` / `lexicalAuthorSeq`（`feature_config.py:171-173`、`recsys_batch.py:355-357`）に生テキストを運び、本番と同じ語一致ライブラリ `xai_search_lexical_match.search_lexical_match` で **（ネガティブ投稿の本文、実際の検索語、著者名）から正しい一致度を再計算**して埋め直す。

**既定値**：`search_negative_clear_word_match` は **既定 `False`**（`phoenix/xrex/configs/data_feeds.py:139`、`phoenix/xrex/data/streaming/kafkaloader.py:1007`）。有効化している設定ファイルはリポジトリ内に**ありません**。

#### Xユーザー/クリエイターへの影響

- **今日の影響：ゼロ**（既定オフ、かつ学習側の変更なので、再学習されたモデルが配信に乗るまで効きません）。
- **有効化された場合**：検索ランキングモデルが「検索語が本文に実際に含まれているか」をより正確に学習します。
  - **検索利用者**：検索語と本文が本当に一致している投稿が上がりやすくなる方向。
