## 非IT精通者向け：運用方法のまとめ（行動指針）

今回は **「既定で即日効いてくる変更」が3件**、**「準備だけ整った大型機能」が1件** です。順に書きます。

### いますぐ気をつけること

- **自分の投稿に警告ラベル（FOSNR）が付くと、今日から自分自身も操作を奪われます。**
  これまでは「他人には出ないが自分には普通に見える」状態でした。今日からは、重い違反（憎悪的言動・暴力的発言・ハラスメント・市民プロセス完全性）のラベルが付くと、**自分の投稿に対して いいね・返信・リポスト・引用・共有・ブックマーク・プロフィール固定・リンクコピー・DM送信・編集・ハイライト・埋め込み・リスト追加 の13操作すべてができなくなります**（異議申立てボタンは出ます）。軽い違反（侮辱）は編集だけが止まります。
  → **行動指針：** 荒れやすい話題では、投稿前に文面を見直す価値が上がりました。ラベルが付いてから直す（編集する）ことができなくなるためです。異議申立ては可能なので、不当だと思ったらその場で申し立ててください。

- **場所を指定した「ローカル投稿」は、その地域の外の人からリポストと返信ができなくなりました。**
  地域外の人でも**読むことはできます**が、リポストと返信だけが止まります。投稿した本人・会話に招待された人・ログアウト中の人は制限されません。
  → **行動指針：** 拡散を狙う投稿に場所を指定しないでください。場所指定はリポスト経路を自ら閉じる設定になります。逆に、近所の人だけで静かに話したいときには有効な道具です。
  → **注意：** 位置情報がシステム側で取得できない閲覧者は「地域外」と見なされて制限されます（位置情報をオフにしている人など）。つまり**場所指定投稿は想定より届きにくい**可能性があります。

- **コミュニティから除名された人は、そのコミュニティの投稿に返信できなくなりました。**
  リポスト経由で流れてきた場合も同じく制限されます。iOS/Android の 10.16.0 以降のアプリが対象です。

### 準備が整っただけ（まだオフ）のもの

- **縦型動画を3〜5本まとめた「動画カルーセル」がFor Youの6番目に入る仕組みが追加されました（既定オフ）。**
  オンになると、**縦型（縦長）動画**の露出が構造的に増えます。選ばれる基準は「その動画が開かれる確率の予測値」のみで、いいね数やリポスト数ではありません。返信は対象外です。
  → **行動指針（先回りするなら）：** 動画を出すなら**縦型（9:16など縦長）**で撮ってください。横型（16:9）はカルーセルの選考から外れます。また、カルーセルは**本文フィードに出なかった「惜しくも落ちた」動画**から選ばれる設計なので、「全体スコアは中くらいだが動画としては開かれやすい」投稿に新しい露出経路ができます。同じ人に60分以内に再表示はされません。

### 裏側で変わったこと（直接の操作はありません）

- **「どれくらい読まれたか（滞在時間）」の予測方式が作り直されました。**
  これまでは「平均何秒か」を直接当てる方式でしたが、今日から「2秒超か？ 3秒超か？ …240秒超か？」を30段階で当てて積み上げる方式に変わりました。短い流し見と長い熟読をはっきり区別できるようになります。
  → **行動指針：** **長く読ませる投稿（長文・読み物・じっくり見る画像）の評価が今より正確に上がる方向**です。スコアの重み自体は変わっていないので劇的な変化ではありませんが、「数字（いいね）は伸びないが読まれている投稿」が正しく評価されやすくなります。
  → 併せて、**通報・興味なし・ブロック・ミュートを押された投稿の「滞在時間0秒」は、単なるデータ欠損とは別扱い**になりました。ネガティブ反応がより正確に学習されます。

- **返信スパム判定が一部で厳しく、一部で緩くなりました。**
  - 「影響力の高いアカウントなのでスパム判定を免除する」基準が **62点 → 66点** に上がりました（免除されにくくなる＝厳しくなる）。これは9月以降 60→62→66 と続く**継続的な引き締め**です。
  - 一方、「大型アカウントのスレッドでの組織的スパム検出」の対象が **フォロワー12.5万人以上 → 18万人以上** に絞られました。**フォロワー12.5万〜18万のアカウントのリプ欄では、組織的スパムの検出が行われなくなります**。
  → **行動指針：** フォロワー10万〜20万規模のアカウントを運用している方は、リプ欄のスパムが増える可能性に備えてください（手動のミュート/ブロック運用の重要度が上がります）。大型アカウントへのリプライで伸ばそうとしている方は、スパム判定の網が以前より細かくなっています。

## 変更サマリ

1. **FOSNRラベル付き投稿の著者本人に「異議申立て可能な通知」と操作制限を新設（既定で稼働）** — 従来は著者には無制限表示だった。レベル3で13操作、レベル1で編集のみを制限。
2. **「ローカル投稿」（場所指定投稿）の地域外閲覧者に対するリポスト・返信制限を新設（既定で稼働）** — 位置情報は Strato `geo/service/userLocation` から取得。位置不明は「地域外」扱い。
3. **コミュニティ除名者の操作制限を新設（クライアント 10.16.0 以降で稼働）** — 返信・プロフィール固定を制限、リポスト経由にも伝播。
4. **縦型動画カルーセル（3〜5本、For You 6番目、疲労60分）を新設（既定オフ）** — Top-50圏外の動画を別枠30件確保し、`video_open_score` 降順で選抜。
5. **滞在時間の学習を Tweedie/MAE 回帰から CREAD（30段階しきい値分類＋復元回帰）に全面切替（ホーム本番configで稼働）** — 履歴側の滞在時間も240秒上限の区分線形埋め込み化＋ネガティブ反応専用行を新設。
6. **Grox 返信スパム：高影響力免除の信用スコア 62→66（厳格化）、組織的スパム検出のフォロワー下限 12.5万→18万（対象縮小）**。
7. 広告のドロップ理由ログ化（挙動は等価）、`phoenix-rankall` の Rust 特徴量ハイドレート基盤新設、二塔検索モデルへの Mixture-of-Logits 追加（既定オフ）など基盤整備。
8. **ランキング重み（`ScoringWeights` / `*Weight` 系パラメータ）の数値変更はありません。** 予測ヘッドの増減もありません。

## 変更点ごとの詳細

### 1. FOSNR投稿の著者本人への「異議申立て可能な通知」＋自分の投稿への操作制限【影響度：大・既定ON】

**メカニズム**

新しい判定アクション `ActionSpec::Appealable` と、著者のみを対象にする観客種別 `Audience::OnlyAuthor` が追加されました（`visibility-filtering/rules/rule_spec.rs:453-480`）。severity は **18** で、ドロップ（17）より高く、**最優先で適用されます**（`rule_spec.rs:535-539`）。

ルール本体は `fosnr_author_appealable()`（`visibility-filtering/rules/tweet_rules.rs:696-707`）。条件は「クライアントがFOSNRルール対応」かつ「FOSNRラベル5種のいずれかが付いている」で、対象は投稿の著者のみです。クライアント対応フラグ `fosnr_rules` の既定値は **true**（`visibility-filtering/models/viewer.rs:72-83`）なので、**実質的に既定で有効**です。

制限される操作は違反レベルで分かれます（`tweet_rules.rs:652-694`）：

- **レベル3**（`FOSNR_HATEFUL_CONDUCT` 憎悪的言動 / `FOSNR_VIOLENT_SPEECH` 暴力的発言 / `FOSNR_ABUSE` ハラスメント / `FOSNR_CIVIC_INTEGRITY` 市民プロセス完全性）→ 13操作：
  `Like`（いいね）, `Reply`（返信）, `Retweet`（リポスト）, `QuoteTweet`（引用）, `ShareTweetVia`（共有）, `AddToBookmarks`（ブックマーク）, `PinToProfile`（プロフィール固定）, `CopyLink`（リンクコピー）, `SendViaDm`（DM送信）, `EditTweet`（**編集**）, `Highlight`（ハイライト）, `Embed`（埋め込み）, `ListsAddRemove`（リスト追加削除）
- **レベル1**（`FOSNR_ABUSE_INSULTS` 侮辱）→ `EditTweet`（編集）のみ

クライアントへは `TweetInterstitial` として、異議申立て情報（`Appealable` / `AppealableReason`：ポリシー種別・レベル・自動検出か人間申告か・既に異議申立て済みか）と制限操作リストが一緒に返されます（`visibility-filtering/treatment.rs` の `fosnr_limited_engagements` / `appealable_reason`）。レベル3には `freedom_of_speech_not_reach` のヘルプリンクが付きます。

**従来挙動との差分（ゴールデンコーパスで確認）**

`visibility-filtering/rules/golden_corpus/tweet_label.rs:139-150` 他で、`(TimelineHomeHydration, Role::Author)` の期待値が **`allow()`（無制限表示）→ `appealed(...)`** に変わっています。4つのレベル3ラベルすべてと、レベル1（`oon_tweet_label.rs:235-248`）で同様です。レベル3とレベル1が同時に付いた場合はレベル3が優先されます（`FOSNR_AUTHOR_VIOLATIONS` の並び順、`tweet_rules.rs:680-694`）。

**Xユーザー/クリエイターへの影響**

- FOSNRラベルが付いた瞬間、**自分の投稿を編集して直すことができなくなります**。これが最も実務的に痛い点です。レベル1（侮辱）でも編集は止まります。
- 自分の投稿を自分でリポスト・引用して補足する、DMで共有する、プロフィールに固定する、といったリカバリー手段も全部塞がれます（レベル3）。
- 一方で、**異議申立ての導線がその場に出るようになった**ため、「気づかないまま露出が落ちていた」状態より改善とも読めます。これまでは著者側には何の表示もありませんでした。
- 対象面は `TimelineHomeHydration`（ホームタイムラインのハイドレーション段）です。`TimelineHome` レベルでは著者は従来どおり `allow()` のままです（`tweet_label.rs:141`）。

### 2. ローカル投稿（場所指定投稿）の地域外閲覧者へのリポスト・返信制限【影響度：中〜大・既定ON】

**メカニズム**

投稿側に `narrowcast_place_id: Option<u64>`（ナローキャスト＝対象を絞った配信先の場所ID）が追加されました（`visibility-filtering/models/tweet.rs`、`hydration/tweet_source.rs:69,174`）。

閲覧者の位置は新規クライアント `ProdUserLocationClient` が Strato の `geo/service/userLocation` 列から取得します（`visibility-filtering/clients/user_location_client.rs:12-57`）。問い合わせる場所タイプは5種（`PLACE_TYPES: [4, 3, 7, 9, 1]`、国/地域/都市などの粒度と思われます（要確認））、信頼度フィルタ `filter_by_confidence` は **true** です（`user_location_client.rs:14-20`）。本番配線済みです（`visibility-filtering/server_deps.rs` に `ProdUserLocationClient::new(stratoserver.clone())`）。

ハイドレーター `Hydrator::OutsideNarrowcastPlace`（`visibility-filtering/hydration/mod.rs:70`）が、投稿の場所IDが閲覧者の所在場所集合に含まれるかを判定します（`hydration/plan.rs:344-349`）。

ルール本体は `local_tweet_limited_actions()`（`visibility-filtering/rules/tweet_rules.rs:873-886`）。条件は以下すべて：

1. 投稿に場所ID がある（`TweetPredicate::HasNarrowcastPlace`）
2. 閲覧者がログイン済み（`NOT_LOGGED_OUT`）
3. 閲覧者が会話ルートの著者でない（`NOT_CONVERSATION_ROOT_AUTHOR`）
4. 閲覧者が会話に招待されていない（`NOT_INVITED_TO_CONVERSATION`）
5. 閲覧者がその場所の外にいる（`RelationshipPredicate::ViewerIsOutsideNarrowcastPlace`）

制限される操作は **`Retweet`（リポスト）と `Reply`（返信）の2つだけ**です（`visibility-filtering/params/limited_actions_policy.rs:308`、コピー名前空間 `LocalPost`）。**閲覧・いいね・ブックマークは制限されません。**

**重要な境界条件（`rules/golden_corpus/local_tweet.rs` と `filter.rs` のテストで確認）**

| 状況 | 結果 |
|---|---|
| 地域外のログインユーザー | **リポスト・返信を制限** |
| 地域内のユーザー | 制限なし |
| 投稿の著者（会話ルート著者） | 制限なし |
| 会話に招待されたユーザー | 制限なし |
| ログアウト中 | 制限なし |
| **位置情報が空で返ってきた**（位置が取れない） | **「地域外」扱いで制限** |
| 位置ルックアップが**失敗**した（エラー） | fail-open で**制限なし** |
| 会話コントロールが `Local` だが場所IDがない | 制限なし |
| 地域外の人が書いた**ローカル投稿への返信**（会話ルート著者が別人） | その返信の著者**自身も制限される** |
| NSFWラベル付きローカル投稿 | ぼかし＋ローカル制限の**両方**が適用 |
| `ByInvitation` コントロール併用 | 会話コントロール制限＋ローカル制限の**両方**が適用 |
| 判定面 | `TimelineHomeHydration` のみ。`TimelineHome` では制限なし |

**Xユーザー/クリエイターへの影響**

- **拡散と場所指定はトレードオフになりました。** 場所を指定した投稿は、その地域の外からリポストされません。バイラルを狙う投稿で場所を指定するのは逆効果です。
- **位置情報を共有していない閲覧者も「地域外」と扱われます。** つまり場所指定投稿の実効リーチは、地域人口より小さくなる可能性があります。プライバシー設定で位置をオフにしている層は相当数いると考えられるため、**場所指定投稿は想定よりかなり届きにくい**と見るのが妥当です。
- 逆に、**近隣コミュニティ向けの告知・募集・イベント情報には有効な道具**です。地域外からの無関係なリプライやリポストが構造的に止まります。
- ローカル投稿の**スレッドに返信した人も、自分が地域外なら自分の返信に制限がかかります**。地域外からローカル会話に参加するのは実質困難です。

### 3. コミュニティ除名者の操作制限【影響度：中・クライアント10.16.0以降でON】

**メカニズム**

Strato 列 `communities/isRemoved.Community` を参照する `viewer_removals()` が追加され（`visibility-filtering/hydration/community_source.rs`）、`HydratedTweetCandidate::viewer_is_removed_from_community` として判定に渡されます（`visibility-filtering/models/mod.rs:69`、`rules/context.rs:128-132`）。

ルールは `community_tweet_limited_actions()`（`tweet_rules.rs:859-871`）。条件は「コミュニティ投稿」＋「閲覧者がそのコミュニティから除名済み」＋「クライアントが対応」。制限は **`Reply`（返信）と `PinToProfile`（プロフィール固定）** の2つ（`limited_actions_policy.rs:304-307`、コピー名前空間 `ViewerIsRemovedFromCommunity`）。

クライアント対応は新スイッチ `community_tweet_viewer_removed_limited_actions_rules_enabled`（`params/client_switches.rs:36-38`）で、既定値は **false**（`models/viewer.rs:78`）、バージョンゲートは **iOS / Android ともに 10.16.0 以降**で有効（`params/client_switches.rs` のテスト：`10.15.9`→false、`10.16.0`→true）。

**リポスト経由にも伝播します**：除名されたコミュニティ投稿の**リポスト**に対しても同じ制限が返ります（`visibility-filtering/retweet.rs` の `a_viewer_removed_from_the_community_is_limited_on_any_retweet_of_its_post` テスト）。

コミュニティ関連では他に `CommunityTweetHidden`（非表示化）、`CommunityTweetMemberRemoved`（著者除名）、`CommunityTweetCommunityNotFound/Deleted/Suspended`（コミュニティ消滅・削除・凍結）の操作制限ポリシーが整理され、クライアントへの通知理由として送られるようになりました（`visibility-filtering/treatment.rs`、`params/limited_actions_policy.rs:276-307`）。

**Xユーザー/クリエイターへの影響**

- コミュニティから除名されると、そのコミュニティの投稿（およびそのリポスト）に**返信できなくなります**。読むことと、いいね等は制限されません。
- コミュニティ運営側から見ると、**除名が「書き込み遮断」として実際に機能するようになった**ということです。これまでは除名後も返信経路が残っていました。
- 古いアプリ（10.15.x 以前）では従来どおり制限されません。**同じ除名ユーザーが、アプリのバージョンによって返信できたりできなかったりします。**

### 4. 縦型動画カルーセル（Video Carousel）【影響度：大（有効化された場合）・既定オフ】

**メカニズム**

3つの新パラメータ（`home-mixer/params/param.rs:1041-1058`）：

| パラメータ | 既定値 | 意味 |
|---|---|---|
| `EnableVideoCarousel` | **false** | 機能の有効化 |
| `VideoCarouselFatigueMinutes` | **60** | 同一ユーザーへの再表示を抑える間隔（分） |
| `VideoCarouselPosition` | **6** | 挿入位置（フィードの6番目） |

定数（`home-mixer/params/config.rs:18,35-36`）：`VIDEO_CAROUSEL_MAX_VIDEOS = 5`、`VIDEO_CAROUSEL_MIN_VIDEOS = 3`、`VIDEO_CAROUSEL_EXTRA_CANDIDATES = 30`。フィードのモジュール枠 `FEED_MODULE_SLOTS` が **4 → 5** に増えました（`config.rs:20`）。

有効条件は3つすべて（`home-mixer/util/video_carousel.rs:7-11`）：リクエストが **For You**、パラメータON、**疲労窓クリア**（直近60分に出していない。`query_hydrators/served_history_query_hydrator.rs:52-58` で `EntityIdType::VIDEO_CAROUSEL_MODULE` の配信履歴を参照）。

**候補の確保と選抜（ここが行動への含意を持つ部分）**

1. Top-K選抜時に、通常の上位50件（`TOP_K_CANDIDATES_TO_SELECT`）とは**別枠で動画を最大30件追加確保**します（`home-mixer/selectors/top_k_score_selector.rs:11-27`）。選抜基準は総合スコアではなく **`video_open_score`（動画が開かれる確率の予測値）の降順**（`util/video_carousel.rs:28-43`）。これらには `video_carousel_extra = true` の印が付きます。
2. カルーセルに載る動画は、**本文フィードの表示枠（`RESULT_SIZE = 35`）より後ろの候補と、別枠で確保した追加候補**から選ばれます（`home-mixer/filters/video_carousel_filter.rs:22-24`：`kept.iter().skip(RESULT_SIZE).chain(&removed)`）。つまり**「本文には出なかった動画」の救済枠**です。
3. 絞り込み条件（`util/video_carousel.rs:45-55`）：
   - 動画がある（`has_video == Some(true)`）
   - **返信ではない**（`in_reply_to_tweet_id.is_none()`）
   - `video_open_score` の予測値が存在する
   - **縦型**：アスペクト比 < 1.0（`MAX_VERTICAL_ASPECT_RATIO`）。**正方形（1.0）と横型（16:9 = 1.778）は除外されます**
4. `video_open_score` 降順で最大5本。**3本に満たなければカルーセル自体を出しません**（`util/video_carousel.rs:22-24`）。

アスペクト比は新規ハイドレーター `VideoAspectRatioHydrator` が TES（Tweet Entity Service）から取得します（`home-mixer/candidate_hydrators/video_aspect_ratio_hydrator.rs`）。このハイドレーターと `VideoCarouselFilter` は、機能がONのときだけ動きます。

`VideoCarouselFilter` はパイプラインの**最後**に置くことがテストで固定されています（`candidate_pipeline/phoenix_candidate_pipeline.rs:1135-1143`）。可視性フィルタ（VFFilter / AncillaryVFFilter）を通った後の候補だけが対象です。

挿入は `insert_video_carousel()`（`selectors/blender_selector.rs:137-153`）で、`VideoCarouselPosition - 1` のインデックスに差し込まれます。

**Xユーザー/クリエイターへの影響**

- **縦型動画の構造的優遇です。** 有効化されれば、9:16 などの縦長動画は「本文フィード」と「カルーセル」の二経路で露出機会を持ちます。16:9 の横型動画はカルーセル経路に一切乗りません。
- **選抜基準が `video_open_score` 単独であることが重要です。** いいね・リポスト・滞在時間ではなく「サムネイルを見てタップされる確率」のみで選ばれます。つまり**サムネイル（冒頭フレーム）の訴求力が、カルーセル露出の唯一の決定要因**になります。
- **「本文に出なかった動画」の救済枠**という設計なので、総合スコアが中位の動画投稿者にとって新しい入口です。逆に、既に本文上位に出ている動画はカルーセルには入りません（二重露出はしない設計）。

- 60分の疲労間隔があるため、1人のユーザーに対しては1時間に1回までです。
- フィードのモジュール枠が4→5に増えたので、**オーガニック投稿が見える位置が1つ分後ろにずれる**可能性があります（`FOR_YOU_MAX_RESULT_SIZE = RESULT_SIZE + FEED_MODULE_SLOTS + MAX_JETFUEL_FRAMES_PER_RESPONSE`、`config.rs:22-23`）。

### 5. 滞在時間（dwell time）の学習方式を CREAD に全面切替【影響度：中・ホーム本番configで稼働】

**メカニズム（損失関数側）**

ホームのランキングモデル本番config `_home_direct_packed_base()`（`phoenix/xrex/configs/xrecsys.py:253-`）で、滞在時間の学習重みが入れ替わりました（`xrecsys.py:272-275`）：

| 損失 | 旧 | 新 |
|---|---|---|
| `dwell-time-tweedie`（Tweedie回帰、power 1.5、上限300秒） | 0.1 | **0.0（無効化）** |
| `dwell-time-mae`（平均絶対誤差回帰） | 0.1 | **0.0（無効化）** |
| `dwell-time-binary-10s`（10秒超か否かの二値） | 変更なし | 変更なし |
| `dwell-time-cread`（**新設**、norm_scale 120秒） | — | **0.1** |
| `dwell-time-cread-immersive`（**新設**、没入面専用、norm_scale 240秒） | — | **0.1** |

CREAD は「連続値を対数間隔のしきい値で区切った**30段階の二値分類**＋**復元回帰**」の組み合わせです（`phoenix/xrex/models/loss_recsys.py:111-188`）。実装：

- しきい値は `log_min_threshold = 2.0秒` から `norm_scale` まで**対数等間隔で30個**（`cread_log_thresholds`、`loss_recsys.py:111-126`）。ホーム面は 2秒〜120秒、没入面は 2秒〜240秒。
- 各しきい値について「実測滞在時間がこれを超えたか」をシグモイド交差エントロピーで学習（`loss_recsys.py:155`）。
- さらに復元値（スカラー予測）を **Huber 損失**（`cread_restoration_loss="huber"`、`cread_huber_delta_sec=5.0`）で学習し、重み **0.5**（`cread_restoration_weight`）で合算（`loss_recsys.py:156-170`）。

没入面（`PRODUCT_SURFACE_GALLERY_PAGE` = 全画面動画などのギャラリー面）は専用の損失に分離され、上限が240秒に拡張されました（`xrecsys.py:725-741`）。ホーム面側は逆にギャラリー面を除外しています（`exclude_product_surfaces`）。

重複設定を防ぐバリデーション `validate_continuous_action_losses()` が追加され、「同一アクション・同一面フィルタで重みが正の損失が2つある」設定はエラーになります（`phoenix/xrex/models/recsys_model.py`）。

**メカニズム（入力特徴量側）**

ユーザー履歴に含まれる「過去の各投稿への滞在時間」の表現も作り直されました（`phoenix/xrex/models/recsys_feature_prep.py:885-940`）。

- 旧：滞在時間を **30秒で打ち切って** 0〜1に正規化し、1本のベクトルにスカラー倍するだけ（情報量＝実質1次元）。
- 新：`enable_dwell_bucket_table=True`（`xrecsys.py:301-304`）で、**240秒上限・2秒起点・30段階の対数間隔ノット**上の**区分線形補間**として埋め込みテーブルを引きます。31ノット＋2行の計33行テーブル（ゼロ初期化）。
  - **追加された2行が重要です**：
    1. **ネガティブ反応行**：その投稿に `CLIENT_TWEET_REPORT`（通報）/ `CLIENT_TWEET_NOT_INTERESTED_IN`（興味なし）/ `CLIENT_TWEET_BLOCK_AUTHOR`（ブロック）/ `CLIENT_TWEET_MUTE_AUTHOR`（ミュート）のいずれかがあった場合（`recsys_feature_prep.py:395-405` の `dwell_negative_action_ids()`）
    2. **欠損センチネル行**：滞在時間が既定センチネル値 2.0 秒だった場合（`DWELL_TIME_DEFAULT_SENTINEL_SEC`）

**serving 側の重みは未変更**です。`DwellWeight = 0.05`（10秒超の二値）、`ContDwellTimeWeight = 0.004`（連続秒数）、`NotDwelledWeight = -0.02`（`home-mixer/params/param.rs:363,390-394,422-426`）はいずれも今回変更なし。

**Xユーザー/クリエイターへの影響**

- **「長く読まれる投稿」の評価精度が上がる方向です。** 旧方式（30秒打ち切りの線形スカラー）では、30秒読まれた投稿と5分読まれた投稿が同じ入力値になっていました。新方式では 240秒まで30段階で区別されます。
- **没入面（全画面動画など）の滞在時間が240秒まで学習対象になりました。** 長尺動画を最後まで見せる価値が、学習上きちんと表現されるようになります。
- **ネガティブ反応（通報・興味なし・ブロック・ミュート）の学習が精密になりました。** これまでは「通報されたので滞在0秒」が「データが取れなかったので0秒」と混ざっていました。今後は専用の表現を持つため、**ネガティブ反応を集める投稿の抑制がより効くようになる**と見るのが妥当です。釣りタイトル・不快な引用などの短期的な手法のリスクが上がります。
- ただし **serving の重み（0.004 など）が変わっていないため、ランキングへの影響は「同じ重みでより正確な予測値」という形**です。即日の順位が大きく動く変更ではありません。

`abuse-enforcement-service` に `strip_redundant_suspends()` が追加されました（`abuse-enforcement-service/service-lib/src/lib.rs`）。既に凍結中（`user.suspended == true`）のアカウントに対して**一時凍結**（`SuspendUser { perm: false }`）を適用しようとした場合、その処分だけを取り除きます。**永久凍結**（`perm: true`）が含まれる場合は通常処理されます。一時凍結が唯一の処分だった場合は処理全体をスキップし、`already_suspended_stripped` としてログに記録します。

→ 既に凍結中のアカウントに一時凍結が重ねられて、**既存の（より重い）凍結期間が上書き・短縮されてしまう事故を防ぐ修正**と読めます。凍結中のユーザーにとっては「処分が不当に軽くなることも重くなることもない」方向の整合性改善です。

#### (g) 内部ツールのリファクタ

`visibility-filtering/hydration/sources/exchange.rs`（+528行）と `visibility-filtering/staging/recording.rs`（+2,348行）は、可視性判定の**記録・再生（record/replay）テスト基盤**の作り直しです。本番挙動への影響はありません。`get_safety_labels.rs` のハッシュマップが `FxHashMap` に差し替えられた（高速化）のも同様です。

## 不確実な点（要確認）

1. **動画カルーセルの有効化時期は不明です。** `EnableVideoCarousel` は既定 false で、実際のロールアウトは非公開のフィーチャースイッチ設定で決まります。`param.rs` 冒頭のコメントが `last sync 2026-10-07T16:00:42Z` となっているため、公開値は前日時点のミラーです。
2. **`video_open_score`（動画を開く確率）の算出ロジックは非公開です。** 予測ヘッドの一つであることは分かりますが、何を入力に学習されているかはこのリポジトリからは読めません。「サムネイル訴求力が決定要因」という本レポートの記述は、スコア名と使われ方からの推論です。
3. **`PLACE_TYPES: [4, 3, 7, 9, 1]`（`user_location_client.rs:14`）の具体的な場所粒度が不明です。** 国・州・都市・近隣といった段階と推測されますが、定義は Geoduck 側（非公開）にあります。**ローカル投稿の制限範囲が「市単位」か「国単位」かはコードからは判定できません。** 影響範囲の見積もりが大きく変わる点なので要確認です。
4. **「ローカル投稿」の投稿側UIがいつ・どの地域で提供されるかは不明です。** `narrowcast_place_id` を設定できる投稿手段がユーザーに開放されているかは、このリポジトリからは分かりません。判定ロジックは配線済みですが、該当する投稿が存在しなければ実効影響はゼロです。
5. **コミュニティ除名制限のWebクライアントでの扱いが判然としません。** `params/client_switches.rs` のテストでは Web は `community_viewer_removed_limits == false` ですが、ゴールデンコーパス（`golden_corpus/community.rs`）では `on_client("web", ...)` のロールが制限される期待値になっています。テストフィクスチャが能力フラグを直接立てているためで、**本番のWebが対象かどうかは公開コードから確定できません。**
6. **滞在時間の予測値（`cont_dwell_time`）が serving でどう正規化されて `ContDwellTimeWeight = 0.004` に掛かるかは非公開です。** CREAD への切替で予測値のスケールや分布が変わるため、同じ重み 0.004 でも実効的な寄与が変わる可能性があります。**「重みが変わっていないので影響は小さい」という評価には、この不確実性が残ります。**
7. **MoL の `user_query_heads` / `mol_item_components` の本番値は非公開です。** 公開configの既定は 0（無効）ですが、実際の学習ジョブが別の値を渡している可能性があります。
8. **`FeedRequestContext` / `FeedCursorDirection` という2つの新 enum が proto に追加されましたが（`recsys.proto`、Rust/Python 両方）、使用箇所が公開コードにありません。** 値から、リクエストの文脈（アプリ起動・プルして更新・手動更新・ポーリング・バックグラウンド取得・サインアップ直後など14種）とカーソル方向（初回・上・下・ギャップ）を**モデルの入力特徴量にする準備**と読めます。これが有効化されれば「どういう操作でフィードを開いたか」で推薦内容が変わることになり、行動への影響は大きくなり得ます。**現時点では未使用で、意図も推測です（要確認）。**
9. **`abuse-enforcement-service` の処分フローが実際にどの違反に適用されるかは非公開です。** 重複凍結抑止の修正の実効範囲は判定できません。
