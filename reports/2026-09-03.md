## 非IT精通者向け：今日から意識したい運用方法

- **「何が For You の候補に選ばれるか」の基準が、今日から本番で変わりました。** これまで X は、あなたが**「サッと見て流した投稿」も含む短い滞在（short dwell）**をもとに「あなたに似た投稿」を探しに行っていました。今日からこれが**「じっくり読んだ投稿」＝長い滞在（long dwell）**基準に切り替わりました（下記①）。8/26 に「並べ替え（ランキング）」側で同じ切替が行われており、**今回で候補探し（retrieval）側も追いついて、両方が揃った**形です。
- **読者としての行動指針：「開いてすぐ閉じる」はもう推薦材料になりにくくなりました。** これまでは、タイトルにつられて一瞬だけ開いた投稿でも、次の推薦の手がかりになっていました。今日からは**一定時間きちんと読んだ投稿だけ**が、次に何を見せられるかを強く左右します。逆に言えば、**見たくないジャンルは「開いて即戻る」で済ませれば、以前より引きずられにくくなります**。
- **クリエイター側の行動指針：「開かせる」から「読ませる」へ、比重がさらに移りました。** 釣りタイトル・釣りサムネで一瞬のタップを稼ぐ戦術は、**並べ替え（8/26 に完視聴 0.05→0、滞在 0→0.05）に続いて、候補に選ばれる段階でも効きが落ちます**。**最後まで読ませる構成**（長文スレッドの1枚目に結論、画像は本文と一体で読ませる、動画は冒頭で離脱させない）が、二重に効くようになりました。
- **フィードの「変な混ざり物」が減る可能性があります。** 推薦モデルの計算用メモリが、前の処理の残りかすを消さずに使い回されていたバグが修正されました（下記②）。ごくまれに「なぜこれが出てきたのか分からない投稿」が混ざる原因になり得たもので、**心当たりがなくても直る側の変更**です。今日は特にすることはありません。
- **なりすまし被害の通報が、人の目に届きやすくなりました。** 自動検知ボットが見つけた案件を、**人間の審査待ち行列（XReview）へ直接投函する仕組み**が新設されました（下記④）。なりすましは「bystander_impersonation（第三者からのなりすまし通報）」という専用の種別で送られ、**被害者本人のIDも一緒に添えられます**。あなたのなりすましアカウントを見つけた場合、**通報が「自動検知」としても並行して上がる**ようになったと考えてください（ただしこれはボット由来の自動投函の配線であり、ユーザーからの通報導線が変わったわけではありません）。
- **リンクカードのタイトルに書いた文言で、安全性判定を惑わすのは難しくなりました。** これまで AI（Grok）が投稿を読むとき、リンクカードのタイトルが `Title:` とだけ書かれて渡されており、**投稿本文の一部と紛らわしい**状態でした。今日から `[Card Title]` と明示されます（下記⑤）。**カードのタイトル欄に指示文めいた文字列を入れる小細工は効きにくくなります**。
- **投稿の見え方・隠され方（安全フィルタ）は今日も一切変わっていません。** VF は内部構造の作り直しが入りましたが、**ルールの数・順序・判定条件はすべて同じ**です（下記⑥）。
- **いいね・返信・滞在時間などの配点（ランキング重み）は今日も無変更です。** 8/26 以来 8日連続で据え置きです。投稿の仕方を変える必要はありません。

## 変更サマリ

- **稼働中の実挙動を変える変更は3件。** 最大は **候補生成（retrieval）側のユーザー行動履歴の集約タイプが `DENSE_WITH_SHORT_DWELL` → `DENSE_WITH_LONG_DWELL`** へ切替。8/26 にランキング側で行われた同じ移行が、今回 retrieval 側にも適用され、**両系統が LONG_DWELL で揃った**。
- Phoenix 推論バッチの**候補埋め込みバッファの初期化漏れバグを修正**。使い回しバッファに前リクエストの残留値が残り得た箇所を、毎回ゼロ埋めするよう修正。9/02 の検索クエリ埋め込み複製バグ修正と同系統の是正。
- **リランカー適用前の「バックボーン素点」を全フィード系エンドポイントで常時取得**し、候補に添付する配線が開通（`backbone_scores`）。**ランキングには一切使われず**、ログ／学習用。8/29 の `RerankerHeadTag` に続くオフポリシー学習の下ごしらえ。
- **Scarecrow（ボット対策）に XReview 通報の自動投函機構を新設**（3ファイル・329行）。検知ボットの判定を人手審査キューへ gRPC 直送する `CreateXReviewReportProd` / `Staging` を追加。
- 二塔リトリーバル学習設定で **`qk_norm` False→True、`attn_logit_cap` 80.0→無効化(-1)**。既存の nano 構成と設定を揃えたもの。**学習側の変更のため、反映は再学習・デプロイ後（要確認）**。
- VF（可視性フィルタ）を**静的テーブル方式へ再実装**（`Policies`→`RuleEngine`、動的ディスパッチ撤廃、安全ラベルを `Arc` 共有化）。**判定は完全同値**で、順序固定テスト＋ゴールデンコーパスで担保。純粋な性能改善。
- インフラ：学習チェックポイントの暗号鍵（DEK）を、`_DEK` ファイルが無い場合でも暗号エンベロープのヘッダから復元して引き継げるように拡張。**推薦結果は不変**。

## 変更点ごとの詳細

### ① 候補生成（retrieval）の行動履歴集約が SHORT_DWELL → LONG_DWELL【影響度：大（全ユーザーのFor Youに効く）】

#### メカニズム

フィーチャースイッチのミラーで既定値が書き換わった。`param.rs` の実質的な差分はこの1行のみ。

```rust
// home-mixer/params/param.rs:133-138
param!(
    PhoenixRetrievalAggregationType,
    String,
    "rust_home_mixer_phoenix_retrieval_aggregation_type",
    "DENSE_WITH_LONG_DWELL"          // ← 前回まで "DENSE_WITH_SHORT_DWELL"
);
```

この値は、候補生成用のユーザー行動履歴を集約サービスから取ってくるときの**集約タイプ**として、そのまま渡される。

```rust
// home-mixer/query_hydrators/retrieval_sequence_query_hydrator.rs:44-53
.fetch_aggregated_sequence(
    cluster,
    query.user_id,
    p::UAS_WINDOW_TIME_MS as u32,          // 300_000ms = 直近5分窓 (params/config.rs:34)
    query.params.get(MaxSeqLengthRetrieval), // 1024件 (param.rs:958-963)
    UserActionAggregationType::from_str_name(
        &query.params.get(PhoenixRetrievalAggregationType),
    )
    ...
```

このハイドレータは既定で有効（`EnableRetrievalSequenceHydration` 既定 `true`、`param.rs:801-806`）で、`retrieval_sequence_query_hydrator.rs:32` の `enable()` で参照されている。取得された系列は `phoenix_candidate_pipeline.rs` に渡り、**二塔モデルが「あなたに似た投稿」を数億件の中から絞り込む際の入力**になる。

重要なのは、これが**8/26 に並べ替え側で起きた変更の retrieval 版**である点。並べ替え側（`PhoenixAggregationType`、`param.rs:127-132`）は 8/26 に既に `DENSE_WITH_LONG_DWELL` へ移行済みで、**今回で両系統が揃った**。

#### X ユーザー／クリエイターへの影響

- **読者：** 「タイトルにつられて開いたがすぐ戻った投稿」が、**候補集合を作る段階からも外れる**方向。これまでは並べ替えの入力からは外れていても、候補として拾われる段階では短い滞在が効いていたため、「一度うっかり開いたジャンル」が引きずられやすかった。今日からは**きちんと読んだ投稿だけ**が次の候補探しの手がかりになる。見たくないジャンルは「開いて即戻る」で以前より断ち切りやすい。
- **クリエイター：** 8/26 の重み変更（VQV 0.05→0、Dwell 0→0.05）と方向が完全に一致し、**「滞在時間」重視が候補生成にまで一貫適用された**。釣りタイトル／釣りサムネで一瞬のタップを稼ぐ戦術は、並べ替えでも候補生成でも効かなくなる二重の逆風。逆に**最後まで読ませる／見せる構成**は、二重の追い風になる。
- **効き方の非対称性：** 「長い滞在」の履歴が薄いユーザー（流し見中心のユーザー）は、retrieval に渡る有効な履歴が短くなる可能性がある。その場合、候補が汎用的・人気寄りに寄る方向に働きうる（境界秒数が不明なため断定不可、下記「不確実な点」参照）。

### ② Phoenix 推論バッチの候補埋め込みバッファ初期化漏れバグ修正【影響度：中（全ユーザー、ただし「まれな異常」の是正）】

#### メカニズム

推論サーバは、候補の埋め込みベクトルを詰め込む大きなバッファをリクエスト間で**使い回している**。従来はそのバッファをクリアせず、各候補の値を上書きするだけだった。

```rust
// phoenix/crates/serving/xai-recsys-engine/src/python.rs:2022-2041
.for_each(|(items_chunk, shard_slice)| {
    shard_slice.fill(f16::ZERO);              // ← 新規追加
    shard_slice
        .par_chunks_exact_mut(row_size)
        .zip(items_chunk.par_iter())
        .for_each(|(embedding_row, item)| {
            if let Some(ref input_buffer) = item.input_buffer {
                let src = &input_buffer.candidate_embeddings;
                let copy_len = embedding_row.len().min(src.len());
                if copy_len > 0 {                                   // ← ゼロ長ガード追加
                    embedding_row[..copy_len].copy_from_slice(&src[..copy_len]);
                }
            }
        });
});
```

```rust
// phoenix/crates/serving/xai-recsys-engine/src/python.rs:2047
sq_slice.fill(0.0);      // 検索クエリ埋め込み側にも同じゼロ埋めを追加
```

上書き漏れが起きるのは3つの経路：(a) `item.input_buffer` が `None` の候補（そのスロットは一切書かれない）、(b) `src.len()` が行幅より短い場合の**末尾の余り**、(c) 検索クエリ側では `.take(length_of_input)` により**バッチ末尾の未使用スロット**。いずれも**直前のリクエストの他人の候補ベクトルが残る**ことになる。

#### X ユーザー／クリエイターへの影響

- 実運用では、残留値の入ったスロットは通常マスクされて最終スコアに効かない設計だが、**マスク漏れが1箇所でもあれば「無関係な投稿のベクトル」でスコアが計算される**。体感としては「なぜこれが出てきたのか説明できない投稿がたまに混ざる」形で現れうる。
- **9/02 の検索クエリ埋め込み複製バグ修正（パディングスロットへの混入除去）と同じ系統**で、Phoenix の入力データ衛生を2日連続で締めている。ユーザーがすべき対応はなく、**フィードの一貫性が上がる方向のみ**の修正。
- ただし残留値がどの程度実スコアに漏れていたかは、マスク処理がリポジトリ外の JAX モデル側にあるため**定量的には断定できない**（要確認）。

### ④ Scarecrow に XReview 通報の自動投函機構を新設【影響度：中（なりすまし被害者・検知対象アカウント）】

#### メカニズム

新規3ファイル・329行。ボット対策基盤 Scarecrow から、**人手審査キュー XReview へ gRPC で直接通報を投函する**アクションが追加された。

```scala

  override def actionLevel: ActionLevel = ActionLevel.PROD_AGENT_WORKFLOW_ACTION
  override def downstreams: Set[DownstreamService] = Set(DownstreamServices.XReviewIntake)
  override def description: String =
```

対象は `post`（投稿）と `profile`（プロフィール）の2種のみで、それ以外は例外で弾かれる（`XReviewReportSubmitter.scala:37-44`）。`DownstreamServices.scala:79-81` に `XREVIEW_INTAKE` が登録された。ステージング用の `CreateXReviewReportStaging` は `ActionLevel.NO_ACTION`（実効果なし）で併設されている。

#### X ユーザー／クリエイターへの影響

- **なりすまし被害者にとっては改善方向。** これまで検知ボットの判定は Scarecrow 内部のアクション（ラベル付与・レート制限など）に閉じていたが、**人手審査の列に自動で並ぶ**経路ができた。`victim_user_id` が添えられるため、審査側が「誰のなりすましか」を紐づけられる。
- **`bystander_impersonation`（第三者からのなりすまし通報）という専用種別を使うよう明示**されている点が実務的に重要で、コメント曰く「レーンのタグ付けはこの種別を見ており、汎用の impersonation では効かない」。つまり**なりすまし案件が専用の審査レーンに乗る**。
- `detection_timestamp_ms` を毎回含めることで、intake 側の**コンテンツハッシュ由来の通報ID が毎回ユニークになり**、その後「証拠ロールアップ（evidence rollup）」が適用される。同一アカウントへの複数回検知が**握りつぶされず証拠として積み上がる**設計。検知対象になったアカウント側から見れば、**再犯が累積証拠として扱われる**ことを意味する。
- 注意：これは**ボット由来の自動投函の配線**であり、ユーザーの手動通報の導線が変わったわけではない。また、どの検知ボットがこのアクションを呼ぶかは Botmaker のルール定義側（リポジトリ外）にあり、**実際に稼働しているかは本レポートからは断定できない**（要確認）。

### ⑤ Grok に渡すリンクカードのタイトル表記を明示化【影響度：小（スパム／安全性判定の入力衛生）】

#### メカニズム

安全性・スパム判定用に投稿を LLM へレンダリングする際、リンクカードのタイトルのラベルが変わった。

```python
# grox/core/data_loaders/data_types.py:376  (LegacyCard.to_convo)
body.append(f"\n\n[Card Title] {self.title}")     # ← 従来 f"\n\nTitle: {self.title}"

# grox/core/data_loaders/data_types.py:448  (UnifiedCard.to_convo)
res.append(f"\n\n[Card Title] {self.title}")      # ← 従来 f"\n\nTitle: {self.title}"
```

周囲のカード要素は既に `[Card]` / `[Card Image]` / `[Card Video]` という角括弧記法で統一されており（`data_types.py:383, 391, 454-456`）、**タイトルだけが `Title:` という平文ラベルで浮いていた**。今回それが揃った。`Description:` / `Domain:` / `Url:` は平文のまま。

#### X ユーザー／クリエイターへの影響

- LLM から見て「これは**カードの**タイトルであって投稿本文ではない」ことが明確になる。従来の `Title:` は、投稿本文中に書かれた文字列と区別しにくく、**カードのタイトル欄に判定を誘導する文言を仕込む**余地があった。その余地が狭まる方向。
- 逆に言えば、**正当なリンクカードのタイトルが投稿本文と誤って合成解釈される誤判定も減る**方向。ニュース記事の見出しが投稿者の主張として読まれてしまう類の取り違えが減りうる。
- 影響は小さいが、**8/27 の「採点対象は最終投稿の著者」ヘッダ新設**と同じく、LLM 入力における**帰属の明確化**という一貫した流れの中にある変更。

### ⑥ VF（可視性フィルタ）の静的テーブル化リファクタ【影響度：なし（挙動同値）】

#### メカニズム

ルール評価が `Box<dyn Rule>`（実行時に構築される動的ディスパッチのベクタ）から、**コンパイル時に確定する静的テーブル**へ置き換えられた。トレイト `Rule` 自体が削除されている（`visibility-filtering/rules/mod.rs` から16行削除）。

**挙動同値の担保：** 既存の `wired_rule_order_matches_pre_migration_sequence` テスト（`registry.rs`）が全ルール名を**順序込みの配列リテラルで固定**しており、この差分でも配列の中身は1文字も変わっていない。加えて 8/29 に導入されたゴールデンコーパス91ケース（`golden_corpus.rs`）が判定結果と「決め手になったルール名」の両方をピン留めしている。新規に `wired_rule_names_are_unique_and_nonempty`（`tweet_rules.rs:1155-1163`）が追加され、15本のルールスライス全てを走査して**ルール名の重複と空文字を禁止**するようになった。

#### X ユーザー／クリエイターへの影響

- **表示・非表示の体感変化はゼロ。** ルールの数・順序・判定条件・決め手の記録すべてが不変。
- 意味は**性能**にある。9/02 の「10ファイル→3ファイルの宣言的テーブル化」に続き、今回で**実行時のヒープ確保と動的ディスパッチが消え、ラベルの値コピーも消えた**。可視性判定の Rust 移行が、機能的完成（8/25 の突き合わせハーネス、8/29 のゴールデンコーパス、9/02 の宣言化）を経て**性能最適化フェーズに入った**と読める。
- 削除されたテスト（`fosnr_labels_drop_non_author_non_follower_on_both_surfaces` ほか3件）はいずれもゴールデンコーパスと重複するケースで、**カバレッジの後退ではない**（`every_wired_rule_decides_a_corpus_case` テストが全 wired ルールに最低1ケースを強制している）。

### ⑦ 二塔リトリーバル学習設定：qk_norm 有効化・attn_logit_cap 無効化【影響度：中（要確認：反映は再学習後）】

`qk_norm`（Query-Key 正規化）を有効化し、`attn_logit_cap`（アテンションスコアの上限クリップ、`soft_sign` 方式）を `-1` ＝無効化した。既存の `xrecsys_two_tower_nano` 構成は既に同じ値（`:423-424`）であり、**本番の combined 構成を nano に揃えた**形。コード側のデフォルトは `attn_logit_cap=80.0` / `qk_norm=False` のまま（`:670, 676`）で、config 側の明示指定だけが変わっている。

#### X ユーザー／クリエイターへの影響

- これは**学習側の構成変更**であり、`param.rs` のようなオンライン設定ではない。**現時点の配信モデルは変わらず、次の再学習・デプロイで反映される**（タイミングはリポジトリ外、要確認）。
- 技術的には、アテンションスコアを上限で頭打ちにする代わりに Q/K を正規化して発散を抑える方式への転換。一般に**上限クリップは「突出して強い関連」を潰す**ため、これを外して正規化に置き換えると、**強い関連を強いまま扱える**方向に働く。retrieval への含意としては「あなたの履歴と極めて強く結びついた投稿」が候補として拾われやすくなる可能性があるが、**モデル本体の実装が JAX 側にあり効き方の向きは断定できない**（要確認）。
- ①（retrieval の集約タイプ切替）と同じ日に、retrieval モデルの学習構成も動いている点は注目に値する。**候補生成レイヤーが今まとめて手を入れられている**。
