## 変更点ごとの解析

### 1. 【閾値変更】grox 返信処理のフォロワー閾値 60,000 → 80,000

**メカニズム (コード根拠):**

- `grox/flows/reply_spam/task_filter.py:17` — `TaskSpamFilter.FOLLOWER_COUNT_THRESHOLD_FOR_SPAM_DETECTION = 80000`（旧 60000）
- `grox/flows/reply_spam/task_filter.py:185` — `TaskReplyRankingFilter.FOLLOWER_COUNT_THRESHOLD_FOR_REPLY_RANKING = 80000`（旧 60000）
- 両フィルタは**同じ閾値を逆向きに使う排他条件**になっている:
  - スパム検知は「返信先の著者・スレッド元の著者の**いずれかが閾値超**」なら対象外 (`:79-92`, `reason: "reply_ranking_target"`)。→ **両方が閾値以下のときだけスパム検知が走る**。
  - 返信ランキングは「**両方が閾値以下**」なら対象外 (`:216-224`, `reason: "low_blast_radius"`)。→ **どちらかが閾値超のときだけ返信ランキングが走る**。
- したがって閾値の引き上げは、**フォロワー 60,000〜80,000 の帯にいるアカウントのスレッドを、「返信ランキング」処理から「返信スパム検知」処理へ移す**。
- 別クラス `TaskCoordinatedSpamFilter`（協調スパム／組織的スパム検知）の閾値は **1,000 のまま変更なし** (`:97`)。

**Xユーザー/クリエイターへの影響:**

- **フォロワー6万〜8万人のアカウント**: 自分の投稿の返信欄が、Grokによる品質順の並べ替え対象から外れ、スパム除去の対象に変わる。返信欄の「上位に良い返信が来る」効果は弱まり、代わりに悪質返信が落とされる方向に働く。
- **返信で露出を狙う側**: 返信ランキングは「露出を得るチャンス」でもあるため、**返信先として有利なのは引き続きフォロワー8万人超のアカウント**。6万〜8万人帯への返信は、上位表示のチャンスが消える一方でスパム判定の網に入る（＝低品質な連投・定型返信のリスクが上がる）。
- **段階的ロールアウトの継続**: 8/15 に 15k→30k、8/18 に 30k→40k、8/19 に 40k→60k、今回 60k→80k。**処理対象を絞り込む方向で連日引き上げられている**ため、明日以降さらに上がる可能性が高い（要確認: 最終的な到達値は不明）。

**影響度:** 中（対象アカウント帯は限定的だが、返信欄の挙動が実際に切り替わる）
**影響ユーザー層:** フォロワー6万〜8万人のアカウント／そこに返信して露出を得ていた返信主体のユーザー。

- **ユーザー（ターゲティング精度）**: アプリ内の購入・カート追加・レベル到達・チュートリアル完了・会員登録が個別に予測されるようになるため、**ショッピングアプリ／ゲームアプリの広告が「自分がそのアプリで実際にやりそうな行動」に沿って当たりやすくなる**。

**影響度:** 小（現時点）／大（有効化された場合。ただし影響は広告面に限定）
**影響ユーザー層:** 広告を見るユーザー全般、特にアプリインストール広告・EC広告の受け手／広告主。

### 4. 【新設】遅延フィードバックと即時フィードバックでヘッドを分離する学習機構

**メカニズム (コード根拠):**

- 新しい入力列を2つ受け付ける (`phoenix/xrex/data/recsys/feature_config.py:146-147`): `is_delayed_feedback`、`conversionKeepMask`。
- `is_delayed_feedback` → `sample_source`（ユーザー単位のbool）に変換 (`phoenix/xrex/data/recsys/recsys_batch.py:983-991`)。欠損は `False` 扱い。
- **ヘッド分離の本体** (`recsys_model.py:3152-3159`):
  ```python
  if self.config.split_head_training_by_source and delayed_mask is not None:
      conv_head_split_mask = jnp.zeros(num_actions).at[jnp.array(SOURCE_SPLIT_CONVERSION_HEAD_INDICES)].set(1.0)
      eng_head_mask = 1.0 - conv_head_split_mask
      is_delayed = delayed_mask[:, :, None]
      loss_mask = loss_mask * (1 - is_delayed * eng_head_mask)      # 遅延サンプル → エンゲージメント系ヘッドを学習しない
      loss_mask = loss_mask * (1 - (1 - is_delayed) * conv_head_split_mask)  # 即時サンプル → 変換系ヘッドを学習しない
  ```
  → **既定 `False`** (`recsys_model.py:560`)。有効時は「変換ラベルは後から確定する遅延ストリームからのみ学習し、いいね・返信などのエンゲージメントは即時ストリームからのみ学習する」という分業になる。連続値ヘッド（滞在時間など）も遅延サンプルを除外 (`:3249-3253`)。
- **安全装置**: `split_head_training_by_source=True` なのに `sample_source` が無ければ `assert` で停止 (`recsys_model.py:2906-2911`、コメント「training unsplit silently would defeat the flag」)。メトリクス側も `condition_conversion_on_click` の同時有効を要求 (`:1371-1374`)。
- **`conversionKeepMask`**: 候補単位のboolで、`False` の候補を**損失計算そのものから除外** (`recsys_model.py:3057-3061`):
  ```python
  keep = cast_jax(conversion_keep_mask)
  pad_len = target_padding_mask.shape[1] - keep.shape[1]
  target_padding_mask = target_padding_mask & jnp.pad(keep, ((0, 0), (0, pad_len)))
  ```
  欠損行は `True`（残す）にフォールバック (`recsys_batch.py:412-419`)、パディングも `True` (`parquet_recsys.py:770-774`)。シーケンスパッキングとの併用は**未対応で assert 停止** (`sequence_packing.py:169-172`)。
- 評価メトリクスも `fresh` / `delayed_clicked` / `delayed_non_clicked` にスライス (`recsys_model.py:1371-1381`)、`metric_mask_keys` で出力メトリクスを絞り込み可能 (`:1398-1405`)。
- Kafka 側で必須列の一部を除外できるスイッチ `exclude_required_columns` を追加 (`phoenix/xrex/data/streaming/kafkaloader.py:870-875`, `configs/data_feeds.py:126,152`)。欠損列の警告も必須列に限定 (`kafkaloader.py:762-763`)。

**Xユーザー/クリエイターへの影響:**

- **間接的**。広告変換の予測精度が上がる方向の学習インフラであり、**オーガニックのタイムライン順位には触れていない**。
- 効いてくる筋道は「変換ラベルの汚染が減る → 変換予測が正確になる → 広告のオークションでの実効価値が正しく測られる → 広告の見え方が変わる」という長い経路。**既定オフのため今日時点の影響はゼロ**。

**影響度:** 小（学習インフラ。既定オフ、かつ広告ヘッド限定）
**影響ユーザー層:** 直接影響なし（広告主向けの計測精度改善）。

### 5. 【新設】検索クエリの「打ち直し」をネガティブフィードバック信号に追加

- `CLIENT_TWEET_SEARCH_QUERY_REFORMULATED = 104` は proto 上は以前から存在した enum（`recsys.proto:344`）で、**今回はじめて学習ラベルとして配線された**。

**Xユーザー/クリエイターへの影響:**

- **検索面の順位に効く**。「検索結果としてこの投稿を見せたが、ユーザーは満足せず検索語を打ち直した」という行動が、**その投稿にとってのマイナス点**として学習される。
- **クリエイター**: 検索流入を狙って**検索語とズレたキーワードを詰め込む／釣りタイトルで検索結果に割り込む**手法は、従来より明確に不利になる。ユーザーが「これじゃない」と思って検索し直した時点で減点が入るため、**「クリックはされるが期待外れ」なコンテンツが最も損をする**構造。
- **ユーザー**: 検索の体感精度が上がる方向。検索し直しを誘発する結果は、時間とともに検索結果から後退する。
- **要確認**: このラベルは検索面（`search` エンゲージメント群）で有効化されているが、For You など他面のモデルで同ヘッドが使われるかはこのコミットからは判断できない。

**影響度:** 中（検索面に限定されるが、方向性は明確で恒常的に効く）
**影響ユーザー層:** 検索経由の露出に依存するクリエイター／検索を多用するユーザー。

### 6. 【変更】EVERGREEN リトリーバル候補プールを「最長5年の動画」→「4〜14日の動画」へ差し替え

**メカニズム (コード根拠):**

- `phoenix/xrex/data/retrieval_dataset.py:255-259`:

  EVERGREEN = (

- `1825day = 5年`。同じ enum の他の動画系プールは `IMMERSIVE2Day`（2日, `:242`）、`IMMERSIVE4Day`（4日, `:272`）であり、今回の `video_4to14day` は**「4日〜14日」という、これまで空いていた鮮度帯を埋める**位置づけ。
- 一方、配信側インデックス生成 `phoenix-rankall/src/config/mod.rs:153,184,239-241` では `evergreen_video` の窓は **`24 * 365 * 5`（5年）のまま**であり、`evergreen_video_1825day` というインデックス名も残っている。**つまり本番のインデックス生成側は5年窓を維持したまま、xrex 側の EVERGREEN スナップショット参照だけが 4〜14日に切り替わった**。

**Xユーザー/クリエイターへの影響:**

- **反映範囲が要確認**。xrex 側の `RetrievalDataset` は二塔リトリーバルモデルが参照する候補インデックスのスナップショットを指しており、**この経路が本番の動画候補源に直結するのか、学習・オフライン評価用の切替なのかは、このコミットの範囲では確定できない（要確認）**。上記のとおり、配信側インデックス生成は5年窓のままであることが確認できるため、**少なくとも「5年分の evergreen インデックス自体が消えた」わけではない**。
- **反映された場合の方向性は明確**: 「エバーグリーン（＝古くても価値が落ちない）」という名前でありながら、実質は **「4〜14日の準新作」プール**になる。**何年も前の動画が突然掘り起こされて伸びる経路が塞がる**一方、**投稿から4日〜2週間の動画に「二度目の露出機会」が生まれる**。
- **動画クリエイターの行動指針**: 過去資産のロングテール再バズを期待する設計から、**「直近2週間の新作を継続的に出し、投稿後1〜2週間の再浮上枠を取りに行く」設計**へ寄せるのが合理的。投稿直後に伸びなかった動画も、4日目以降にもう一度チャンスが来る構造になりうる。

**影響度:** 中（要確認事項付き。反映されれば動画面の候補構成が大きく変わる）
**影響ユーザー層:** 動画クリエイター全般、特に過去動画の再浮上に依存していたアカウント／没入型動画フィードの閲覧者。

### 7. 【配線】SlateContext を推論レスポンス proto に追加（8/21 の `UseServedSlateContext` の受け皿）
