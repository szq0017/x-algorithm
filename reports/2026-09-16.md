## 変更点ごとの詳細

### 1. クリック後滞在時間ヘッドの学習開始（影響度：**大**・ただし発現は将来）

**メカニズム（コード根拠）**

- 本番 For You 学習構成の共通ベース `_home_direct_packed_base()` に `"click_dwell_loss_weight": 1.0` が追加（`phoenix/xrex/configs/xrecsys.py:262`）。このベースは `home_direct_packed`（H100）/ `home_direct_packed_gb300` / `home_direct_packed_nano` の**全本番系構成が継承**（同 `:404, 411, 419`）。
- 対応する損失設定が新規追加（同 `:685-692`）：

  ```python
  ContinuousActionLossConfig(
      action_index=recsys_pb2.ContinuousActionName.CLICK_DWELL_TIME,  # = 2
      metric_name="click-dwell-binary",
      loss_weight=mparams.get("click_dwell_loss_weight", 0.0),
      loss_type="binary",
      binary_threshold=10.0,
      norm_config=NormConfig(norm_scale=60.0),
  )
  ```

- `loss_type="binary"` は今回新設された損失種別（`recsys_model.py:221, 225, 248-262`）。実装は「生の滞在秒数が閾値を超えたか」を0/1に変換してシグモイド交差エントロピーを取るもの（`loss_recsys.py:160-185`）。**回帰（何秒か）ではなく分類（10秒超えたか）**である点が設計上の要点です。
- 履歴側の入力特徴量も有効化：`enable_click_dwell_time=True`（`xrecsys.py:293`）、実装は連続値スロット2を0〜60秒にクリップし `log1p` 正規化して埋め込みに加算（`recsys_feature_prep.py:847-855`）。
- 評価指標として `metric_xauc`（ペアワイズの順序一致率）を新設し、`*-xauc-clicked` として記録（`recsys_model.py:352-377, 3540-3547`）。**「滞在時間の長短を正しく順序付けられているか」を直接測る指標**です。

**Xユーザー／クリエイターへの影響**

- **現時点では影響ゼロ。** 配信側の重み `ContClickDwellTimeWeight` は 0.0（`home-mixer/params/param.rs:420-424`）で、予測値はランキングスコアに加算されていません。
- **重みが引き上げられた時点で影響が発現。** その場合、「クリック率は高いが滞在が短い」投稿（釣りタイトル、誤誘導サムネ、中身の薄い外部リンク）が相対的に不利になり、「クリック後に読み込まれる」投稿が有利になります。
- 閾値が**10秒**という短さである点は重要です。長文記事を要求しているのではなく、**「開いて即座に閉じられていないか」を見ている**水準です。
- なお、同じくクリック滞在に関する既存の抑制機構 `EnableClickDwellLowFavRatePenalty`（クリック滞在は長いがいいね率が低い投稿への減点）は **`false` のまま据え置き**です（`param.rs:426-430`）。

### 2. 広告の購入金額予測：学習ロジックの実装（影響度：**中**・未有効化）

**メカニズム（コード根拠）**

- 学習対象は「広告主の直近28日平均購入額に対する、この購入の金額比率」。`purchase_value_loss_compute()` が Huber 損失で回帰します（`loss_recsys.py:115-152`）。デルタ既定 1.0（`recsys_model.py:570`）。
- 学習サンプルに使う条件が厳格で、**「ラベル有効 かつ パディングでない かつ 負例サンプルでない かつ 遅延フィードバックでない かつ クリックがある かつ 購入がある かつ 学習対象候補」の全てを満たす行のみ**（`loss_recsys.py:95-113`）。つまり**実際に購入に至った広告インプレッションだけ**で学習します。
- データ読み込み側に `valueLabelValidSeq` / `valueBaselineMeanUsdSeq` の2列を追加（`phoenix/xrex/data/recsys/feature_config.py:147-148`、`recsys_batch.py:316-317, 334-355`）。負例サンプリング後も列が保持されるよう配線済み（同 `:1321, 1554`）。
- 出力ヘッドは softplus（非負）で活性化（`recsys_model.py:2306-2309`）。
- 有効化条件のガードが実装され、スロット5と購入コンバージョンヘッド(200)の両方が存在しない限り起動時に例外（`recsys_model.py:575-593`）。

**Xユーザー／広告主への影響**

- **既定重み 0.0 のため、現時点の広告の並び順は変わりません**（`recsys_model.py:569`、`xrecsys.py:650`）。
- 有効化された場合：広告ランキングが「クリック/コンバージョン確率」から「予測売上」寄りに移り、**高単価商材の広告が表示されやすく、低単価・釣り型の広告が相対的に不利**になります。一般ユーザーから見ると**表示される広告の客単価が上がる**方向です。**広告の本数が増える変更ではありません。**
- 昨日（9/15）比の進捗：proto の枠予約のみ → **損失関数・データ経路・検証の実装完了**。残るはフラグを立てるだけの状態に近づきました。

### 4. 返信スパム対策の分界点変更と専用モデル投入（影響度：**中**・実挙動変更）

**メカニズム（コード根拠）**

- 新定数（`grox/flows/reply_spam/constants.py:6-8`）：

  ```python
  GEMMA_REPLY_SPAM = "oai-gemma4-26b-reply-spam"
  GEMMA_REPLY_SPAM_MIN_FOLLOWERS = 150_000
  GROK_GEMMA_FOLLOWER_SPLIT = 180_000
  ```

- 2つのフィルタが**同じ分界点を共有する相補的な関係**であることが明示されました。
  - `TaskSpamFilter`（スパム判定系統）：親投稿・ルート投稿の**両方が分界点以下**のときのみ処理（`task_filter.py:18, 78-92`）。
  - `TaskReplyRankingFilter`（返信ランキング系統）：**どちらかが分界点超え**のときのみ処理（同 `:186, 214-227`）。
  - 分界点が **150,000 → 180,000**。したがって**15万〜18万フォロワー帯が、ランキング系統からスパム判定系統へ移動**しました。
- スパム判定系統の中でモデルが2分割（`classifier_simple_reply_scorer.py:35-45`）：

  ```python
  thread_followers = max(... for p in (post.ancestors[0], post.ancestors[-1]) ...)
  return (self.oai_gemma4_reply_spam
          if thread_followers > GEMMA_REPLY_SPAM_MIN_FOLLOWERS   # 150,000
          else self.oai_gemma4)
  ```

  スパム判定系統は上限18万なので、**専用モデルが担当するのは実質 15万〜18万の帯域ちょうど**です。
- スパム判定の結果は `score == 0.0` をスパムとして記録・計上します（`task_spam_detection.py:41-53`）。

**Xユーザー／クリエイターへの影響**

- **15万〜18万フォロワーのアカウントの返信欄**：処理が「良い返信を上に並べる」から「スパム返信を検出する」に切り替わりました。**取り締まりの緩和ではなく、方式の切り替え**です（9/15の連携スパム閾値引き上げ＝対象範囲縮小とは性質が異なります）。
- 該当帯域の投稿主から見ると、**返信欄の並び方の体感が変わる**可能性があります（良質返信の押し上げが効かなくなる一方、スパム返信は除去される）。
- **返信でリーチを稼ぐ運用をしている側**：この帯域のアカウントの返信欄では「良い返信として押し上げられる」経路が弱まります。18万超の大型アカウントでは従来通りランキング系統が動きます。
- 専用モデルの投入は、**この帯域に固有のスパム様式（有名アカウント狙いの定型スパム等）に特化して精度を上げる狙い**と読めますが、**具体的な閾値や学習内容はコードからは分かりません（要確認）**。

### 5. Grokプロンプトにおける引用ポストの著者明示（影響度：**小〜中**・実挙動変更）

**メカニズム（コード根拠）**

- `grox/core/lm/post.py:104-114`。従来は `"This Post quotes Post {id}"` とID だけを提示していたのに対し、

- `PostRenderer` は `grox/core/lm/thread.py:88, 99` 経由で **PTOS（安全性ポリシー判定, `ptos/classifier.py:133, 223, 425, 547, 744`）・返信スパム各種・UPA 系統**に広く使われます。**Grok/Gemma による安全性・スパム判定全般に波及**します。

**Xユーザー／クリエイターへの影響**

- **引用ポストで他者の発言を批判・ファクトチェックするタイプの投稿**が、「引用した中身を自分が言った」と誤認されるリスクが下がる方向です。安全性ラベルの誤付与が減る期待があります。
- 逆に**自分の過去投稿を自己引用して繰り返し露出させる運用**は、判定側から「自己引用」と識別可能になりました。現時点でそれに対する減点ロジックは見当たりませんが、**識別可能になったこと自体が前提条件の整備**です。
- **精度がどれだけ改善するかはコードからは測れません（要確認）。**

### 6. 配信側の性別特徴量エンコード変更（影響度：**小**・要確認）

**メカニズム（コード根拠）**

- `phoenix/crates/common/xai-recsys/src/util.rs:731`。変更前は独自マッピング：

  ```rust

      Ok(pb::Gender::Male) => 2, Ok(pb::Gender::Female) => 1, _ => 0,

  ```

  変更後は proto 列挙値をそのまま使用：

  ```rust

  ```

- proto 定義は `MALE = 1; FEMALE = 2; UNKNOWN = 3;`（`phoenix/crates/serving/xai-recsys-proto/proto/recsys.proto:1097-1102`）。したがって **男性 2→1、女性 1→2 と入れ替わり、不明 0→3** に変わります。新設テストの名称も意図を示しています（`util.rs:2356-2368` `user_gender_is_raw_proto_enum`）。
- 学習側は性別を**カーディナリティ3**で埋め込み（`recsys_feature_prep.py:496-500`）、`_embed_categorical` は `jnp.clip(values, 0, cardinality-1)` を行う（同 `:329`）ため、**UNKNOWN(3) は 2 にクリップされ、FEMALE と同じ埋め込み枠に落ちます**。
- `record_fill("gender", ...)` の判定が `!= 0` のままのため、**従来「不明＝未充填」と数えていたものが、今後は「充填済み」と数えられます**（`util.rs:732`）。監視メトリクスの見え方が変わる点に注意。

**Xユーザーへの影響**

- 学習パイプラインが raw 列挙値でログしているのであれば、これは**学習/配信の不整合（性別が反転して入力されていた）の修正**であり、性別を利用した出し分けの精度が改善します。
- **ただし、どちらの向きが正だったかはこのリポジトリのコードだけでは断定できません（要確認）。** 学習データ生成側のエンコードが公開範囲に含まれていないためです。
- いずれにせよ **UNKNOWN が FEMALE と同じ枠に丸められる**点は設計上の粗さであり、意図的かどうかは不明です（要確認）。
- **一般ユーザーが今日体感できる変化ではありません。**
