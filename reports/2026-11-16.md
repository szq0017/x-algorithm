## 非IT精通者向け：今日の差分を踏まえた運用方法のまとめ

今回は**小さな差分だが、1つは「本番の既定値が実際に切り替わった」変更**です。行動指針は以下のとおりです。

- **同じ話題の連投は、これまで以上に効率が落ちる方向に進みつつある。**
  おすすめ（For You）タブで「直前に自分が見た投稿」の情報が、並べ替えサービスへ**本番既定で送られるようになりました**（昨日時点ではOFF）。これは「似た投稿が連続しないようにする仕組み」の配管部分です。並べ替え側の最終スイッチは公開コードの既定では依然OFFですが（要確認）、**準備は完了した状態**と読めます。
  → 1アカウントで同系統の投稿を短時間に何本も出す運用は、将来さらに不利になる前提で組み替えるのが安全です。話題・切り口を散らすほうが有利になります。

- **その「見た投稿の記憶」は、200件分→50件分に縮まった。**
  効き方が「直近の数ページ分」に限定されたため、**10分以上あけて投稿する／間隔を置いて読まれる**ケースでは重複ペナルティは効きません。連投するなら時間を空ける、というのが素直な対処です。

- **画像を5枚以上貼って「1枚の大きな絵を分割して見せる」投稿は、全体像で審査される準備が始まった。**
  5枚以上の画像投稿について、全画像を**横に並べて1枚に合成した画像**を安全性審査AIに渡す仕組みが追加されました（既定OFF）。対象になるのは**縦長の画像を5枚以上貼った投稿**（＝横長の絵を縦に切り分けた形）にほぼ限られ、正方形や横長の画像を5枚並べた通常の多画像投稿は対象外です。
  → 「1枚ずつ見れば問題ないが、並べると問題のある絵になる」形での審査回避は、有効化後は通らなくなります。逆に、**正当な分割画像（長い図解、マンガのコマ、パノラマ）は意図が正しく伝わりやすくなる**ため、こうした表現にはプラスに働きます。

- **この画像合成は「いいね64件以上」の条件が付いていない。**
  従来の投稿スクリーンショット審査は高エンゲージ投稿のみが対象でしたが、今回の合成ビューは**エンゲージメントに関係なく対象**です。小規模アカウントの多画像投稿も同じ扱いになります。

- **今日は、スコア重み・Thunder・OON係数・著者多様性・retrieval Top-K・広告挿入密度・grox閾値のいずれも変更なし。** 既存の運用方針を変える必要はありません。

5. 合成前に**X上の表示順**へメディアを並べ替える処理を追加（外部 `StratoMediaEntities` 依存）。並べ替えは `post.media` 自体を書き換えるため、grox配下の他フロー（埋め込み生成・返信スパム判定）にも波及。
6. 多数メディア安全性フロー（`safety_ptos_many_media`）で、合成ビューは**先頭チャンクのみ**に添付されるよう調整。

### 2【中】grox：5枚以上の画像投稿を「横一列に合成した1枚」として安全性AIに見せる仕組み（既定OFF）

**メカニズム**

- 設定：`grox/config/config.py:116` — `enable_screenshot_v2: bool = False` を **`enable_combined_view: bool = False`** に置換（既定OFFは維持）。
- データ型：`grox/core/data_loaders/data_types.py:724` に `Post.combined_view: Image | None`、`grox/core/data_loaders/media_processor.py:147` でワーカープロセスから親へ受け渡し。
- 生成判定：`grox/core/data_loaders/media_loader.py:188-195` — `enable_combined_view` が真なら、`post_media_is_screenshot_target()`（`:103-114`、**画像2枚以上かつ動画0**）を満たす投稿と、同条件を満たす**引用元投稿**の両方に対して生成を試行。
  - **重要**：従来のスクリーンショット経路（`:180-187`）は `is_high_fav`（`deluxe_fav_count_threshold = 64`、`config.py:120`）と `not post.ancestors` でゲートされているが、**combined_view にはこの2つのゲートが無い**。いいね数・スレッド有無を問わず対象。
- 実生成：`media_loader.py:197-233` `hydrate_combined_view()` — ①表示順ソートに成功し、②画像が **`_COMBINED_VIEW_MIN_IMAGES = 5` 枚以上**（`:44`）、③**全メディアが画像**（`len(images) == len(post.media)`）のときのみ `side_by_side()` を呼ぶ。生成物は `deluxe_image_tile_size = 600` で `resize_tile`。
- 合成関数：`grox/libs/video_tools/image.py:152-164` `side_by_side()` — 全画像を**最大の高さに揃えて横連結**し、合計アスペクト比が **`_COMBINED_VIEW_MAX_ASPECT = 3`** を超えたら `None`（生成中止）。
  - 解像度の帰結：`image.py:23-35` `_resize_and_pad()` は長辺を600pxに縮小するため、アスペクト3:1なら **600×200**。画像5枚なら1枚あたり横**約120px**。つまり**細部の判定用ではなく「並べたときの全体像」を見るための画像**。
- 表示順ソート：`media_loader.py:235-249` `_sort_in_display_order()` — 外部 `StratoMediaEntities.fetch(post_id)` で取得した `mediaKey.mediaId` の順に `post.media` を**破壊的に並べ替える**。1枚でも対応が取れなければ警告ログを出して並べ替えを放棄し、`outcome="unordered"` として合成も行わない。
- LMへの提示：`grox/core/lm/post.py:139-144` — 既存の screenshot より**前**に、`"Sometimes user slice one picture across the post's images. So all of the post's images are attached side by side as one view, in the order X shows them, for reference"` という説明文とともに添付。
- 多数メディアフロー連携：`grox/flows/ptos/task_safety_ptos_many_media.py:101-111` — `MANY_MEDIA_CHUNK_SIZE = 4`（`grox/flows/ptos/constants.py:46`）で4枚ずつに分割する際、**2番目以降のチャンクでは `combined_view` を `None`**（投稿側・引用元側とも）。合成ビューは**先頭チャンクで1回だけ**モデルに渡る。
- 削除：`grox/libs/html_render/tweet_render_for_grox.py:153-195` `take_screenshot_v2()` と定数 `_IMAGES_LOADED` を削除。`media_loader.py:117` `hydrate_screenshot()` の `v2` 引数も削除され、v1（従来の撮影経路）一本化。

**Xユーザー/クリエイターへの影響**

- **審査回避の穴が1つ塞がる方向**。4枚ずつに分割して審査する `safety_ptos_many_media` フロー（昨日新設）は、**チャンク境界をまたいで初めて成立する表現**を見落とす。例えば「5枚の画像を並べると1枚の問題のある絵になる」投稿は、4枚＋1枚に割って個別に見ると各チャンクが無害に見える。合成ビューはこの死角を埋める。有効化後は**画像分割による審査すり抜けは通りにくくなる**。
- **正当な分割表現にはプラス**。長い図解・インフォグラフィック、マンガのコマ割り、パノラマ写真、連続写真などは、「1枚の大きな絵の断片」として正しく解釈される可能性が上がる。従来は断片単体で評価され、文脈を失っていた。
- **対象範囲が広い**：いいね64件のゲートが無いため、**フォロワーが少ないアカウントの多画像投稿も等しく対象**。従来のスクリーンショット経路（高エンゲージ限定）とは非対称。
- **動画が1本でも混ざると生成されない**（`post_media_is_screenshot_target` が動画0を要求し、さらに全メディアが画像であることも要求）。画像＋動画の混在投稿は対象外。
- **生成条件は実質「縦長の画像を5枚以上」にほぼ限定される**：アスペクト比3の上限は、高さを揃えて横に並べた合計幅で判定される（`image.py:154-157`）。画像5枚で合計3以内に収めるには、1枚あたり平均アスペクト比**0.6以下**（＝5:3より縦長）が必要。
  - 1:1（正方形）5枚 → 合計5:1で上限超過＝**生成されない**
  - 16:9（横長）5枚 → 合計約8.9:1で大幅超過＝**生成されない**
  - 9:16（縦長）5枚 → 合計約2.8:1で**通る**
  つまりこのゲートは、**横長の1枚絵を縦方向に5分割した投稿**がちょうど通る条件になっている。コード内のプロンプト文（`post.py:141`「ユーザーが1枚の絵を投稿の画像にまたがって切り分けていることがある」）と合わせて、**「分割された1枚絵」の検出に照準を合わせた設計**と読める。逆に、**正方形・横長の画像を5枚以上並べる通常の多画像投稿は対象外**であり、無関係な投稿に合成コストをかけない設計になっている。
- **副作用（挙動不変ではない点）**：`_sort_in_display_order()` は `post.media` を書き換えるため、`enable_combined_view` を有効化すると、**合成が実際に行われなかった場合（アスペクト超過・4枚以下など）でも、メディアの並び順だけがX表示順に変わる**。メディアハイドレーションは `grox/core/data_loaders/media_processor.py:38` → `grox/core/tasks/task_media.py:12` の共通段で、安全性PTOS系・マルチモーダル埋め込み系（`plan_post_embedding_v5/v82/v8_search`）・返信スパム系の**全フローが共有**する。したがって埋め込みベクトルに入る画像の順序も変わり得る。従来の読み込み順がX表示順と一致していたか否かは本リポジトリでは確認できない（**要確認**）。
- **スクリーンショットv2の廃止**：x.com の投稿ページをヘッドレスブラウザで撮影して「ユーザーが見る見た目」を得る方式は放棄され、サーバ側合成に置き換わった。v2は既定OFFだったため**ユーザー影響はない**が、方向性として「レンダリング済みの画面を撮る」から「素材を組み立てる」へ転換したと読める。レンダリング待ち（画像ロード待ち10秒＋可視待ち15秒）のコストと不安定さを避ける意図と推測される（要確認）。
