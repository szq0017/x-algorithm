## 非IT精通者向け：今日から意識したい運用方法

- **返信は「投げ直し」が効かなくなった。最初の1本を丁寧に。** 返信につく品質スコアは、下がるか据え置きにしかならない仕様が今日さらに強化されました。あとから中身を良くしても、返信の評価は上がりません。中身の薄い連投より、1本を練って投げるほうが有利です。
- **裏側の一時障害で「採点そのものが付かない」ケースが出ます。** 今日の変更で、既存スコアの読み出しに失敗すると書き込み自体を中止する挙動になりました（従来は上書きして続行）。返信の伸びがたまたま日によってブレることがあり得ますが、こちらでできる対策はありません。時間をおいて別の返信を投げるのが現実的です。
- **リンクカード（プレビュー画像・見出し）の細工は、大アカウントでも罰則対象になりました。** 「本文と違う見出しを出すカード」「差し替えたリンク」などのカード操作が、これまでは影響力の大きいアカウントは免除されていましたが、今日から一律でスパム扱いされます。フォロワー数を盾にできなくなったと考えてください。
- **際どい内容の投稿が多いタイムラインに、広告が入る余地が新設されました（まだ既定オフ）。** 現時点で見え方は変わりませんが、将来オンになると「これまで広告ゼロだった刺激の強いフィード」にも広告が挿さるようになります。クリエイター側の収益機会が増える方向の準備です。
- **ブラジル関連：誤って規制対象にされていた14アカウントが解除されました。** ブラジル2026年選挙の候補者フィルタから、本人のものでないと判断された10件と、生存が確認できなかった等の4件が外れています。心当たりがある場合はリーチが戻っている可能性があります。
- **（日本語ユーザー向け豆知識）ミュートキーワードは「単語まるごと一致」です。** 「京都」をミュートしても「東京都」を含む投稿は消えません（今日この挙動がテストで明文化されました）。狙った投稿が消えないときは、ミュート語の切り方を見直してください。
- **X本体の使い方として変えるべきことは、上記以外にありません。** 今日の変更の大半はサーバー内部の効率化と、まだ有効化されていない準備コードです。

## 変更サマリ

- ランキング重みの数値変更はゼロ。実挙動の変化は「返信スコアの書き込み経路」と「スパム判定の免除範囲」に集中している。
- grox の返信ランキング書き込みが **フェイルオープン → フェイルクローズ** に転換。既存スコア読み出しの例外を握りつぶすのをやめ、失敗時は書き込みを丸ごと中止するようになった。あわせてラチェット条件が `>` から `>=` に厳格化。

- ブラジル2026選挙フィルタが **2,328 → 2,315 アカウント**（14件除外解除／1件追加）。
- 可視性フィルタ(VF)に **L2キャッシュ・ウォーマー（新規203行）**、home-mixer に **Stratoヘッダ由来の `is_polling` 判定**を追加。いずれもインフラ寄り。
- Phoenix は gRPC トレーラ取りこぼしの修正、モデル重み読み込みのシャード順シャッフル、ストリーミング復元など純インフラ。動画6秒視聴アクション名を proto に宣言（未配線）。

### 1. 返信ランキングスコア書き込みのフェイルクローズ化＋ラチェット厳格化【影響度：大】

**メカニズム**

`grox/flows/reply_spam/task_write.py:113` — 既存スコアの取得を包んでいた `try/except` が削除された。

```python
# 変更前
existing = None
try:
    existing = await ReplyRankingScoreStratoLoader.fetch_reply_ranking_score(post.id)
except Exception:
    logger.warning(f"Failed to fetch existing ... proceeding with write")

# 変更後 (task_write.py:113)
existing = await ReplyRankingScoreStratoLoader.fetch_reply_ranking_score(post.id)
```

例外は呼び出し元 `TaskWriteReplyRankingManhattan.write` の `except Exception:`（`task_write.py:89` 付近）に伝播し、`task.write_reply_ranking_manhattan.failed.count` を加算してそのまま終了する。**Strato の読み出しが一時的にでも失敗すると、その返信にはスコアが1件も書かれない**（Manhattan にも Kafka にも書かれない）。従来は「読めなかったら上書きして続行」だった。

さらにラチェット条件が厳格化された（`task_write.py:119`）:

```python
if existing is not None and existing.score is not None and score >= existing.score:
    # skip: reason="not_lower_than_existing"
```

前回（8/27）は `score > existing.score` でスキップ＝「新スコアが既存より高いときだけ書かない」。今日から `>=` になり、**同点も書き込みスキップ**。スコアは下がる方向にしか動かず、同点なら reasoning テキストの更新すら行われない。

書き込み順序も入れ替わった（`task_write.py:132` Kafka v2 → `:139` Manhattan、従来は逆）。Kafka が先に発火するため、Manhattan 書き込みが失敗しても下流の返信ランキング系はスコアを受け取る。一方、ラチェット判定の読み出し元は Manhattan 側なので、片落ちすると次回実行で再び書き込みが走り得る。

なお `score == 0.0` のときのスパムラベル付与（`task_write.py:130` `_apply_reply_spam_label`）はスキップ判定を通過した場合のみ実行されるため、読み出し失敗時はラベル付与も行われない。

**X ユーザー／クリエイターへの影響**

- 返信の品質スコアは「投げた瞬間の初回採点が生涯の上限」という8/27からの性質がさらに強まった。同点再採点でも書き換わらないため、実質的に**初回採点で確定**に近い。
- Strato の読み出し障害中に投げられた返信は、スコア未設定のまま扱われる。返信ランキングでの並び順が日によってブレる原因になり得るが、投稿者側に制御手段はない。
- 同時に、スコア0（＝スパム相当）の返信へのラベル付与も障害時には発火しない。**取り締まりが緩む方向のフェイルモード**でもある。

### 2. `MultiRiskAdsBlender` 新設 — 高リスク許容広告を「Mediumリスク投稿」の間に挿す【影響度：中〜大（既定オフ）】

**メカニズム**

新規ファイル `home-mixer/ads/multi_risk_blender.rs`（332行）。`home-mixer/selectors/blender_selector.rs:56` で `"multi_risk"` として選択可能になった。既定値は `param.rs:902-906` の `AdsBlenderType = "partition_organic_low_risk"` のままで、`blender_selector.rs:54` に明示アームが追加されただけ（挙動不変）。

現行の `PartitionOrganicAdsBlender` は `has_avoid()`（＝Medium または High リスク）に該当する投稿を一律に「広告の隣に置けない投稿」として除外する。`MultiRiskAdsBlender` はこれを3段階に分割する（`multi_risk_blender.rs:60-71`）:

- **safe**（Medium でも High でもない）→ 通常広告の上下に配置
- **medium** → **BSR-High 広告（高リスク隣接を許容した広告主）専用**の枠として利用（`multi_risk_blender.rs:101`）
- **high** → どの広告の隣にも置かない（filler へ回す）

予算計算（`multi_risk_blender.rs:51-55`）:

```rust
let safe_budget = num_ads.min(spacing_cap).min(max_safe_slots);
let any_bsr_high = ads.iter().any(is_bsr_high_ad);
if safe_budget == 0 && !(any_bsr_high && max_medium_slots > 0 && spacing_cap > 0) {
    return posts_to_feed_items(scored_posts);   // 広告ゼロ
}
```

安全な投稿が足りず `safe_budget == 0` でも、BSR-High 広告と Medium ペアがあれば広告挿入が続行される。全体の上限は `spacing_cap`（`multi_risk_blender.rs:97`）なので、**Medium 枠のぶんだけ従来より広告本数が増え得る**。

新規判定関数は `home-mixer/ads/util.rs:31-38`（`is_high_risk` / `is_medium_risk`）と `:89-95`（`is_bsr_high_ad`）。

テストが挙動差を明示している（`home-mixer/ads/tests/multi_risk_blender_tests.rs:161-172`）:

```rust
fn all_medium_risk_places_bsr_high_drops_normal() {
    let posts: Vec<_> = (1..=8).map(make_avoid_post).collect();  // 全部 Medium
    let with_high = blend_impl(posts.clone(), vec![make_bsr_high_ad(100)], 5);
    assert_eq!(ad_count(&with_high), 1);      // multi_risk: 広告1本入る
    ...
}
```

対する現行ブレンダーは同条件でゼロ（`home-mixer/ads/tests/partition_organic_blender_tests.rs:1135-1140` `bsr_high_ad_dropped_when_only_medium_posts`）。この対照テストが今日同時に追加されており、**A/B 比較の準備が整った**ことを示している。

**X ユーザー／クリエイターへの影響**

- 現時点では見え方は変わらない（既定オフ）。
- 有効化されると、**きわどい内容が多いタイムライン（従来は広告が挿さらなかった）にも広告が入る**。ユーザー体感としては広告密度の増加。
- クリエイター視点では、Medium リスク判定を受けている投稿の周辺にも広告在庫が付くため、これまで収益化から外れていた領域が対象化される方向。
- High リスク判定の投稿は引き続きどの広告の隣にも置かれない（`multi_risk_blender_tests.rs:147-158`）。この線引きは維持。

## 不確実な点（要確認）

1. **`MultiRiskAdsBlender` の投入計画** — `rust_home_mixer_ads_blender` の実運用値は本リポジトリからは読めない（`param.rs` はミラーの既定値のみ）。既定 `partition_organic_low_risk` に対し実験バケットで `multi_risk` が配られているかは不明。
2. **協調スパム判定でのフォロワー数の効きの向き** — プロンプト本体が非公開。フォロワー数が緩和方向（大手を疑わない）か厳格方向（大手の定型返信を疑う）かはコードで裏付けできない。
3. **返信スコアの読み出し失敗率** — フェイルクローズ化の実害は Strato の可用性次第だが、その稼働率は本リポジトリから観測できない。障害が稀なら影響は限定的、頻発するなら返信ランキングの穴が常態化する。
4. **`non_polling_timestamps` の消費者** — 書き込み（`update_past_request_timestamps_side_effect.rs`）と読み出し（`past_request_timestamps_query_hydrator.rs`）はあるが、スコアリング・フィルタ側で参照する箇所が本リポジトリ内に存在しない。home-mixer 外のサービスが使っていると推測。
5. **SimClusters `_TMP_RECOVERY` の背景** — データ欠損の規模・期間、および28日フォールバックが実際に発動したかはコードからは分からない。トピック埋め込みの鮮度低下がどれだけ現実に起きたかは不明。
6. **`CLIENT_TWEET_VIDEO_6SEC_VIEW` の位置づけ** — 8/26 に撤廃された VQV（完視聴）の代替として重み付き予測ヘッドになるのか、単なる計測用アクションに留まるのかは、現時点の配線からは判断できない。
7. **`enforcement_user.yaml` の空行2行** — 非公開の GrowthBook 側で `panda_reports_embedding_v10_rough_spam` の直後にルールが存在し、ミラー時に伏せられている可能性がある。公開分だけを見ればルール変更ゼロ。
