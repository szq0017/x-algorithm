## 1. 非IT精通者向け:今日から意識するとよいこと

- **「フォロー中」タブで、これまで丸ごと消えていた投稿が表示されるようになります。** 具体的には、あなたがフォローしている人が「フォロー外の、成人向け/スパム/拡散抑制ラベルの付いた投稿」を**引用ポスト**したり、そういう投稿への**返信スレッド**を投稿していた場合、従来はその投稿ごと「フォロー中」タブから除外されていました。今回、判定基準が「おすすめ欄用の厳しい基準」から「フォロー中タブ用の緩い基準」に変わり、**除外されなくなります**。フォロー中タブの内容がフォロー関係により忠実になる一方、**目に入る「危うい引用元」も増える**方向です。
- **返信欄の見え方が変わる境界が、フォロワー4万人から6万人に上がりました。** フォロワー4万〜6万人規模のアカウントの投稿への返信は、これまで「AIによる返信の並べ替え(返信ランキング)」の対象でしたが、今回から「リプライスパム検知」の対象に移ります。この規模の方の返信欄は、**整列されるのではなくスパムが除去される**挙動に変わります。
- **リプライスパム検知の処理経路が、返信ランキングと同じ列に統合されました。** 別々のデータストリームで動いていたものが 1 本にまとまったため、**処理の順番待ちと流量制限を共有**します。スパム判定が付くまでの時間が変わる可能性があります(具体的な流量設定は公開コードに含まれないため**要確認**)。
- **話題の重複情報が、最終段の並べ替えAIにも渡るようになりました。** 前回(8/18)「同じ話題が何回目に出てきたか」をモデル入力に加えた変更が入りましたが、今回それが**本番で既定オンの再ランキングモデル**にも供給されます。「バズっている話題に後乗りする」戦術の期待値は、引き続き下がる方向に傾いています(モデルの学習内容次第のため断定はできません)。
- **広告に関する安全性判定(ブランドセーフティ)の内部ロジックが整理されました。** ただし**既定はオフ**の実験フラグ配下です。有効化された場合、**古い判定器が「広告に不適」と付けたラベルの一部が無視され、より「安全」寄りに倒れます** = 広告が隣接しやすくなる方向です。
- 上記以外(コールドスタートの計測キー変更、成人向け判定の集計ラベル細分化)は**計測・ログのみの変更**で、あなたの見え方には影響しません。

## 2. 変更サマリ

- **「フォロー中」(逆時系列)タイムライン専用の可視性フィルタ用ハイドレータ `VFFollowingCandidateHydrator` が新設**され、従来の `VFCandidateHydrator` から差し替えられた。返信の祖先投稿・引用元投稿に適用される安全性レベルが `TimelineHomeRecommendations` から `TimelineHome` に変わり、**OON 専用の 26 種類の Drop ルールが適用されなくなった**。
- **grox の返信スパム検知/返信ランキングの発動フォロワー閾値が 40,000 → 60,000 に引き上げ**られた(前回 30,000 → 40,000 に続く 2 回連続の引き上げ)。
- **grox の `PostStreamTaskGenerator`(v1 トピック消費)が削除**され、スパムコメント検知と協調スパム検知のプランが**返信ランキングと同じ v3 ストリーム生成器へ統合**された。
- **広告ブランドセーフティ v2 (`compute_verdict_v2`) が「v2 ラベルが無ければ v1 判定へ完全に委譲する」方式に変更**され、v2 判定時は v1 由来の `NSFA_HIGH_PRECISION` / `NSFA_LIMITED_INVENTORY` を評価対象から外すようになった。**既定はオフ**。
- **セマンティックID(話題コード)由来の重複コンテキスト `sid_*` が、VMRanker(既定オン)のランキングリクエストにも渡される**ようになった。
- **Phoenix rank-all の投稿作成イベント取り込みが v3 Kafka トピックへ移行**(キー付きメッセージ化、別クラスタ、devel コンシューマグループ追加)。
- **可視性フィルタの Gizmoduck(ユーザー情報)RPC に 80ms のリクエストタイムアウトが明示設定**された。
- コールドスタートの追跡メトリクスのキー付けが著者ID→投稿ID に統一(計測のみ)。PTOS 成人向けクロスバリデーションの集計属性が hard/soft 二値から実ポリシー種別へ細分化(計測のみ)。

## 3. 変更点ごとの詳細:メカニズム → Xユーザー/クリエイターへの影響

### 3.1 「フォロー中」タブの祖先・引用元投稿に対する安全性フィルタが緩和 — 影響度: **大**

**メカニズム**:

- 逆時系列(フォロー中)パイプラインの可視性ハイドレータが差し替えられた:
  `home-mixer/candidate_pipeline/reverse_chron_posts_pipeline.rs:141-144`
  ```rust
  Box::new(VFFollowingCandidateHydrator::new(
      strato_vf_client,
      xai_vf_client,
  )),
  ```
  (旧: `Box::new(VFCandidateHydrator::new(strato_vf_client, xai_vf_client).await)`)

- **旧実装 `VFCandidateHydrator`** は候補を 2 群に分けて 2 本の RPC を並行発行していた(`home-mixer/candidate_hydrators/vf_candidate_hydrator.rs:66-104`):
  - `in_network`(=自分がフォローしている著者)の本体投稿・リポスト元 → 安全性レベル **`TimelineHome`**
  - **祖先投稿(返信スレッドの親・ルート)と引用元投稿** → 安全性レベル **`TimelineHomeRecommendations`**

- **新実装 `VFFollowingCandidateHydrator`** は、本体・祖先・引用元・リポスト元を**すべて 1 つの ID リストにまとめ、一律 `TimelineHome` で 1 本の RPC** を発行する(`home-mixer/candidate_hydrators/vf_following_candidate_hydrator.rs:47-66`):
  ```rust
  for candidate in candidates {
      post_ids.push(candidate.tweet_id);
      post_ids.extend(candidate.ancestors.iter().copied());
      if let Some(quoted_post_id) = candidate.quoted_tweet_id { post_ids.push(quoted_post_id); }
      if let Some(reposted_post_id) = candidate.retweeted_tweet_id { post_ids.push(reposted_post_id); }
  }
  ...
  client.get_result(post_ids, TimelineHome, query.user_id, context).await
  ```

- **2 つの安全性レベルの差**は `visibility-filtering/rules/registry.rs:134-169` に明示されている。`timeline_home_policy` は `base_home_rules()` そのまま(28 ルール)。`timeline_home_recommendations_policy` は**そこに OON 専用の Drop ルール 26 件を追加**したもの:
  ```rust
  fn timeline_home_recommendations_policy() -> Vec<Box<dyn Rule>> {
      let mut rules = base_home_rules();
      let oon_drops: Vec<Box<dyn Rule>> = vec![
          Box::new(DropTweetsWithDmcaMediaRule),
          Box::new(DropTweetsWithGeoRestrictedMediaRule),
          Box::new(author::NSFW_USER_AUTHOR_DROP),
          ...
          Box::new(tweet_label::DO_NOT_AMPLIFY_DROP),
          Box::new(tweet_label::MALICIOUS_URL_DROP),
          Box::new(tweet_label::SPAM_HIGH_RECALL_DROP),
          Box::new(tweet_label::NSFW_TEXT_DROP),
          Box::new(tweet_label::FOSNR_ABUSE_INSULTS_OON_DROP),
          Box::new(user_label::SPAM_HIGH_RECALL_USER_DROP),
          Box::new(user_label::IMPERSONATION_HIGH_PRECISION_USER_DROP),
          Box::new(user_label::DO_NOT_AMPLIFY_NON_FOLLOWER_USER_DROP),
          ...
      ];
      rules.extend(oon_drops);
      rules
  }
  ```

- **なぜ「本体投稿」には影響しないか**:「フォロー中」タブの候補源 `FollowingNightOwlSource` は全候補に `in_network: Some(true)` を立てる(`home-mixer/sources/following_night_owl_source.rs:209`)。したがって本体投稿とリポスト元は旧実装でも `TimelineHome` で判定されていた。**実際に変わるのは祖先投稿と引用元投稿だけ**である。

- **祖先・引用元の判定が候補全体の運命を決める**構造になっている点が重要。`should_drop_ancillary`(`vf_candidate_hydrator.rs:136-166`、今回 `pub(crate)` に公開されて新ハイドレータから再利用)が祖先・引用元・リポスト元のいずれかに Drop 判定を見つけると `drop_ancillary_posts = true` を立て、`AncillaryVFFilter` が**その候補を丸ごと除去**する(`home-mixer/filters/ancillary_vf_filter.rs:14-18`):
  ```rust
  .partition(|c| c.drop_ancillary_posts.unwrap_or(false));
  ```

**Xユーザー/クリエイターへの影響**:

- **視聴者側**:「フォロー中」タブで、フォロー中アカウントの投稿が**引用元や返信の親のせいで消えていた現象が解消**される。具体的には、引用元/祖先が以下のいずれかに該当する場合に消えていたが、今後は残る:
  - 著者が NSFW 設定ユーザー/NSFW 管理者判定
  - 投稿に `NSFW_HIGH_RECALL` / `NSFW_HIGH_PRECISION` / `NSFW_TEXT` / `GORE_AND_VIOLENCE_HIGH_PRECISION` / `NSFW_CARD_IMAGE` ラベル
  - `DO_NOT_AMPLIFY`(拡散抑制)、`MALICIOUS_URL`、`SPAM_HIGH_RECALL`
  - 著者にスパム/なりすまし/乗っ取り/読み取り専用/NSFWアバター等のユーザーラベル
  - DMCA メディア、地域制限メディア
  - OON 向けの侮辱系(`FOSNR_ABUSE_INSULTS_OON_DROP`)
  → **「フォロー中」タブは、より「自分がフォローした人が投稿したものは全部見える」に近づく**。同時に、**フォロー外の危うい投稿を引用/参照する経路での露出は増える**。センシティブな内容を避けたい利用者には体感の悪化になり得る。
- **クリエイター側**:引用ポストや、フォロー外アカウントへの返信を多用するスタイルのアカウントにとって、**フォロワーのタイムラインでの到達が改善**する。特に「話題の投稿を引用して論評する」形式は、引用元がグレーなラベルを持っていても、フォロワーには届くようになる。
- **注意**:これは「フォロー中」タブ限定の変更で、**「おすすめ(For You)」タブは従来どおり** `VFCandidateHydrator` を使い、OON 候補には `TimelineHomeRecommendations` が適用される。したがって「フォロー中では見えるが、おすすめでは相変わらず出ない」という非対称が拡大する。
- **副次効果**:VF への RPC が 2 本 → 1 本に減り、ID の重複排除も 1 回にまとまるため、フォロー中タブの応答は速くなる方向。

### 3.2 grox の返信スパム検知/返信ランキング発動閾値 40,000 → 60,000 — 影響度: **中**

**メカニズム**:

- `grox/flows/reply_spam/task_filter.py:17` — `TaskSpamFilter.FOLLOWER_COUNT_THRESHOLD_FOR_SPAM_DETECTION = 60000`(旧 40000)
- `grox/flows/reply_spam/task_filter.py:185` — `TaskReplyRankingFilter.FOLLOWER_COUNT_THRESHOLD_FOR_REPLY_RANKING = 60000`(旧 40000)
- 2 つのフィルタは**相補的**である:
  - スパム検知(`task_filter.py:79-92`):返信先の直近親著者**と**ルート著者の**両方**がフォロワー数 ≤ 閾値 のときのみ対象(片方でも超えると `reply_ranking_target` として除外)。
  - 返信ランキング(`task_filter.py:214-228`):親著者**または**ルート著者のフォロワー数が > 閾値 のときのみ対象(両方 ≤ だと `low_blast_radius` として除外)。

**Xユーザー/クリエイターへの影響**:

- **フォロワー 4 万〜6 万人規模のアカウント**が「返信ランキング(AI による返信の品質順並べ替え)」の対象から外れ、「リプライスパム検知」の対象へ移動した。前回(8/18)の 3 万〜4 万に続き、境界が 2 日で 2 段階上がったことになる。
- この層のアカウントの**返信欄は「良質な返信が上に来る」から「スパム返信が落とされる」へ**性格が変わる。返信で露出を狙うユーザーにとっては、**この規模のスレッドでは"質で上位に食い込む"経路が消え、"スパム判定を避ける"ことが主目的**になる。
- 逆に**フォロワー 6 万人超のアカウント**のスレッドだけが返信ランキングの対象として残る。返信での露出狙いは、より大きなアカウントに集中する誘因が強まる。
- コスト観点では、より高価な返信ランキング処理の対象母数を絞る意図と読める(**推測、要確認**)。

### 3.3 スパム検知プランが返信ランキングと同一ストリームへ統合 — 影響度: **中**

**メカニズム**:

- `PostStreamTaskGenerator`(v1 トピック `content-understanding-realtime-unified-posts` を消費し、`PlanSpamComment` と `PlanCoordinatedSpam` を注入していた)が**削除**された。
- 併せて定数 `POST_STREAM` と `TOPIC_UNIFIED_POSTS` も削除(`grox/flows/reply_spam/constants.py`)。
- 2 つのプランは `ReplyRankingTaskGenerator` へ移された(`grox/flows/reply_spam/generators.py:16-25`):
  ```python
  class ReplyRankingTaskGenerator(StreamTaskGenerator):
      TASK_GENERATOR_TYPE = REPLY_RANKING
      PLANS_TO_INJECT = {
          PlanReplyRanking.KEY,
          PlanSpamComment.KEY,
          PlanCoordinatedSpam.KEY,
      }
      def _get_loader(self):
          return KafkaPostLoader(TOPIC_UNIFIED_POSTS_V3)
  ```
- `StreamTaskGenerator` は**生成器単位で `max_qps` を持つ**(`grox/core/generators/stream_generator.py:15`)。統合により、返信ランキング・スパムコメント検知・協調スパム検知の 3 プランが**単一の QPS 予算と単一の Kafka コンシューマグループを共有**することになる。

**Xユーザー/クリエイターへの影響**:

- 3 種類の判定が**同じ投稿ストリームから同時に発火**するようになるため、対象投稿の抽出タイミングが揃う。これまで v1/v3 の 2 系統に分かれていたことによる「片方だけ処理される」ズレは解消する。
- 一方で**流量制限を共有**するため、投稿量の急増時にはスパム検知の遅延が返信ランキングの負荷に引きずられる可能性がある。実際の `max_qps` 設定値は公開コードに含まれない(**要確認**)。
- 対象トピックが v3 に一本化されたことで、**v1 トピックにしか流れていなかった投稿があった場合はスパム検知の対象外になる**が、v1/v3 のカバレッジ差は公開情報からは判定できない(**要確認**)。

### 3.4 広告ブランドセーフティ v2 の判定ロジック変更 — 影響度: **小**(既定オフ / 有効時は **中**)

**メカニズム**:

- v2 判定関数の冒頭に**「v2 ラベルが 1 つも無ければ v1 判定へ丸ごと委譲する」**分岐が追加された(`home-mixer/models/brand_safety.rs:88-101`):
  ```rust
  const V2_WRITTEN_LABELS: &[SafetyLabelType] = &[
      SafetyLabelType::GROK_SFA_V2,
      SafetyLabelType::GROK_NSFA_V2,
      SafetyLabelType::GROK_NSFA_LIMITED_V2,
      SafetyLabelType::GROK_NSFA_EXPANDED_V2,
  ];

  pub(crate) fn compute_verdict_v2(...) -> BrandSafetyVerdict {
      if !V2_WRITTEN_LABELS.iter().any(|l| labels.contains_key(l)) {
          return compute_verdict(labels, tweet_id);
      }
      ...
  ```
  旧実装は「v1 の Grok プロンプト由来ラベル(ルールID 1400/1410/1420/1500/1510/1610/1700)を剥がしてから v2 のリストで判定」する `strip_v1_grok_written` 方式だった。これが**削除**されている。
- 併せて v2 のリスク一覧から **v1 由来ラベル 2 件が除外**された:
  - `MEDIUM_RISK_LABELS_V2` から `NSFA_HIGH_PRECISION` を削除(`brand_safety.rs:65-81`)
  - `LOW_RISK_LABELS_V2` から `NSFA_LIMITED_INVENTORY` を削除(`brand_safety.rs:83-86`)
- 上流自身のテストがこの意図を明示している(`brand_safety.rs:274-322`, `v2_defers_to_v1_when_v2_has_not_ruled`)。特に末尾の "freed" ケース:
  ```rust
  let freed = labels_with(&[
      SafetyLabelType::NSFA_HIGH_PRECISION,
      SafetyLabelType::GROK_NSFA,
      SafetyLabelType::GROK_SFA_V2,
  ]);
  assert_eq!(compute_verdict(&freed, PRE_CUTOFF_ID), BrandSafetyVerdict::MediumRisk);
  assert_eq!(compute_verdict_v2(&freed, PRE_CUTOFF_ID), BrandSafetyVerdict::Safe);
  ```
  → **v1 が「広告不適(MediumRisk)」と判定する投稿を、v2 は「Safe」と判定する**ケースが明示的に許容されている。
- 有効化フラグ `EnableAdsBrandSafetyVerdictV2`(`rust_home_mixer_ads_bs_v2_exp_enabled`)の**既定値は `false`**(`home-mixer/params/param.rs:921-926`)。呼び出しは `home-mixer/candidate_hydrators/ads_brand_safety_vf_hydrator.rs:58-62`。

**Xユーザー/クリエイターへの影響**:

- **現時点では影響なし**(既定オフ)。ただし前回レポート時点の v2 は「v1 と挙動同値」を狙う設計だったのに対し、今回は**明確に v1 より緩い方向へ振れる設計**に変わった点が重要。
- 有効化された場合:Grok v2 が「広告に適する(SFA)」と判定した投稿は、**古い判定器が付けた NSFA ラベルがあっても Safe に昇格**する。結果として
  - **クリエイター側**:誤って「広告不適」扱いされていた投稿が解放され、**投稿の周辺に広告が挿入されやすくなる**。収益分配の対象になりやすくなる方向(収益分配の実装は本リポジトリ範囲外、**要確認**)。
  - **視聴者側**:これまで広告が付かなかった種類の投稿の近くにも広告が出るようになる。
  - **広告主側**:ブランドセーフティの基準が実質的に緩む。判定の主導権が完全に Grok v2 に移る。
- 逆に v2 ラベルが未付与の投稿は**完全に v1 の判定に戻る**(旧実装では v2 のラベル一覧で評価されていたため、v2 ロールアウト過渡期の誤判定が減る)。これは実装上の堅牢性改善。

  ```rust
  }),
  ```
- 値の生成元は前回(8/18)追加された `compute_slate_contexts`(`home-mixer/scorers/ranking_scorer.rs:646-702`)。セマンティックIDの L1〜L3 プレフィックス単位で「同一話題が上位に何件あったか(`sid_k`)」「直前の同話題投稿との順位差(`sid_gap`)」を算出する。
- 前回時点では `as_score_info`(`home-mixer/models/candidate.rs:161-180`、recsys 向けのスコア情報 = 主にログ/学習データ)にのみ渡っていた。**今回、推論時の再ランキング要求そのものに入った**。
- `EnableVMRanker` の**既定値は `true`**(`home-mixer/params/param.rs:604-609`)。つまり本番の既定経路で VMRanker に届く。

**Xユーザー/クリエイターへの影響**:

- 前回レポートで「モデルに渡しているだけ」と評価した段階から、**本番の再ランキングモデルが実際にこの信号を受け取る段階**へ進んだ。
- 期待される方向:**おすすめ欄で同じ話題の投稿が連続することが減る**。先に上位に入った投稿(`sid_k` が小さい)が有利、後発の類似投稿(`sid_k` が積み上がった状態)が不利。
- **クリエイター視点**:「トレンドに後乗りする」戦術の期待値がさらに下がる。同じ話題なら**早く出す**か、**別の切り口(=別のセマンティックID)にずらす**方が有利になり得る。
- ただし Rust 側に `sid_*` を使った明示的な減点処理は**依然として存在しない**(`ranking_scorer.rs` の `author_diversity_multipliers` は著者カウント `k` のみを使用)。実際の効き方は VMRanker の学習済み重み次第であり、**「話題連投が沈む」と断定はできない**(**要確認**)。

### 3.6 Phoenix rank-all の投稿作成イベント取り込みを v3 へ移行 — 影響度: **小〜中**

**メカニズム**:

- ストリームフォワーダの購読先が変わった(`phoenix-rankall-strato/stream_forwarders/postCreationEventForwarder.strato:3-14`):
  - トピック:`content_understanding_realtime_unified_posts` → **`content_understanding_realtime_unified_posts_v3`**
  - クラスタ:`/s/kafka/main-2:kafka-tls` → **`/s/kafka/phoenix-kafka-external-bootstrap`**
  - コンシューマグループ:`post_creation_event` → `post_creation_event_v3`、**devel グループ `post_creation_event_v3_devel` を新設**
  - メッセージ形式:`ValueOnly` → **`KeyValue`**(key = `Long`/`NativeEncoding`、value は従来どおり `ContentUnderstandingMetadataV2`/Thrift)
  - import 元も `content_understanding/sharedConfig` → `hydra/sharedConfig`
- 受け側の処理も引数型が変わった(`phoenix-rankall-strato/columns/phoenix_rank_all/postCreationEventProcessor.strato:7-12`):
  ```
  val executeOp = Op.execute({ idempotent = true })[(Long, Event), Unit] { ctx =>
    val (postId, _) = ctx.arg
    val request = { postId = postId, eventSource = PostCreation }
  ```
  → 従来は Thrift ペイロードの入れ子(`ctx.arg.postMetadata.post.postId`)から投稿IDを取り出していたが、**Kafka メッセージキーから直接取得**するようになった。

**Xユーザー/クリエイターへの影響**:

- この経路は「投稿が作成された瞬間に Phoenix の候補処理を発火させる」ものである。**新規投稿がおすすめ候補プールへ入るまでの経路**そのもの。
- キーからIDを取ることで、ペイロード内の入れ子が欠落していた場合の取りこぼしが構造的に無くなる。**新規投稿の取り込み漏れが減る方向**であり、投稿直後の露出の安定性に効く。
- ただし v1 トピックと v3 トピックのカバレッジ・遅延特性の差は公開コードからは判定できないため、**取り込み対象の母数が増えたのか同等なのかは要確認**。
- devel コンシューマグループの追加は開発環境向けであり、本番挙動には影響しない。

### 3.7 可視性フィルタの Gizmoduck RPC に 80ms タイムアウトを設定 — 影響度: **小〜中**

**メカニズム**:

- `visibility-filtering/server_deps.rs:244-253`:
  ```rust
  const GIZMODUCK_STRATO_REQUEST_TIMEOUT_MS: u64 = 80;

  fn gizmoduck_client_config(deterministic_aperture: bool) -> GizmoduckClientConfig {
      GizmoduckClientConfig {
          ...
          request_timeout_ms: Some(GIZMODUCK_STRATO_REQUEST_TIMEOUT_MS),
          ..Default::default()
      }
  }
  ```
  これまで `request_timeout_ms` は未設定(`Default`)だった。TES クライアントには従来から同種の設定がある(`server_deps.rs:238`)。
- Gizmoduck は**著者のアカウント安全性情報**(凍結・削除・非公開・NSFWユーザー/管理者フラグ・ユーザーラベル)を引くクライアントである(`visibility-filtering/hydration/gizmoduck_hydrator.rs:53-72` の `QueryFields::SAFETY, QueryFields::LABELS`)。
- ハイドレータ側の上位タイムアウトは 150ms(`gizmoduck_hydrator.rs:13`)。今回の 80ms は**その内側の RPC 単位のタイムアウト**なので、実効的な打ち切りが早まる。
- 失敗時の扱い:結果は `Hydrated::Failed` になり(`visibility-filtering/hydration/batch.rs:14-19`)、`get_or_default` 経由で参照されるため(`visibility-filtering/hydration/mod.rs:77`)、`AuthorFeatures` は**全フラグ false = 「安全な著者」の既定値**に落ちる。つまり**フェイルオープン**である。
- 緩和策として `FallbackCache`(直近の成功結果を保持し、`ServeStale` モードなら古い値を返す)が用意されている(`gizmoduck_hydrator.rs:23-27`)。ただし**本番でどのモードが設定されるかは公開コードに含まれない**(`filter.rs:189-190` はテスト用の `Disabled`)。

**Xユーザー/クリエイターへの影響**:

- 通常時は**タイムライン応答の尾側レイテンシ短縮**に効く。ユーザー体感としてはタイムラインの読み込みが速くなる方向。
- Gizmoduck が遅延した場合、**著者レベルの安全性ルール(凍結著者・非公開アカウント・NSFW著者・スパム著者ラベル等)が一時的に適用されない**投稿が混ざり得る。凍結・非公開アカウントの投稿が一瞬見えるといった事象の頻度が、理論上は上がる。フォールバックキャッシュのモード次第で実害は大きく変わる(**要確認**)。
- 投稿ラベルベースのルール(PDNA、スパムラベル等)は TES 経由の別ハイドレータなので、この変更の影響を受けない。

### 3.8 計測のみの変更(ユーザー影響なし)

- **コールドスタート追跡メトリクスのキー統一**(`home-mixer/scorers/author_cold_start.rs:92-107`):`count_tracked_ids` は従来、追跡対象IDに投稿IDが一致すれば投稿IDで、著者IDが一致すれば著者IDで別々に加算していた。今回、**一致判定は投稿ID・著者IDのどちらでも行い、カウンタのキーは常に投稿ID**に統一された。出力先は `home_mixer.cold_start_tracked_ids_total` という統計カウンタのみ(`author_cold_start.rs:110-127`)で、ランキングにも配信にも影響しない。運用者が特定の著者を追跡したとき、その著者の**どの投稿が**どの経路で出たかが分かるようになる、という観測性の改善。

  ```python
  Metrics.counter(metric).add(1, attributes={"outcome": judged.policyType.value})
  ```

  従来は `"hard"` / `"soft"` の二値に丸めていたものを、Grok 4.5 が下した**実際のポリシー種別をそのまま**属性に載せるようになった。`is_hard` による後続の分岐処理(`:134`)は変更されておらず、**判定挙動そのものは同一**。

## 5. 不確実な点(要確認)

1. **3.1 の変更が意図的な緩和か、リファクタリング時の副作用か**は、公開されたコミットメッセージからは判定できない。新ハイドレータは「Following 専用」という名前を持ち、Following タブでは本体が常に in-network である以上「安全性レベルを 1 つに統一してよい」という整理は自然に見える。しかし**祖先・引用元は in-network とは限らない**ため、結果として OON ルール 26 件が外れる。上流の意図が「祖先・引用元も含めてフォロー中は緩くする」なのか「本体だけを想定していた」のかは**要確認**。この変更に実験フラグは付いておらず、**無条件で有効**である点は確認済み。
2. **`sid_*` を VMRanker のモデルが実際にどう使うか**は、公開 Rust コードからは決定できない。Rust 側に明示的な減点処理はなく、学習済み重みに依存する。
3. **grox 生成器統合後の `max_qps` 設定値**は公開コードに含まれない(`StreamTaskGenerator.__init__` の引数として外部注入)。スパム検知の実効スループットが上がったか下がったかは判定不能。
4. **v1 トピックと v3 トピックのカバレッジ差**(3.3 / 3.6 の両方に関わる)。v1 のみに流れていた投稿種別があるかは不明。
5. **Gizmoduck の `FallbackCacheMode` の本番設定値**。`ServeStale` なら 3.7 のフェイルオープン懸念はほぼ解消されるが、`Disabled` なら実害が出る。公開コードにはテスト用の `Disabled` しか現れない。
6. **`EnableAdsBrandSafetyVerdictV2` の実際のロールアウト状況**。既定は `false` だが、実験プラットフォーム側でどの割合に配信されているかは本リポジトリからは分からない。
7. **ブランドセーフティ判定と収益分配の関係**。本リポジトリには広告挿入の可否ロジックはあるが、クリエイター収益分配の計算は含まれていない。
