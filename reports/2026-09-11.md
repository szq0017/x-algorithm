## 非IT精通者向け・運用方法のまとめ（行動指針）

- **今日の本命は「投稿が理由もなく消えてしまう事故」を減らす改修です。** ランキング（並び順）の計算式は今日も一切変わっていません。変わったのは、**Xの裏側で投稿の表示可否を判断するシステムが、時間内に情報を取り寄せられなかったときの振る舞い**です。
- **これまでの仕組み：** タイムラインに投稿を出す直前、Xは投稿ごとに「誰が書いたか」「規約違反ラベルが付いていないか」を別サービスに問い合わせます。**この問い合わせの制限時間が 0.15 秒**しかなく、時間切れになると投稿は**「安全側に倒して削除」＝タイムラインから丸ごと消える**扱いでした（`visibility-filtering/rules/mod.rs:25-30` の `unresolved_author` ＝ `Drop`）。つまり**あなたの投稿に何の問題がなくても、裏方が一瞬詰まっただけで誰にも表示されない**ことがありました。
- **今日の変更で、これが二段構えで緩和されました。**
  1. **制限時間が 0.15 秒 → 0.39 秒に延長**（約2.6倍）。時間切れそのものが大幅に減ります。
  2. **それでも間に合わなかった場合、「以前この投稿の著者は誰だったか」を記録した手元のメモ（最大100万件）から復元**して、判定を続行するようになりました。**この救済措置は既定でオン**です。
- **クリエイター側の行動指針：**
  - **「なぜかインプレッションが極端に落ちる時間帯がある」「バズっている最中に急に伸びが止まる」といった現象の一因が減る方向**の変更です。特に**急上昇中の投稿・大量の投稿が一斉に処理される時間帯**で恩恵が出ます。
  - ただしこれは**あなたの評価が上がるわけではありません**。「取りこぼしが減る」だけです。**シャドウバン的な現象の一部が、実は裏方の時間切れだった**という可能性が今回のコードから読み取れます。
  - **注意点（逆方向のリスク）：** 制限時間を延ばした分、**タイムラインの読み込みが遅くなる可能性**があります。同じコミットで「所定時間を超過した件数」を測る計測が追加されており（後述2）、**X側もこれを様子見している段階**と読めます。数値がまだ調整途中の可能性があるため、**この 0.39 秒という値は今後変わりうる（要確認）**。
- **同時に「消し漏れ」を塞ぐ修正も入りました（後述3）。** これまでは「投稿の本文情報が取れなかった」場合に、**成人向け判定・著作権削除（DMCA）・広告専用投稿（nullcast）といった安全性の情報まで道連れで無効化**されていました。今日から、本文が取れなくても**これらの判定は生き残ります**。**「裏方が詰まった瞬間はNSFWや削除対象がすり抜ける」という穴が塞がった**形です。
- **X の「Under the Hood（透明性ダッシュボード）」に国別情報が入ります（後述4）。** アカウント・投稿に対する措置が**「どの国で」適用されたかを日次で集計する新しい処理**が追加され、措置の理由も「法的要請 / 第三者通報 / DMCA / 未指定」の4分類で記録されます。**将来「あなたの投稿は◯◯国で非表示です」と理由付きで確認できるようになる布石**です（公開UIへの反映時期は要確認）。
- **動画の「動きで暴かれる」検査が強化されました（後述7）。** 動画から静止背景を差し引いて「動いている部分だけ」を抽出する解析が、**サンプル数 32→48 コマに増量、手ブレ補正（位置合わせ）を追加、肌色軸の判定を追加**。**静止画では健全に見えるが動かすと問題のあるものが写る動画**への対処が精密になりました（この機能自体は既定オフの任意機能＝要確認）。
- **「トレンドページ」「発見タブのスポットライト」が推薦システムの対象面として定義されました（後述6）。** さらに**「没入モード（縦型動画）での長時間滞在」を集計する新しい行動シグナル種別**が追加されました。**現時点では枠の予約のみで、ランキングへの反映は本コードからは確認できません（要確認）が、縦型動画の「最後まで見た／長く見た」が今後さらに効くようになる方向の準備**です。

## 変更サマリ

1. **可視性フィルタ（VF）の全バックエンド呼び出しのタイムアウトを 150ms → 390ms に統一**（TES／Gizmoduck／SocialGraph、および Strato クライアント側 100ms・80ms も 390ms へ）。時間切れによる「巻き添え削除」が大幅減。
2. **著者ID フォールバックキャッシュを新設（既定オン・最大100万件）。** TES（投稿本体サービス）が失敗しても、過去に成功した著者IDを再利用して判定を継続。従来は著者IDが解決できない投稿＝無条件 `Drop`。
3. **本文取得失敗時に他の安全性特徴まで初期化してしまう不具合を修正。** nullcast / コミュニティ投稿 / NSFW（ユーザー・管理者）/ 削除理由（DMCA等）/ 編集履歴 / メディア情報が、本文欠落時も保持されるように。
4. **Under the Hood（透明性）に国コードを追加。** 投稿・アカウントのラベル集計に `countryCodes` を追加し、**アカウント措置の日次イベントを生成する新規 Scalding ジョブ**を追加（理由を LEGAL_REQUEST / BYSTANDER_REPORT / DMCA / UNSPECIFIED の優先順位で解決）。
5. **広告挿入ログに `ads_blender` 項目を追加**（Following タイムラインは `"following"`、それ以外はパラメータ `rust_home_mixer_ads_blender` の値、既定 `"multi_risk"`）。判定・挿入密度の変更はなし。
6. **Phoenix proto に商品面 `TREND_PAGE`(16) / `EXPLORE_SPOTLIGHT`(17) を追加**、ユーザー行動集計種別のプレースホルダ29を **`IMMERSIVE_LONG_DWELL`** として実体化。
7. **Grox の動画「モーションリビール」解析を大幅強化**（32→48 コマ、ECC による位置合わせ、オプティカルフローによる残差整列、肌色軸ゲート）。
8. 挙動不変の基盤系：著者ラベルを HashSet からビットセット化（11ラベル固定・メモリ/速度改善、**判定結果は不変**）、新規 `clock_cache.rs`（**未接続 dead_code**）、キャッシュの事前メモリ確保、gRPC deadline の計測追加、Two-Tower モデルのパディング処理修正、Grox gRPC keepalive 調整。

## 変更点ごとの詳細（メカニズム → Xユーザー／クリエイターへの影響）

### 1. VF のタイムアウト 150ms → 390ms に統一（影響度：**大**）

**メカニズム**

可視性フィルタは、タイムラインに出す候補ごとに以下を並列で問い合わせます。

- TES（投稿本体：本文・著者ID・メディア・削除理由・nullcast・NSFW）
- Gizmoduck（著者アカウント：凍結・非公開・NSFW・各種ユーザーラベル）
- SocialGraph（閲覧者と著者の関係：フォロー／ブロック／ミュート）

これまで各クライアントの制限時間は**個別に 150ms 固定**でした。今回、共通定数に一本化されています。

`visibility-filtering/hydration/mod.rs:35`：
```rust
pub(crate) const HYDRATION_TIMEOUT: Duration = Duration::from_millis(390);
```

これを3つのハイドレータが参照します（`tes_hydrator.rs:14`、`gizmoduck_hydrator.rs:13`、`socialgraph_hydrator.rs:10` いずれも `const CLIENT_TIMEOUT: Duration = crate::hydration::HYDRATION_TIMEOUT;`）。

さらに**下位の Strato クライアント側の制限時間も引き上げ**られました（`visibility-filtering/server_deps.rs:332,346`）。

```rust
const TES_STRATO_REQUEST_TIMEOUT_MS: u64 = crate::hydration::HYDRATION_TIMEOUT.as_millis() as u64;   // 旧 100
const GIZMODUCK_STRATO_REQUEST_TIMEOUT_MS: u64 = crate::hydration::HYDRATION_TIMEOUT.as_millis() as u64; // 旧 80
```

**なぜこれが表示に効くのか。** TES の問い合わせが失敗すると、その投稿の**著者IDが解決できません**。著者IDが無い候補は `resolve_candidates` の `filter_map` で候補リストから脱落し（`visibility-filtering/models/mod.rs:47-64`）、最終的に以下の判定が確定します。

`visibility-filtering/rules/mod.rs:25-30`：
```rust
pub fn unresolved_author() -> Self {
    Self {
        action: VfAction::Drop(FilteredReason::UnspecifiedReason),
        decided_by: Some("unresolved_author_id"),
    }
}
```

つまり **TES のタイムアウト＝その投稿はタイムラインから消える**。制限時間が 2.6 倍になったことで、この「無実の削除」が構造的に減ります。

**Xユーザー／クリエイターへの影響**

- **恩恵を受ける側（投稿者）：** 高負荷時間帯・大量配信時に、**内容に問題がないのに配信されなかった投稿**が減ります。伸び盛りの投稿ほど短時間に大量の配信要求が走るため、**バズの立ち上がり局面での取りこぼしが減る**方向。
- **恩恵を受ける側（閲覧者）：** タイムラインの歯抜けが減ります。
- **トレードオフ：** VF が最大 390ms 待つようになるため、**タイムライン応答の遅い側（テールレイテンシ）が悪化しうる**。実際、同じコミットで「呼び出し元が指定した制限時間を超過したか」を測る計測が追加されています（後述2）。**ユーザー体感としては「消えにくくなる代わりに、まれに読み込みが重くなる」**可能性があります。
- **注意：** 390ms という値は上位の呼び出し元（home-mixer）の許容時間との兼ね合いで決まるはずですが、**呼び出し元の制限時間は本コードからは確認できません（要確認）**。上位が先に諦めれば、待った分がそのまま無駄になります。

### 2. gRPC deadline の解釈と超過計測を追加（影響度：**小**、ただし1の検証用）

**メカニズム**

呼び出し元が送る `grpc-timeout` ヘッダを解析し（`visibility-filtering/filter_tweets.rs:103-119`）、実処理時間と突き合わせて「収まった / 超過した」を記録します。

`visibility-filtering/rules/metrics.rs:102-114`（要約）：
```rust
if elapsed <= deadline { incr(DEADLINE, &[("outcome", "within")], 1); ... }
else { incr(DEADLINE, &[("outcome", "overrun")], 1); observe_vm(DEADLINE_OVERRUN_MS, ...); }
```

加えて処理を「ハイドレーション（外部問い合わせ）」と「ポストハイドレーション（ルール評価）」の2段階に分けて所要時間を計測（`visibility-filtering/filter.rs:40,50-51,90`）。

**Xユーザー／クリエイターへの影響**

直接の影響はありません。ただし**「390ms は妥当か」を X 側が測定中**であることを示しており、**この値が後日下げられる／上げられる可能性**を意味します。次回以降の差分で `HYDRATION_TIMEOUT` の再変更がないか注視すべき箇所です。

### 3. 著者ID フォールバックキャッシュ（既定オン）（影響度：**大**）

**メカニズム**

TES が失敗しても投稿を救済するため、**「投稿ID → 著者ID」だけを保持する手元キャッシュ**が新設されました。

`visibility-filtering/hydration/tes_hydrator.rs:19`：
```rust
pub(crate) type AuthorIdFallbackCache = FallbackCache<TweetId, u64>;
```

復元の条件は厳密で、**「過去に TES が成功して著者IDが取れた投稿」だけ**が対象です（`tes_hydrator.rs:195-232` の `resolve_pure_core`）。TES が明示的に「存在しない(NotFound)」と答えた投稿は復元されません。復元された著者IDは、本体取得も本文取得も失敗したときの**最後の砦**として使われます（`visibility-filtering/models/mod.rs:47-51`）。

```rust
let author = raw
    .request_author_id
    .or_else(|| core.get(&raw.tweet_id).map(|c| c.author_id))
    .or_else(|| recovered_authors.get(&raw.tweet_id).copied())?;
```

**既定でオンである点が重要**です（`visibility-filtering/config.rs:47-58`）。

```rust
pub(crate) fn author_id_fallback_enabled() -> bool {
    std::env::var("VF_AUTHOR_ID_FALLBACK_ENABLED").ok()
        .is_none_or(|value| parse_env_flag(Some(&value)))   // 環境変数が未設定なら true
}
```
容量の既定は **1,000,000 件**（`config.rs:53-58`）。比較として、著者アカウント情報側のフォールバックキャッシュ（`VF_FALLBACK_CACHE_ENABLED`）は**未設定なら false＝既定オフ**のままで、**今回オンになったのは著者IDキャッシュだけ**です。

**Xユーザー／クリエイターへの影響**

- **1 とセットで「無実の削除」をさらに減らします。** 390ms でも間に合わなかった場合の二次救済。
- **対象は「一度は正常に配信された投稿」** です。**投稿直後の新規投稿は、まだキャッシュに載っていないため救済されません。** 投稿直後に TES が詰まると従来どおり消えます。**キャッシュに載る条件から見て、恩恵は「継続的に配信され続けている投稿＝すでに伸びている投稿」に偏ります。**
- **安全性は落ちていません。** 復元されるのは著者IDだけで、その著者に対する凍結・NSFW・スパム等の判定（Gizmoduck 由来）と投稿側のラベル判定はこれまで通り実行されます。テストでも、復元経路を通った投稿に対し nullcast ドロップが従来どおり効くことが明示的に検証されています（`tes_hydrator.rs:615-668` `missing_core_keeps_nullcast_drop_for_supplied_and_recovered_authors`）。

### 4. 本文欠落時に安全性特徴まで消えていた不具合の修正（影響度：**中**）

**メカニズム**

投稿の特徴量の組み立て（`visibility-filtering/hydration/tes_hydrator.rs:236-269` `build_tweet_features`）は、旧実装では **本文（core）が取れなければ `TweetFeatures` 全体を `unwrap_or_default()` で初期化**していました。`TweetFeatures` には本文のほかに、

- `is_nullcast`（広告専用・タイムラインに出さない投稿）
- `is_community_tweet`（コミュニティ投稿）
- `nsfw`（ユーザー自己申告／管理者判定）
- `takedown_reasons`（DMCA・法的要請等）
- `media` / `edit_control`

が同居しており、**これらは本文とは別の問い合わせで取得しているにもかかわらず、道連れで全部 false / 空になっていました。**

新実装は core だけを既定値にし、残りは取得結果をそのまま載せます。

```rust
let core = core_datas.get(&tweet_id).map(|core_data| CoreFeature { ... }).unwrap_or_default();
TweetFeatures { core, media, takedown_reasons, nsfw, is_nullcast, is_community_tweet, edit_control }
```

新テスト `assemble_preserves_independent_features_when_core_missing`（`tes_hydrator.rs:588-613`）が、本文欠落時でも nullcast・コミュニティ・NSFW・DMCA・メディアが保持されることを固定しています。

**Xユーザー／クリエイターへの影響**

- **これは「厳しくなる」方向の変更です。** 従来は、本文取得だけが失敗した瞬間に **NSFW 判定・DMCA 削除・nullcast 除外がすり抜けていた**ことになります。今日からは塞がります。
- ただし 3 の救済と組み合わさるため、**「本文が取れないから消える」から「本文が取れなくても正しく判定される」へ**の移行であり、全体としては**判定の精度が上がる**変更です。
- **影響を受ける層：** 成人向け・センシティブ寄りの投稿、著作権侵害申立てを受けた投稿、広告専用投稿。**バックエンドが不安定なタイミングで露出を得ていた分が消えます。**

- **ただし公開UIに出るかどうか・いつ出るかは本コードからは判断できません（要確認）。** 追加されたのはデータ生成と配信スキーマのみです。

### 7. トレンドページ／発見スポットライトと「没入長時間滞在」シグナル（影響度：**中**、ただし準備段階）

**メカニズム**

推薦システムの商品面 enum に追加（`phoenix/.../proto/recsys.proto:974-978`、Rust 版・Python 版の両方に同一変更）：
```protobuf
PRODUCT_SURFACE_TREND_PAGE = 16;
PRODUCT_SURFACE_EXPLORE_SPOTLIGHT = 17;
PRODUCT_SURFACE_PLACE_HOLDER_18 = 18;  // 以降 20 まで予約
```

ユーザー行動集計種別の実体化（同 `:1638`）：
```protobuf
-  PLACEHOLDER_29 = 29;
+  IMMERSIVE_LONG_DWELL = 29;
```

**Xユーザー／クリエイターへの影響**

- **トレンドページ・発見タブのスポットライトが、For You と同じ推薦基盤で個人最適化される布石**です。トレンドが「万人共通の話題一覧」から「あなた向けに並べ替えられた話題」へ寄る方向。
- **`IMMERSIVE_LONG_DWELL` は縦型動画（没入モード）での長時間滞在を、独立した行動履歴の種別として集計する**ものです。既存の `IMMERSIVE`(26) に対し「長く見た」を別建てにするため、**「流し見された回数」より「じっくり見られた回数」が重く扱われる方向**。縦型動画の**冒頭で引き止めて最後まで見せる構成**の価値が上がります。
- **ただし enum の定義追加のみで、これらを読むスコアリング側のコードは本コミットには含まれません（要確認）。** 実際のランキング反映時期は不明です。

### 8. 挙動不変の基盤系（影響度：**小**）

- **著者ラベルのビットセット化**（`visibility-filtering/models/author.rs:15-44`）：`HashSet<LabelValue>` を 11 種固定の `AuthorLabelSet(u64)` に置換。`AuthorFeatures` が 16 バイトの `Copy` 型になり、候補ごとのメモリ確保が消えます。**判定に使われる11ラベル（NSFW各種・スパム・侮辱・乗っ取り・読み取り専用・なりすまし・DoNotAmplify）は完全に同一**で、除外された `EGREGIOUS_NSFW` / `RECOMMENDATIONS_BLACKLIST` は**元々どのルールも参照しておらず「常に許可」だった**ことがゴールデンテストの削除内容から確認できます（`visibility-filtering/rules/golden_corpus.rs` から該当4ケースを削除）。**表示結果は変わりません。** 未対応ラベルの出現数は新メトリクス `vf_author_labels{result="unmapped"}` で監視されます。
- **`visibility-filtering/clock_cache.rs`（新規446行）**：32-way セットアソシアティブの CLOCK 置換キャッシュ。ファイル冒頭で `#![cfg_attr(not(test), expect(dead_code, reason = "TODO: no consumer wired yet"))]` と明記されており、**まだどこからも使われていません**。既存の LRU 系キャッシュを置き換える準備と読めます。
- **キャッシュの事前メモリ確保**（`fallback_cache.rs:38-42`、`expiring_cache.rs:29-32`）：起動時に容量分を `reserve` し、運用中の再確保による遅延スパイクを回避。
- **Two-Tower モデルのパディング処理修正**（`phoenix/xrex/models/recsys_two_tower_model.py:70-81, 1277-1281`）：ユーザー塔のアテンションで、**パディング位置に履歴と同じセグメントIDを与えていた**ものを `PADDING_SEGMENT_ID` に分離。履歴が短いユーザーの埋め込み品質に効く修正ですが、**再学習が前提のため実運用への反映時期は不明（要確認）**。
- **Grox の gRPC keepalive 調整**（`grox/core/services/service.py:25,29`）：`keepalive_timeout_ms` 5000→20000、`min_ping_interval_without_data_ms` 300000→5000。接続断による安全性判定の取りこぼし低減が目的と読めます。ユーザーへの直接影響なし。

### 9. Grox のモーションリビール解析強化（影響度：**中**、ただし既定オフ）

**メカニズム**

動画から「静止している背景」を時間方向の中央値で推定し、そこからの残差＝**動いている部分だけを浮かび上がらせた静止画**を作り、Grox（マルチモーダル安全性モデル）に渡す機能です。

- 入力コマ数 **32 → 48** に増量（`grox/libs/video_tools/image.py:159`、`grox/libs/video_tools/video_frames.py:23`）
- **ECC（Enhanced Correlation Coefficient）によるフレーム位置合わせ**を追加（`image.py:247-278`）＝手ブレ・カメラ移動のある動画でも残差抽出が成立
- **位相相関による「静止判定」**（`image.py:280-296`）＝カメラが動いていないコマだけを効率的に処理
- **オプティカルフローによる残差の整列**（`image.py:305-352`）
- **Lab色空間の肌色軸ゲート** `_MOTION_REVEAL_SKIN_LAB_AB = (143.0, 148.0)`、距離閾値 12.0（`image.py:178-179`）
- 事前ゲート `_MOTION_REVEAL_PREGATE_P99 = (2.0, 130.0)`（`image.py:177`）＝動きが小さすぎる／大きすぎる動画は処理しない

**Xユーザー／クリエイターへの影響**

- **静止画のサムネイルやフレーム単体では健全に見えるが、動かすと問題のある内容が現れる動画**（一瞬だけの挿入、動きによって初めて判別できる内容など）に対する検出が精密になります。
- 肌色軸のゲートが入っていることから、**主たる用途は成人向けコンテンツの検出**と読めます。
- **ただしこの機能は `enable_motion_reveal` フラグ付きの任意機能で、既定は無効**（`video_frames.py:47,71`）。**本番の安全性パイプラインから呼ばれているかは公開コードの範囲では確認できません（要確認）。**

## 不確実な点（要確認）

1. **390ms が最終値かは不明。** 同コミットで deadline 超過の計測が追加されており、**測定→再調整の途中**である可能性が高い。上位の home-mixer 側が VF に与えている制限時間は公開コードから読めないため、**390ms 全部を待てる保証はない**。
2. **著者IDキャッシュの実効カバレッジ不明。** 1,000,000 件・64シャードだが、**エントリの生存期間（TTL）や再起動時の扱い**はこの差分からは読み取れない。実際に何割の失敗が救済されるかは不明。
3. **UTH の国別情報が一般ユーザー向けUIに出る時期・範囲は不明。** データ生成ジョブとスキーマのみの追加。
4. **`IMMERSIVE_LONG_DWELL` / `TREND_PAGE` / `EXPLORE_SPOTLIGHT` を消費する側のコードが未公開。** enum 予約のみのため、ランキングへの実反映時期・重みは不明。
5. **`rust_home_mixer_ads_blender` の既定値 `"multi_risk"` が何を指すか不明。** ブレンダー実装の中身は本差分に含まれない。
6. **モーションリビールが本番の安全性判定に接続されているか不明。** 既定オフの任意機能であり、呼び出し元が公開範囲に存在しない。
7. **`clock_cache.rs` の接続先が未定。** 自己申告で `no consumer wired yet`。次回以降、どのキャッシュを置き換えるかが焦点。
8. **Two-Tower のパディング修正は再学習しない限り本番に反映されない。** 反映時期は不明。
