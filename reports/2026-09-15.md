## 非IT精通者向け・運用方法のまとめ（行動指針）

- **今日、あなたの For You の並び順を直接変える変更は、ほぼありません。** ランキングの計算式（`ScoringWeights`）は20日連続で据え置きです。今日の変更の大半は **「Xが自社のフィードを採点するための物差し」を作った**もので、ユーザーから見た挙動は**現時点では変わりません**。

- **① Xは「フィードが単調になっていないか」を本格的に計測し始めました（後述1・2）。これは近い将来の変更の前触れです。**
  - 新しく `ResponseDiversityStatsSideEffect` という計測装置が For You の配信パイプラインに組み込まれました（`home-mixer/candidate_pipeline/phoenix_candidate_pipeline.rs:455`）。**配信したタイムライン1本ごとに、「何人の別々の著者がいたか」「一番多い著者が何割を占めたか」「話題（セマンティックID）が何種類あったか」「フォロー内の投稿が何割か」を記録**します（`response_diversity_stats_side_effect.rs:120-186`）。
  - **重要なのは「3つの断面」で測っている点**です（`response_diversity_stats_side_effect.rs:17-19, 51-56`）。
    1. `final` … 実際にユーザーに配信した最終結果
    2. `top10` … そのうち**先頭10件**（＝ほとんどの人が実際に見る範囲）
    3. `pre_heuristic` … **「著者多様性ペナルティなどの後処理を適用する前」の、モデルの生スコア順**
  - **つまりXは「自分たちがかけている“同じ人ばかり出さない”補正が、本当に効いているのか」を数値で検証する段階に入った**ということです。この計測の結果次第で、**今後 `AuthorDiversityDecay` / `AuthorDiversityFloor`（同一著者の連投にかけるペナルティの強さ）が調整される可能性が高い**と読めます。
  - **クリエイター側の行動指針：** 今すぐ何かが変わるわけではありませんが、**「1人の著者がタイムラインの25%以上/50%以上を占める」状態をXは問題として計測対象にしています**（`tweet_type_metrics_hydrator.rs:155-159`）。**短時間の大量連投で他人のタイムラインを埋める戦法は、中期的に抑制される方向**と見るのが妥当です。分散投稿に寄せるほうが安全です。

- **② 「この人の投稿、あなた一度も反応したことないですよね」という判定が新設されました（後述2）。**
  - 新しいラベル `AUTHOR_NOT_ENGAGED_BY_VIEWER`(317) が追加されました。これは **「フォローもしていない」かつ「過去にいいね・返信・RT・クリック・ブックマークなど18種の能動的な反応を一度もしていない」著者の投稿**に付きます（`util/viewer_history.rs:9-28`, `tweet_type_metrics_hydrator.rs:203-208`）。
  - このラベルは**クライアントのイベントログに乗る**ため、Xは「まったく縁のない著者を見せたとき、ユーザーは実際どう反応するか」を**大規模に集計できるようになりました**。
  - **意味するところ：** 現状は計測のみですが、**「初見の著者をどれだけ混ぜるか（＝新規発見の量）」を調整するためのデータ取り**です。ここが増える方向に調整されれば**小規模アカウントの露出が増え**、減る方向なら**既に接点のある著者に偏る**ことになります。**どちらに動くかはこのコードからは判断できません（要確認）。**

- **③ 「連携スパム（組織的な返信スパム）」の取り締まり範囲が狭まりました（後述3）。これは実際に効いている挙動変更です。**
  - grox の連携スパム検知は、**「スレッドの大元の投稿者のフォロワー数」が閾値未満だと、そもそも検査しない**設計です（`grox/flows/reply_spam/task_filter.py:158`）。
  - この閾値が **10,000 → 30,000 に引き上げ**られました（同 `:97`）。つまり **フォロワー 1万〜3万の人の投稿にぶら下がる組織的スパム返信は、今日から検査対象外**です。
  - 履歴を見ると 8/13 に 1,000 → 9/4 に 5,000 → 9/8 に 10,000 → 9/15 に 30,000 と、**段階的に「大物の投稿だけ」に絞り込み続けています**。誤検知の抑制か処理コストの削減が目的と推測されますが、**理由はコードからは読み取れません（要確認）**。
  - **ユーザー側の行動指針：** **フォロワー数万規模までのアカウントの返信欄は、スパム対策の自動保護が薄くなります。** 返信欄が荒れやすいと感じる中規模アカウントは、**返信制限（返信できる人の設定）などXの手動機能に頼る比重を上げる**のが現実的です。なお**個人単位のスパム判定（`TaskSpamFilter`、閾値15万）は変更なし**で、そちらは従来通り動きます。

- **④ 広告が「クリックされるか」ではなく「いくら買ってもらえるか」で並ぶ準備が始まりました（後述4）。**
  - 予測対象の連続値シグナルに **`ADS_WEB_CT_PURCHASE_VALUE`(5)** が追加され、あわせて**「この広告主の直近28日間の平均購入額（USD）」を推論リクエストに同梱する仕組み** `PurchaseValueBaseline` が新設されました（`recsys.proto:124-131, 489`）。
  - **意味するところ：** これまで広告ランキングは主に「クリック/コンバージョンの確率」で動いていました。今回の枠は **「予測購入金額（＝実際の売上）」で広告を並べる**ための土台です。実現すれば、**高単価商材の広告が表示されやすくなり、低単価・釣り型の広告が相対的に不利**になります。
  - **ただし現時点では枠と検証コードだけで、実際の配信には一切つながっていません**（proto とヘルパ `purchase_value.rs` 以外に参照箇所なし＝コード全体を grep して確認済み）。**いつ有効化されるかは不明（要確認）。**
  - **一般ユーザーへの影響：** 将来的に**表示される広告の「客単価」が上がる**方向。**広告の本数が増える変更ではありません**（広告挿入密度に関する変更は今回ゼロ）。

- **⑤ 残り2件はサーバー内部の効率化で、ユーザー体験への影響はゼロです。** 学習用GPUの計算方式の切り替えと、学習データ取り込みの監視ログの送信間隔を30秒→120秒に変更しただけです（後述5）。

## 変更サマリ

1. **フィード多様性の計測装置 `ResponseDiversityStatsSideEffect` を新設**し、Phoenix 候補パイプラインに組み込み。配信スレート1本ごとに著者・供給元・話題（セマンティックID）の集中度を、`final` / `top10` / `pre_heuristic` の3断面で記録。既定サンプリング率5%。**ランキング挙動の変更なし。**
2. **投稿ラベル（tweet type metrics）に12種のビットを追加**（239〜244、315〜320）。スレート全体の著者集中度（著者ユニーク率≤50%、ユニーク著者≤5/10/15、単一著者シェア≥25%/50%）と、投稿ごとの位置情報（同一著者の重複、話題の重複、閲覧者が未接触の著者か）を付与。**クライアントイベントの分析用であり、ランキング入力ではない。**
3. **grox 連携スパム検知の対象閾値を 10,000 → 30,000 フォロワーに引き上げ**。スレッド大元の投稿者が3万フォロワー未満なら検査をスキップ。**実挙動の変更あり。**
4. **Phoenix proto に広告の購入金額予測枠 `ADS_WEB_CT_PURCHASE_VALUE`(5) と `PurchaseValueBaseline` メッセージを追加**（広告主の28日平均購入額をリクエストに同梱）。検証ヘルパとテストのみで、**配信・学習側への配線はなし**。
5. 挙動不変の基盤系：H100 の attention 実装を `pallas_ranker_varlen_attn` → `cutedsl_ranker_varlen_attn` に統一、Kafka データローダの OpenTelemetry メトリクス送出間隔を 30秒 → 120秒に緩和。

### 1. フィード多様性の計測装置を新設（影響度：**中**／挙動不変だが今後の変更の予告として重要）

**メカニズム**

新ファイル `home-mixer/side_effects/response_diversity_stats_side_effect.rs` が追加され、Phoenix 候補パイプラインの副作用リストに組み込まれました。

`home-mixer/candidate_pipeline/phoenix_candidate_pipeline.rs:455`：
```rust
Box::new(ScoredStatsSideEffect),
Box::new(ResponseDiversityStatsSideEffect),   // ← 追加
Box::new(AuthorServedMetricsSideEffect),
```

計測は3つの断面で行われます（`response_diversity_stats_side_effect.rs:17-19, 51-56`）：

```rust
const STAGE_FINAL: &str = "final";
const STAGE_TOP10: &str = "top10";
const STAGE_PRE_HEURISTIC: &str = "pre_heuristic";
...
let final_order = sorted_desc(selected.iter(), |c| c.score);
let top = &final_order[..TOP_POSITIONS.min(final_order.len())];   // TOP_POSITIONS = 10
let pre_heuristic =
    pre_heuristic_top_k(selected, &input.non_selected_candidates, selected.len());
```

ここが本質的です。`pre_heuristic_top_k` は **`weighted_score`（＝モデルの重み付きスコア、後処理前）** で並べ直したものです（`:85-95`）。一方 `final` は **`score`（＝著者多様性ペナルティ等を適用した後の最終スコア）** 順です。この2つの定義は `home-mixer/scorers/ranking_scorer.rs:836-837` で確定します：

```rust
candidate.weighted_score = scored.weighted_score;
candidate.score = scored.score;
```

そして `score` は `apply_author_diversity`（`ranking_scorer.rs:666-672`、`AuthorDiversityDecay` / `AuthorDiversityFloor` を使う）を通ったあとの値です。

記録される指標は以下（`:120-186`）：

| 指標 | 意味 |
|---|---|
| `Size` | スレートの件数 |
| `UniqueAuthors` / `UniqueAuthorRatio` | 別々の著者の数／全体に占める割合 |
| `MaxAuthorShare` | **最も多く登場した著者が占める割合** |
| `AuthorHhi` | 著者集中度（ハーフィンダール指数。1に近いほど独占的） |
| `AuthorEntropyNorm` | 著者分布の均等さ（1に近いほど均等） |
| `UniqueSources` / `SourceEntropyNorm` | 供給元（`served_type`＝どの検索経路で来たか）の多様性 |
| `InNetworkShare` | **フォロー内投稿の割合** |
| `SidCoverage` | セマンティックIDが付いている投稿の割合 |
| `UniqueSidL1` / `MaxSidL1Share` / `SidL1EntropyNorm` | **話題（粗い粒度）の多様性・集中度** |
| `UniqueSidL2` / `SidL2EntropyNorm` | 話題（細かい粒度）の多様性 |

集計そのものは新ユーティリティ `home-mixer/util/composition.rs` が担当します（HHI とエントロピーを一括計算する小さな構造体、63行）。

負荷対策として、**実験バケットに入っていないリクエストは5%だけ**サンプリングされます（`:14, 40-41`）：
```rust
const DEFAULT_SAMPLING_RATE: f64 = 0.05;
...
if experiment_buckets.is_empty() && random::<f64>() >= DEFAULT_SAMPLING_RATE {
    return Ok(());
}
```
対応する新スイッチ `EnableResponseDiversityStatsExperimentBucket`（`rust_home_mixer_enable_response_diversity_stats_experiment_bucket`、既定 `false`）が `home-mixer/params/param.rs:103-108` に追加されています。これは**計測を止めるスイッチではなく、実験グループ別に分けて集計するためのスイッチ**である点に注意してください（`false` でも5%サンプリングは走ります）。

**Xユーザー／クリエイターへの影響**

- **今日この瞬間の影響はゼロです。** 副作用（side effect）はレスポンスを返したあとに走る記録処理であり、候補の並び順にも取捨選択にも一切関与しません。
- **ただし「何を測るか」は「何を変えるつもりか」を示します。** `pre_heuristic` と `final` を並べて測る設計は、**「著者多様性ペナルティを入れたことで、実際にどれだけ多様になったか（＝ペナルティが強すぎ／弱すぎでないか）」を A/B 検証する**ためのものとしか読めません。
- **想定される次の一手：** `AuthorDiversityDecay` / `AuthorDiversityFloor` の再調整。これが強化されれば**同一著者の連投は不利、多様な著者の露出は有利**。緩和されれば逆。**どちらに動くかは現時点で不明（要確認）。**
- **`InNetworkShare` を測っていることも注目点です。** 「フォロー内 vs フォロー外の比率」は OON（Out-Of-Network）係数の調整に直結する指標であり、ここも将来の変更候補です。

**メカニズム**

`home-mixer/util/tweet_type_metrics.rs:23-39` に12個の新ビットが定義されました。

スレート（配信されたタイムライン）全体にかかるラベル（全投稿に同じ値が付く）：

| ビット | 名前 | 条件 |
|---|---|---|
| 239 | `unique_author_ratio_lte_50_pct` | 著者ユニーク率 ≤ 50% |
| 240 | `unique_author_lte_5` | 別々の著者が5人以下 |
| 241 | `unique_author_lte_10` | 別々の著者が10人以下 |
| 242 | `unique_author_lte_15` | 別々の著者が15人以下 |

| 244 | `single_author_gte_50_pct` | **単一著者が50%以上を占める** |

投稿ごとにかかるラベル：

| ビット | 名前 | 条件 |
|---|---|---|
| 315 | `author_repeat_in_slate` | 同じ著者がこれより上位に**1回以上**既出 |
| 316 | `author_repeat_gte_3_in_slate` | 同じ著者がこれより上位に**2回以上**既出（＝3件目以降） |
| 317 | `author_not_engaged_by_viewer` | **未フォロー かつ 過去に能動的反応なし**の著者 |
| 318 | `has_semantic_ids` | 話題ベクトル（セマンティックID）が付与済み |
| 319 | `sid_l1_repeat_in_slate` | **同じ粗い話題**が上位に既出 |
| 320 | `sid_l2_repeat_in_slate` | **同じ細かい話題**が上位に既出 |

判定は `home-mixer/candidate_hydrators/tweet_type_metrics_hydrator.rs:138-222` に実装されています。ポイントは **スコア降順に走査しながら「自分より上に同じ著者/話題が何回出たか」を数える**ことです（`:167-172, 193-200`）：

```rust
let prior_appearances = author_counts.entry(candidate.author_id).or_insert(0);
if *prior_appearances >= 1 {
    post_bits.insert(AUTHOR_REPEAT_IN_SLATE);
}
if *prior_appearances >= 2 {
    post_bits.insert(AUTHOR_REPEAT_GTE_3_IN_SLATE);
}
```

「未接触著者」の判定には新ファイル `home-mixer/util/viewer_history.rs` が使われます。閲覧者の行動履歴（Arrow 形式の `columnar_scoring_sequence`）を読み、**18種の能動的アクション**のいずれかがあった著者を集めます（`viewer_history.rs:9-28`）：

`ServerTweetFav` / `ServerTweetReply` / `ServerTweetQuote` / `ServerTweetRetweet` / `ClientTweetClick` / `ClientQuotedTweetClick` / `ClientTweetOpenLink` / `ClientTweetClickProfile` / `ClientTweetPhotoExpand` / `ClientQuotedTweetPhotoExpand` / `ClientTweetVideoOpen` / `ClientTweetVideoQualityView` / `ClientQuotedTweetVideoQualityView` / `ClientTweetShare` / `ClientTweetClickSendViaDirectMessage` / `ClientTweetShareViaCopyLink` / `ClientTweetBookmark` / `ClientTweetFollowAuthor`

そして「フォローもしていない、かつこの18種のどれもしたことがない」著者に 317 が立ちます（`tweet_type_metrics_hydrator.rs:203-208`）：

```rust
if let Some(engaged) = &engaged_authors
    && !followed.contains(&candidate.author_id)
    && !engaged.contains(&candidate.author_id)
{
    post_bits.insert(AUTHOR_NOT_ENGAGED_BY_VIEWER);
}
```

**このラベルがランキングに使われていないことの根拠：**
`TweetTypeMetricsHydrator` は **`post_selection_hydrators`**（＝候補の選抜が終わったあとに走る層）に登録されています（`phoenix_candidate_pipeline.rs:425`）。出力先を追うと、`controller_data`（`util/urt/controller_data.rs:8-16`）経由でクライアントに渡り、クライアントイベントの分類軸として Kafka に戻る経路（`side_effects/client_events_kafka_side_effect.rs:164, 195`）しかありません。**スコアラーもフィルタもこの値を読んでいません。**

**Xユーザー／クリエイターへの影響**

- **並び順への影響は今日時点でゼロ**です。これは「配信結果に後付けで貼るラベル」です。
- **ただしXは今後、「著者が重複しているタイムライン」と「していないタイムライン」で、ユーザーの滞在時間・エンゲージメントがどう違うかを直接比較できます。** 結果が「重複が多いとユーザーが離脱する」と出れば、**同一著者の連投抑制が強化される**方向に進みます。
- **317（未接触著者）は「新規発見の量」を測る指標です。** Xが「初見の著者をもっと混ぜたほうが良い」と結論すれば、**フォロワーの少ないアカウントの露出が増える**可能性があります。逆の結論なら**既存の接点に閉じる**方向です。**現時点では結論は出ていません（要確認）。**
- **話題の重複（319/320）も同時に測られている**点は、9/12 に追加された DPP のシード機能（同一話題の連続排除）と目的が一致します。**「同じ話題が続く体験」をXが問題視しているのは、2つの独立した変更から裏付けられます。**

### 3. grox 連携スパム検知の対象範囲を縮小（影響度：**中**／実挙動の変更あり）

**メカニズム**

この値の使われ方が重要です（同ファイル `:157-162`）：

if root_user_follower_count < cls.FOLLOWER_COUNT_THRESHOLD_FOR_SPAM_DETECTION:

| 2026-09-08 | 10,000 |
| **2026-09-15** | **30,000** |
