## 非IT精通者向け：今日から意識したい運用方法

- **動画で「見た目をごまかす」タイプの投稿は、近いうちに通用しなくなります。** 静止画のような覆いをかぶせて、その下に本当の中身を薄く動かして隠す——という動画の作り方を見破る新しい審査ラインが、今日まるごと1本追加されました（下記②）。今はまだ設定1つでオフになっていますが、パイプラインは末端まで組み上がっています。**いいね64件以上の動画投稿**が対象なので、伸びている動画ほど先に審査されます。心当たりのある投稿は今のうちに整理しておくのが無難です。
- **その新ラインでは「判定できなかった＝セーフ」ではなく「判定できなかった＝アウト寄り」に倒れます。** 今までの成人向け判定は、照合に失敗したら元の判定を維持する（＝結果的に見逃す方向）でした。新しい動画ラインだけは逆で、照合が失敗すると自動的に「ソフト成人向け」の違反ラベルが付きます。**通常の投稿の扱いは今日も変わっていません**が、動画ラインだけは厳しい側です。
- **年齢確認まわりの「対象国リスト」が、コードを直さなくても切り替えられるようになりました。** 生年月日を登録していない人に対して性的・過激なメディアを隠す国は、これまで16か国がコードに直書きでした。今日から設定ファイル側で差し替えられ、**30秒ごとに読み直され**ます（下記③）。今日時点の中身は従来の16か国と同一なので**見え方は変わりません**が、今後は「ある日から急に自分の国が対象に入る／外れる」ことが起こり得ます。生年月日未登録の方は、対象国に入ったときに一部メディアが見えなくなるので、登録しておくと表示が安定します。

## 変更点ごとの詳細

### 1. 閲覧者ID `0` を「ログアウト」として正規化【影響度：中（ログアウト／埋め込み閲覧に直撃）】

**メカニズム**

VF の gRPC エンドポイントに、リクエストの `viewer_id` を正規化する関数が新設された。

```rust
// visibility-filtering/filter_tweets.rs:114
fn normalize_viewer_id(raw: Option<u64>) -> Option<u64> {
    raw.filter(|&id| id as i64 > 0)
}
```

呼び出しはリクエスト受理直後（`filter_tweets.rs:36-37`）で、正規化後の値がそのまま下流の `FilterRequest.viewer_id` に渡る（同 `:75`）。`u64` を `i64` として解釈して 0 以下を弾くため、**`0` だけでなく最上位ビットの立った不正値（例：`u64::MAX`）も落ちる**（テスト `filter_tweets.rs:186-190` が両方をピン留め）。

これがなぜ効くのか。VF のルール群は「ログアウトかどうか」を `viewer_id` の有無だけで判断している（`visibility-filtering/rules/context.rs` の `ViewerPredicates::is_logged_out()`）。従来 `viewer_id = Some(0)` が届くと **ログイン済みの利用者ID 0 番**として扱われ、

- `SensitiveViewerLoggedOutDropRule`（`nsfw_age_gating.rs:36`）が発火しない → 性的・過激メディアがログアウト閲覧者に素通り
- `ViewerBlocksAuthorRule` / `ViewerMutesAuthorRule` / `MutedRetweetsRule`（`socialgraph_rules.rs:13,31,49`）が早期 Allow を返さず、ソーシャルグラフ照会に進む
- `ProtectedAuthorDropRule`（`user_rules.rs:74`）の「ログアウトなら鍵アカを落とす」分岐に入らない
- Gizmoduck（利用者情報）への RPC が無駄に飛ぶ（新テスト `filter_tweets.rs:179-183` が「viewer_id=0 の Gizmoduck 呼び出し回数はログアウト時と同数」を保証）

という状態になっていた。今日からこれが全て正しくログアウト経路に乗る。

観測用カウンタも同時に新設され、「ログアウト扱いになった件数」と「そのうち生の値が入っていた（＝正規化で落とした）件数」が別々に取れる（`rules/metrics.rs:15-25`）。**正規化で落ちた件数をわざわざ別カウンタにしている**ことから、実トラフィックに `viewer_id = 0` が相当数流れていた可能性が高い（実数は要確認）。

**X ユーザー／クリエイターへの影響**

- **閲覧者側（ログアウト・未ログインの埋め込み表示・シェアリンク経由）**：これまで見えていた NSFW / GORE 系メディアが**閲覧注意やドロップに変わる**。厳しくなる方向。
- **クリエイター側**：ログアウト閲覧者への露出が減る。センシティブ寄りのメディアを投稿している場合、外部埋め込みやログアウト流入からのインプレッションが目減りし得る。
- **鍵アカウント**：ログアウト閲覧者に対して確実にドロップされるようになる（プライバシー面ではプラス）。
- 影響を受けるのは「クライアントが `viewer_id` に 0 を送っていた経路」に限られる。ログイン済みの通常利用では**何も変わらない**。

### 2. grox「特殊動画」安全性フロー新設 ＋ モーションリビール【影響度：大（ただし既定オフ）】

**メカニズム**

新しいプラン `safety_ptos_special_video` が丸ごと1本追加された（`grox/flows/ptos/plan_safety_ptos_special_video.py`、新規55行）。専用の Kafka トピック `safety-ptos-special-video` から投稿を取り込む生成器も登録済み（`grox/flows/ptos/generators.py:97-102`、`constants.py:27-28`）。

処理の並びは次の通り（`plan_safety_ptos_special_video.py:38-55` の `TASK_DEPENDENCIES`）:

```
特殊動画フィルタ → レート制限 → メディア水和 → 特殊動画スクリーン
  → カテゴリ検知 → ポリシー検知 → SafeModel性的・ヌード判定
  → 成人向けクロスバリデーション → 安全性ラベル書き出し
```

**入口の条件**（`task_safety_ptos_special_video_filter.py:27-41`）：

- 投稿主が存在すること
- 本投稿または**引用元投稿**に動画が含まれること
- **いいね数 ≥ `deluxe_fav_count_threshold`（既定 64）**（`grox/config/config.py:114`）

**モーションリビールの中身**（`grox/libs/video_tools/image.py:211-279`、新規125行）：

1. フレームを最大32枚に間引き、最大640pxへ縮小
2. 全フレームの**中央値画像**を「静止レイヤー（覆い）」とみなす
3. `frame - 0.7 × median` を計算して覆いを差し引き（`image.py:161,249`）、2〜98パーセンタイルでコントラストを引き伸ばす
4. 残差の p99 中央値が **3.0〜75.0 の範囲外なら打ち切り**（`image.py:165-166,240-244`）＝ほぼ静止／ほぼ全面動きの動画は対象外
5. 各リビール画像の**肌色面積率**（YCrCb 空間の閾値マスク、`image.py:199-208`）を計算し、`動きエネルギー × (0.5 + 肌色率)` の降順で並べ替え
6. 上位1枚を「原フレーム｜リビール」の左右並置で、同じ1枚を単独で、上位4枚を2×2グリッドで——計3枚をJPEG化

さらに、元の抽出フレームが12枚未満の短い動画では、**リビール専用に16点で再サンプリング**して精度を上げる（`grox/libs/video_tools/video_frames.py:23,87-104`）。

生成された画像は LLM への入力に、専用の説明文を添えて渡される（`grox/core/lm/convo.py:23-28`）：

> "Motion-reveal stills for this video follow (static layer subtracted, faint moving layers amplified); they distort colors and motion, and can make opaque clothing look like bare skin. People or acts absent from the frames above but visible here are the video's actual overlay-hidden content; judge anyone already visible above solely from the original frames."

（訳：静止レイヤーを差し引き、薄い動きレイヤーを増幅した静止画が続く。色と動きは歪み、不透明な衣服が素肌のように見えることがある。**上の通常フレームには写っていないのにここには写っている人物や行為が、この動画の本当の「覆いで隠された中身」である**。既に通常フレームに写っている対象は通常フレームだけで判断せよ。）

つまりこれは、**「静止画のような覆いの下に、本編を薄く重ねて動かす」タイプの回避テクニック**を名指しで狙い撃つ機能である。プロンプト自体が誤検知（衣服が素肌に見える）を明示的に警告している点も、通常フレーム優先の帰属ルールも、過検知を抑える設計になっている。

**スクリーン段の挙動**（`task_special_video_screen.py:20-49`）：水和済み動画が1本もなければ `no_hydrated_video` としてスキップ、**モーションリビール画像が1枚も生成されなかった場合も `return bool(hits)` が `False`** となりフローはそこで止まる。

**既定オフの根拠**：`enable_motion_reveal` の既定値は `False`（`grox/config/config.py:113`）。有効化されるのは「設定オン **かつ** 本投稿 **かつ** いいね64件以上」の3条件が揃ったときのみ（`grox/core/data_loaders/media_loader.py:230-234`）。既定のままではリビール画像が空 → スクリーンが常に `False` → **フロー全体が不発**。デプロイ側の実設定値はリポジトリ外のため**要確認**。

**X ユーザー／クリエイターへの影響**

- **狙われる層**：動画に静止画の覆いを重ねる／薄く合成する等の手法で成人向け・過激コンテンツの自動判定を回避してきたアカウント。いいね64件以上に達した時点で審査対象に入るため、**伸びた投稿ほど先に捕まる**。
- **一般の動画投稿者**：肌色率で優先度が上がる仕組みのため、水着・スポーツ・医療系など肌の露出が多い正当な動画は**リビール画像が生成されやすい**。ただし生成＝違反ではなく、その後にカテゴリ検知→ポリシー検知→SafeModel→クロスバリデーションの4段が入る。プロンプトも誤検知を警告している。とはいえ**審査に回る回数自体は増える**方向。
- **今日の時点では何も起きない**（既定オフ）。ただし配線は末端まで完了しており、設定1つで全面稼働できる状態。

### 3. 成人向けクロスバリデーションの初のフェイルクローズ経路【影響度：中（新フロー限定）】

**メカニズム**

Grok 4.5 によるクロスバリデーションが**例外で失敗したとき**の振る舞いが、タスク種別によって分岐するようになった。

```python
# grox/flows/ptos/task_safety_ptos_adult_content_cross_validation.py:105-118
except Exception as e:
    Metrics.counter(metric).add(1, attributes={"outcome": "error"})
    if ctx.payload.task_type == SAFETY_PTOS_SPECIAL_VIDEO:
        logger.warning(f"... failing closed to Soft: {e}")
        cls._apply_soft_verdict(ctx, _CROSS_VALIDATION_FAILED_REASON)
    else:
        logger.warning(f"... keeping original decision: {e}")
    return
```

判定を書き込む処理は `_apply_soft_verdict()` として括り出され（同 `:130-148`）、既存の「4.5 が Hard に同意しなかった → Soft に格下げ」経路（`:127`）と、新しい「照合そのものが失敗 → Soft を付与」経路（`:112`）が同じコードを共有する。理由文字列だけが `"Grok 4.5 Cross Validation disagreed"` と `"Grok 4.5 Cross Validation failed"` で区別される。

`_apply_soft_verdict` は、既存の成人向け違反があればそれを Soft へ書き換え、**なければ新規に違反を1件作って追加**する（`:133-146`）。つまり特殊動画フローでは、**元の判定がクリーンでも照合失敗だけで違反ラベルが付く**。

あわせて「デラックス扱い」の判定が単一値比較から集合所属へ広がり（`constants.py:29` の `DELUXE_TIER_TASK_TYPES`）、特殊動画フローは `SafetyPtosMode.DELUXE`（`mode.py:15`）、SafeModel の無条件実行（`task_safety_ptos_safemodel_sex_nudity.py:62`）、デラックス専用の重複排除キャッシュ（`task_rate_limit.py:18`）を自動的に引き継ぐ。

**X ユーザー／クリエイターへの影響**

- 8/25 のレポートで「全経路が緩和方向のみでフェイルオープン」と整理した状況に対する、**初めての逆方向の変更**。ただし適用範囲は特殊動画フローに限定され、**通常の投稿の扱いは今日も変わらない**。

- 実際に何%が失敗経路に落ちるかはモデル可用性次第で、リポジトリからは判断できない（**要確認**）。

### 6. VF 結果マージ順の反転（重複IDで「フォロー内」判定が優先）【影響度：小】

**メカニズム**

home-mixer は候補を「フォロー内（`TimelineHome`）」と「ネットワーク外（`TimelineHomeRecommendations`）」の2グループに分けて VF に問い合わせ、結果を1つのマップに畳み込む。この畳み込み順が反転した。

```rust
// OLD: home-mixer/candidate_hydrators/vf_candidate_hydrator.rs
all_results.extend(in_network_result);
all_results.extend(oon_result);          // ← 衝突時は OON（厳しい側）が勝つ

// NEW: home-mixer/candidate_hydrators/vf_candidate_hydrator.rs:107-112
all_results.extend(
    oon_result
        .into_iter()
        .chain(in_network_result)        // ← 衝突時は in-network（緩い側）が勝つ
        .map(|(id, r)| (id, r.map(|t| t.reason))),
);
```

同一の投稿IDが両グループに現れるのは、たとえば「A さんの投稿がフォロー内候補として入り、同時に別候補の引用元／祖先として OON 側にも積まれる」ケース（`vf_candidate_hydrator.rs:69-81` が `ancestors` と `quoted_tweet_id` を OON 側へ、`retweeted_tweet_id` を in-network 側へ入れる）。

`TimelineHomeRecommendations` は `TimelineHome` の全ルールに OON 専用ドロップを上乗せした厳しい方のポリシー（`visibility-filtering/rules/registry.rs:151-161`）。したがってこの反転は、**重複IDについて判定が緩む方向**。

8/19 に報告した「フォロー中タブ専用ハイドレータで祖先／引用元の安全性レベルが `TimelineHomeRecommendations` → `TimelineHome` へ緩和」と**同じ方向の変更**であり、方針として一貫している。

**X ユーザー／クリエイターへの影響**

- フォロー中のアカウントの投稿が、たまたま他候補の引用元／祖先としても候補に入っていた場合、これまで OON 基準で落ちていたものが**表示される**ようになる。
- 発生条件が限定的なので体感差は小さい。「フォローしている相手の投稿は、フォローしている基準で判定する」という一貫性の改善と読むのが妥当。

### 7. Phoenix に「ページ生成デコード」の proto を宣言【影響度：中（準備段階・配線ゼロ）】

```protobuf
message PredictNextActionsRequest {
  ...

message PageDecodeParams {

  float temperature = 3;  // サンプリング温度

  repeated float pickedProbs = 2;
  repeated float pickedScores = 3;

```

結果は候補分布セットに載り（`recsys.proto:222`）、スロット単位の確率が `ScoreInfo.pageDecodeSlotProb`（同 `:1221`）に返る。Python 側 proto も同一内容で追従。

**これは「独立にスコアを付けて上位K件を並べる」従来方式とは質的に異なる仕組み**である。`temperature` と `pickedProbs` があることから、候補プール `poolN` からスロットを **1枠ずつ確率的にサンプリングして1ページ分を組み立てる**——文章生成と同じ逐次デコードをタイムライン構成に持ち込む設計と読める。

ただし**配線は一切ない**。リポジトリ全体で `pageDecode` に触れるのは2つの proto と `home-mixer/models/candidate.rs:213` だけで、そこも `page_decode_slot_prob: None` の固定値。8/29 の `RerankerHeadTag`、8/27 の広告ピクセル発火ヘッドと同じ「proto 先行宣言」パターン。

**X ユーザー／クリエイターへの影響**

- **今日は何も起きない**。
- 将来これが稼働すると、タイムラインは「点数の高い順」ではなく「1ページとしての組み合わせの良さ」で決まり、しかも**温度付きサンプリングのため同じ入力でも毎回並びが変わり得る**。多様性は増えるが、「良い投稿を出せば必ず上位に来る」という前提は弱まる。伸び方の分散が広がる方向。
- 現時点ではパラメータの既定値も、実際に使われるかも不明（**要確認**）。
