## 1. 非IT精通者向け:今日から意識するとよいこと

- **ブラジルの選挙候補者・関係アカウント(665件)の投稿は、「おすすめ(For You)」に出なくなりました。** ただし**自分がそのアカウントをフォローしていれば、これまで通り表示されます**。ブラジル政治の情報を追いたい人は、当該アカウントを**明示的にフォローする**のが唯一の対処法です。
- この除外は**リポスト・引用・返信の連鎖にも波及**します。対象アカウントの投稿をリポスト/引用した投稿や、対象アカウントが会話の上流にいる返信も、おすすめから消えます。
- **地域判定のコードが見当たらないため、ブラジル在住者だけでなく全世界のユーザーのおすすめに適用されている可能性が高い**です(要確認)。
- **「通報(Report)を大量に受けるとリーチが壊滅する」「1件の通報がいいね468件を打ち消す」は誤りである**と、X社が公式にコード内コメントとREADMEで明記しました。重みは「あなた個人がその行動を取る確率の予測値」に掛かるもので、生の件数には掛かりません。**組織的な通報・ブロックによる攻撃を過度に恐れる必要はありません**(ただし通報が完全に無意味という意味でもありません)。
- **フォロワー1.5万〜3万人規模のアカウント**が絡む返信欄は、AIによる自動リプライスパム検知・返信ランキングの**対象から外れました**。返信欄の荒れ方が変わる(自動整理されにくくなる)可能性があります。
- **14日より古い投稿**について、AIモデルに渡すいいね数・返信数などを**ゼロ扱いにする仕組み**が追加されました(現時点では既定オフ)。有効化されれば、古い人気投稿が「数字の力」で掘り起こされることは減ります。

## 2. 変更サマリ

- **ブラジル2026年選挙フィルタ `Brazil2026ElectionFilter` が For You 本流パイプラインに新規投入**された。ブラジル選挙裁判所に届け出られた 665 アカウントの投稿を、フォローしていない視聴者のおすすめから除外する。
- **ランキング重み(`ScoringWeights`)の数値は一切変更なし。** 代わりに「重みは予測確率に掛かるもので生の件数ではない」という**誤解を正す説明コメント**が `param.rs` / `ranking_scorer.rs` / README に追加された。
- **著者コールドスタートに Thompson Sampling(ベータ分布による確率的選択)が実装**された。既定は**オフ**。あわせて特定ID群の配信状況を計測する運用メトリクスが追加。

- **Phoenix 推論エンジンに「古い投稿(14日超)のエンゲージメント数値をゼロ化」する機能(既定オフ)**と、**視聴者⇔著者のフォロー関係を表す真偽値特徴量2種**が追加された。

### 3.1 ブラジル2026年選挙フィルタの新設 — 影響度: **大**

**メカニズム**:
- 新規ファイル `home-mixer/filters/brazil_2026_election_filter.rs:1-1573`。ブラジル選挙裁判所(TSE)に届け出られたアカウントの **user_id 665件** を `LazyLock<FxHashSet<u64>>` としてハードコードで保持(`brazil_2026_election_filter.rs:20-22`、件数はテスト `hardcoded_list_is_non_empty` で 665 と固定検証)。コード内では ID の横に `// @renildo`、`// @cirogomes`、`// @ManuelaDavila` 等のユーザー名がコメントとして併記され、透明性が確保されている。
- 除外判定 `is_excluded_author`(`brazil_2026_election_filter.rs:1359-1361`):
  ```rust
  BRAZIL_2026_ELECTION_USER_IDS.contains(&user_id) && !followed_user_ids.contains(&user_id)
  ```
  → **リスト該当 かつ 視聴者がフォローしていない**場合のみ除外。フォロー済みなら除外されない。
- 除外の波及範囲 `should_remove`(`brazil_2026_election_filter.rs:1363-1378`):投稿者本人(`author_id`)に加え、**リポスト元(`retweeted_user_id`)・引用元(`quoted_user_id`)・返信スレッドの祖先(`ancestor_users`)** のいずれかが該当すれば、その候補投稿ごと落とす。
- 適用箇所 `home-mixer/candidate_pipeline/phoenix_candidate_pipeline.rs:359-366`。For You(Phoenix)候補パイプラインの filters 配列に、`AuthorSocialgraphFilter` の直後・`VideoFilter` の直前で登録。**視聴者の国・地域を判定する条件は filter 実装・登録箇所のいずれにも存在しない。**
- 法的根拠はコード内コメントに明記:「レコメンドシステムを用いるアプリケーション提供者は、選挙裁判所に届け出られたチャンネル・プロフィール、および(有料ブースト時を除き)そこへの投稿を結果から除外しなければならない」。データ出典は TSE のオープンデータ(`dadosabertos.tse.jus.br/dataset/candidatos-2026`)。
- README(`README.md:34`)でも X 社公式アナウンスとして告知されている。

**Xユーザー/クリエイターへの影響**:
- **対象665アカウントのオーガニックリーチが、フォロワー以外に対して事実上ゼロになる**(For You 経由分)。ブラジルの選挙候補者・現職議員の情報発信は、既存フォロワーとフォロー/検索/プロフィール直接訪問等の経路に限定される。
- **フォローが唯一の解除手段**。ブラジル政治の情報を追いたい一般ユーザーは、能動的にフォローしない限りおすすめ欄で当該情報に接触しなくなる。これは「アルゴリズムによる偶発的接触」の消滅を意味し、政治情報の流通経路が「既にフォローしている人だけ」に狭まる。
- **一般クリエイターへの巻き込み影響**:対象アカウントを**リポスト・引用した第三者の投稿も落ちる**。ブラジル政治を論評するジャーナリスト・解説アカウントは、引用対象を選ぶだけでその投稿のおすすめ配信を失う。返信スレッドも祖先に対象者がいれば落ちるため、**候補者の投稿への返信で伸ばす**という戦術は成立しなくなる。
- **地理的スコープ**:コード上に地域判定がないため、日本を含む全世界のユーザーの For You に適用されていると読める。ブラジル国外のユーザーにとっても、ブラジル選挙関連の候補者投稿はおすすめに出ない(**要確認** — 上流のリクエスト単位で地域別にパイプラインが分岐している可能性は排除できない)。
- **広告(有料ブースト)は対象外**:このフィルタはオーガニック候補パイプラインにのみ登録されており、`home-mixer/ads/` 系の広告挿入経路には入っていない。法文の「有料ブースト時を除き」という但し書きと整合する。つまり**同じアカウントでも、広告費を払えば表示され得る**構造になっている。
- リストがコードにハードコードされているため、**候補者の追加・削除にはコード変更とデプロイが必要**。選挙期間中の届出変更への追随速度は不明(要確認)。

### 3.2 ランキング重みに関する「誤解訂正」コメントの追加 — 影響度: **小(挙動変更なし)/ 情報価値は大**

**メカニズム**:
- `home-mixer/params/param.rs:282-306` および `home-mixer/scorers/ranking_scorer.rs:418-445` に、同一内容の説明コメントが追加された。**重み定数の値・`apply()` の計算式・スコアリングロジックは1行も変わっていない**(差分は全てコメント行)。
- コメントの主張(コードで裏付けの取れる範囲):
  1. 各重みは**予測確率**(P(favorite), P(repost) …)または連続値(視聴時間等)に掛かる。`ranking_scorer.rs:446-448` の `fn apply(score: Option<f64>, weight: f64) -> f64 { score.unwrap_or(0.0) * weight }` がその通りの実装であることは確認できる。
  2. 「通報の重みがいいねの468倍だから、通報1件がいいね468件を打ち消す」という読み方は誤り。重みは生の件数に掛からないため。
  3. Report の基底確率は Like より 1000倍以上低いため、予測がランキングに影響できるよう重みを大きくしてある。
  4. 大量ブロック/通報による攻撃が効きにくい理由として、(a) 推薦はパーソナライズされており、悪意ある行為者による通報は主に**その行為者と類似したユーザー**の推薦に影響する、(b) **ホームタイムラインで配信された投稿上での行動しかランキングに算入されない**ため、グループチャット等でURLを共有して直接投稿へ飛んで通報しても影響しない、と説明されている。
- README(`README.md:343`)にも同趣旨の段落が追加。

**Xユーザー/クリエイターへの影響**:
- **フィードの挙動は今日時点で何も変わっていない。** 変わったのは「公開情報としての説明」のみ。
- ただし実務上の意味は大きい:8/14 レポートで扱った公開重み値をもとに広まった「1通報 = いいね468件の打ち消し」式の解釈を、X社が**明示的に否定**した。組織的な通報・ブロックキャンペーンを過度に恐れて発信を自粛する必要性は、少なくともX社の説明上は低い。
- 上記 (b) の説明が正しければ、**「グループチャットで投稿URLを配って一斉通報」という手口はランキングに作用しない**。逆に言えば、自分の投稿がタイムラインで配信された相手からの反応こそが効く、という構造の再確認になる。
- なお「効かない」の主張は**ランキング(推薦順位)についてのもの**であり、通報が安全性ポリシーによる可視性制限・アカウント処分の判断材料になる経路(`abuse-enforcement-service` 等)を否定するものではない点に注意(要確認 — 本コメントはランキング経路のみを論じている)。

### 3.3 著者コールドスタートへの Thompson Sampling 導入 — 影響度: **中(既定オフのため潜在)**

**メカニズム**:
- 新規パラメータ群(`home-mixer/params/param.rs:690-724`):
  | パラメータ | 既定値 | 意味 |
  |---|---|---|
  | `EnableColdStartThompsonSampling` | **false** | TS 方式の ON/OFF |
  | `ColdStartBetaAlpha0` | 0.75 | ベータ事前分布 α₀ |
  | `ColdStartBetaBeta0` | 49.25 | ベータ事前分布 β₀ |
  | `ColdStartTsTopK` | 5 | サンプリング上位K件 |
  | `ColdStartImpressionScale` | 1.0 | 表示回数のスケール係数 |
  | `ColdStartTrackedIds` | ""(空) | 計測対象IDのCSV |
- 従来のコールドスタート枠の選び方(`author_cold_start.rs:284`)は「対象候補のうち**スコア最大の1件**を昇格」(`pick_by_score`)。TS を有効にすると `pick_thompson`(`author_cold_start.rs:216-241`)に切り替わる:
  1. 各候補について `sample_reward`(`author_cold_start.rs:212`)で **Beta(α₀ + fav_count, β₀ + (scale×view_count − fav_count))** から報酬を1回サンプリング。要は「いいね率の事後分布からのくじ引き」。
  2. サンプル値の降順に並べ、**上位K件(既定5件)**に絞る。
  3. その K 件の中から、**通常のランキングスコアが最大**のものを昇格枠に選ぶ。
  - `top_k == 0` または α₀/β₀ が非正の場合は `pick_by_score` にフォールバック(`author_cold_start.rs:228-230`)。
- 事前分布 α₀=0.75, β₀=49.25 は合計50、事前平均いいね率 1.5%。表示回数が少ない新規投稿ほど事前分布に引っ張られ、サンプルのばらつきが大きくなる = **探索が効く**設計。
- 別途、`record_tracked_ids`(`author_cold_start.rs:114-133`)が `ColdStartTrackedIds` に列挙された tweet_id / author_id について、`served_type`(候補の供給元)別の出現数を `home_mixer.cold_start_tracked_ids_total` メトリクスに計上する。コールドスタート判定より前・無条件に実行される(`author_cold_start.rs:323-324`)。

**Xユーザー/クリエイターへの影響**:
- **既定オフのため、現時点でフィードは変わらない**(本番の feature switch 設定値は不明 = 要確認)。
- 有効化された場合:これまでコールドスタート枠は「ランキングスコア最高の1件」に決定的に与えられていたため、**同じ傾向の投稿が繰り返し枠を取る**構造だった。TS が入ると、**初期のいいね率が良い投稿にくじ引き的なチャンス**が回り、スコアでは2〜5位でも枠を取り得る。無名アカウントの投稿が最初の露出を得る確率が上がる方向。
- ただし最終選択は「上位K件の中でランキングスコア最大」なので、**完全なランダム化ではなく「候補プールをくじ引きで絞ってから実力で選ぶ」2段構え**。極端に低品質な投稿が押し上げられる設計ではない。
- 「初期表示に対するいいねの付き方」がくじ引きの当たりやすさを左右するため、**投稿直後の数分〜数十分の反応**の重要性が(有効化されれば)さらに上がる。
- `ColdStartTrackedIds` は特定の投稿/アカウントの配信経路をピンポイント計測する運用機能。ランキングには影響しない(カウントのみ)が、**個別アカウントの挙動を名指しで監視できる仕組みが実装されている**ことは事実として記録しておく。

### 3.4 grox 返信スパム検知・返信ランキングの発動閾値の引き上げ(15,000 → 30,000)— 影響度: **中〜大**

**メカニズム**:
- `grox/flows/reply_spam/task_filter.py:17`:`TaskSpamFilter.FOLLOWER_COUNT_THRESHOLD_FOR_SPAM_DETECTION` が 15000 → **30000**。
- `grox/flows/reply_spam/task_filter.py:185`:`TaskReplyRankingFilter.FOLLOWER_COUNT_THRESHOLD_FOR_REPLY_RANKING` が 15000 → **30000**。
- 返信ランキング側の判定ロジック(`task_filter.py:214-224`):
  ```python
  if (in_reply_user_follower_count <= THRESHOLD
      and root_user_follower_count <= THRESHOLD):
      # skip, reason="low_blast_radius"
      return False
  ```
  → **返信先の投稿者と、スレッド根元の投稿者の両方が閾値以下なら、その会話は返信ランキングの対象外**。閾値を 3万に上げたことで、**対象となる会話が減る**。
- スパム検知側も同じ閾値定数を用いて会話規模で振り分けている(前回レポート 2.2 参照)。

**Xユーザー/クリエイターへの影響**:
- **フォロワー1.5万〜3万人規模のアカウント**の投稿の返信欄が、**AI による自動返信ランキング(品質による並べ替え)の対象から外れた**。この層のクリエイターにとっては:
  - 返信欄が品質順に整理されなくなり、**低品質な返信が上位に残りやすくなる**可能性がある。
  - 逆に、丁寧な返信を書いても「AI による品質評価で上位に押し上げてもらう」恩恵は受けられなくなる。この層の投稿に返信して露出を狙う戦術の効きが変わる。
- **返信スパム検知の対象範囲も同時に変わる**(こちらは会話規模による振り分けなので、どちらの方向に働くかは grox 側の分岐実装に依存 = 要確認)。
- 変更の動機はコード上に記載がないが、閾値を倍にする = **LLM 呼び出し対象の会話数を絞る**方向であり、計算コスト削減または誤判定削減が背景にある可能性がある(要確認)。
- **フォロワー3万人超のアカウント**の会話は従来通り対象。この層の返信欄の挙動は変わらない。

### 3.6 Phoenix:古い投稿のエンゲージメント数値ゼロ化 + フォロー関係の特徴量追加 — 影響度: **中(既定オフ)**

**メカニズム**:
- **stale post(古い投稿)の扱い**:
  - `HashTableConfig` に `enable_stale_post: bool` フィールドが追加(`phoenix/crates/common/xai-recsys/src/model_config.rs:40`)。Python 側の既定値は **`False`**(`phoenix/crates/serving/xai-recsys-engine/src/python.rs:3171`、`xai_recsys_engine.pyi:214`)。
  - `phoenix/crates/common/xai-recsys/src/util.rs:474-500`:候補投稿の作成時刻から `STALE_POST_14D_TTL_SEC`(名称から14日 = 1,209,600秒と推定、定数定義ファイル `feature_config/constants.rs` は本公開リポジトリに含まれず値は**要確認**)を超えて経過していれば `is_stale = true` とし、**その候補の fav / reply / retweet / quote / view の全カウントを 0 として推論モデルに渡す**。
  - あわせて `IS_STALE_POST14D` という真偽値特徴量として「これは古い投稿である」旨をモデルに明示(`util.rs:537-542`)。
- **フォロー関係の真偽値特徴量2種**:
  - `IS_AUTHOR_FOLLOWED_BY_VIEWER_SEQ`(視聴者が著者をフォローしている)と `IS_AUTHOR_FOLLOWING_VIEWER_SEQ`(著者が視聴者をフォローしている)を、**候補側**(`util.rs:543-554`)と**履歴側**(`util.rs:898-910`)の双方でモデル入力に詰めるようになった。
  - 従来これらのスロットは `vec![false; ...]` で**全てゼロ埋めされていた**(`util.rs:563`・`util.rs:972` の変更前)。つまり**モデルにフォロー関係が渡っていなかったものが、今回渡るようになった**。
- **Sid リトリーバルの新ウィンドウ**:`phoenix-rankall/src/config/mod.rs:180` に `WindowConfig::new("video", 24 * 14)` = **video_14day** ウィンドウを追加(既存は video 48h / 96h)。NSFW 動画には既に 14日窓が存在したが、通常動画にも追加された形。
- `phoenix/crates/serving/xai-recsys-proto/src/lib.rs:15` に `SAFETY_BIT_AUTHOR_NSFW: u64 = 1 << 2` 定数を追加(利用箇所は本コミットの差分内には無い)。

**Xユーザー/クリエイターへの影響**:
- **stale post ゼロ化(有効化された場合)**:14日より古い投稿は「いいね10万件」でもモデルからは「いいね0件」に見える。**古い人気投稿が、蓄積したエンゲージメント数値の力でおすすめに再浮上することがなくなる**。「バズった過去投稿の掘り起こし」「古い投稿へのリポストによる再燃」が起きにくくなる方向。フィードの鮮度は上がるが、**エバーグリーンな良質コンテンツ(解説・チュートリアル等)には不利**。ただし既定オフのため現時点では未適用(本番設定は要確認)。
- **フォロー関係特徴量**:モデルが「この候補の著者を、あなたはフォローしているか / 著者はあなたをフォローしているか」を初めて直接学習・利用できるようになった。特に**相互フォロー(双方向)の関係性**をモデルが識別できるようになるため、8/14 で追加された `bidirectional_follow_*_weight_boost`(ヒューリスティックな相互フォロー加点)と合わせ、**相互フォロー関係のコミュニティ内投稿がフィードで優遇される流れが、ヒューリスティックと学習モデルの両面で強化**される。
- **video_14day ウィンドウ**:Sid ベースのリトリーバルが、視聴者の**過去14日分の動画視聴傾向**を参照できるようになった。従来は最大96時間(4日)。動画クリエイターにとっては、**1〜2週間前に自分の動画を見たユーザーに再到達する経路が広がる**ことを意味する。逆に視聴者側から見ると、動画の推薦がより長期の視聴履歴に基づくものになり、**一度見たジャンルからの脱出がやや難しくなる**可能性がある。

## 5. 不確実な点(要確認)

1. **Brazil2026ElectionFilter の地理的スコープ**:filter 実装・パイプライン登録箇所のいずれにも視聴者の国・地域を判定するコードが無い。上流のリクエストルーティングで地域別にパイプラインが分岐している可能性は本リポジトリからは判定できない。**全世界適用と読めるが確定はできない**。
2. **`STALE_POST_14D_TTL_SEC` の実値**:定数を定義する `phoenix/crates/common/xai-recsys/src/feature_config/constants.rs` は本公開リポジトリに含まれていない。名称から14日(1,209,600秒)と推定されるが未確認。同様に `IS_STALE_POST14D` 等の bool 特徴量インデックスの定義も非公開。
3. **feature switch の本番設定値**:`EnableColdStartThompsonSampling`、`enable_stale_post`、`ColdStartTrackedIds` はいずれもコード上の既定値(false / false / 空)であり、本番の feature switch サーバ側で上書きされている可能性がある。実際に有効かはコードから判定不能。
4. **grox 閾値引き上げの動機と、スパム検知側の方向性**:返信ランキング側は「対象が狭まる」と確定できるが、スパム検知側(`TaskSpamFilter`)の会話規模による振り分けが、閾値引き上げでどちら向きに作用するかは grox 内部の分岐実装に依存し、本差分だけでは断定できない。
5. **フォロー関係特徴量の効果発現タイミング**:特徴量をモデル入力に詰める配管が追加されただけで、その特徴量を使うようモデルが再学習済みかどうかはコードから判定できない。学習側が未対応なら当面は挙動変化なし。
6. **通報の扱いに関する X 社の説明の検証範囲**:「大量通報はリーチを大きく下げない」という主張のうち、コードで裏付けが取れるのは「重みが予測確率に掛かる」点(`ranking_scorer.rs:446-448`)のみ。「ホームタイムラインで配信された投稿上の行動しか算入されない」という主張の実装上の裏付けは、本差分の範囲では確認できていない。
7. **enforcement_note が利用者に開示されるか**:BigQuery 行に記録されることは確認できるが、異議申立てフローでユーザーに提示されるかどうかはこのリポジトリの範囲外。
8. **Brazil リストの更新運用**:665件がソースコードにハードコードされているため、TSE への届出変更(追加・取り下げ)への追随はデプロイを要する。更新頻度・運用体制は不明。
