## 非IT精通者向け・運用方法のまとめ（行動指針）

> 今回は**1日分・実質61ファイル**の小〜中規模な回です。**ランキングの重み（点数の付け方）は一切変わっていません。** 投稿の作り方を今日変える必要はありません。
> ただし「既定で有効」な実挙動の変更が**2件**あり、どちらも**中小アカウントに弱い追い風**です。

- **① 【追い風・小〜中】コールドスタート・ブーストの「対象外ルール」が1つ撤廃されました（後述2）。**
  - X には「反応がまだ無い投稿を、For You の1枠だけ無理に上位へ持ち上げる」仕組み（コールドスタート・ブースト）があります。10月1日のレポートで「本番稼働した」とお伝えした機能です。
  - これまでは、**特定の取得経路（AI埋め込みによる類似検索＝MoE経路やコールド専用経路）で拾われてきた投稿は、このブーストの対象から外されていました**（一部の閲覧者グループにおいて）。今回**その除外が撤廃**され、**どの経路で拾われた投稿でも同じようにブースト対象になりました**（`home-mixer/scorers/author_cold_start.rs:203-207`）。
  - **行動指針：** 投稿者側でできることは変わりません（投稿直後2時間・フォロワー5万人以下・返信/リポスト以外、という条件は不変）。**「同じ条件なのに経路によって当たり外れがあった不公平が解消された」**と理解してください。**当たる確率がわずかに上がる方向**です。

- **② 【中立・情報としては重要】表示回数・いいね数などの「数字」が、画面を再読み込みしたときに全投稿で最新化されるようになりました（後述6）。**
  - これまでは、For You を再表示（キャッシュから再配信）したとき、**フォロワーが少ない著者の投稿だけ**いいね・リポスト・表示回数を取り直し、**それ以外は古い数字を使い回していました**。今回**全投稿で取り直す**ようになりました（`home-mixer/candidate_hydrators/engagement_counts_hydrator.rs:102-131`）。
  - **行動指針：** 投稿後に数字が伸びた場合、**その伸びがランキングに反映されるまでの遅れが短くなります**。「投稿から数時間後に急に伸び始めた投稿」が拾われやすくなる方向。**作り方を変える話ではありません。**

- **③ 【将来の大変化・今日は影響ゼロ】「SID retrieval」という新しい候補の探し方が実装されました（既定オフ、後述1）。**

## 変更サマリ

1. **新しい候補取得経路 `SidSource`（SID retrieval）を新設**（+358行、既定オフ）。閲覧者が反応した投稿を種に「意味ID」の共通接頭辞で類似投稿を引く方式。有効化時は既存の MoE 経路を停止する排他設計。
2. **コールドスタート・ブーストの「MoE/コールド経路の候補は Control アームでは対象外」という除外が撤廃**（既定で有効な実挙動変更）。
3. **可視性フィルタ：「リポストかどうか」の判定元が `TES get_tweets` から `TES get_tweet_core_datas`（PureCore）へ移管**。あわせて「リポスト非表示」設定の社会グラフ照会を**リポストのみに限定**（効率化）。
4. **推論 proto に列挙枠4件追加**：`LLM_JUDGE_RELEVANT_TO_SEARCH`(108) / `LLM_JUDGE_NOT_RELEVANT_TO_SEARCH`(109) の**復活**、広告コンバージョン金額の連続値2件、広告に「閲覧者×広告主」単位の履歴枠2件、取得要求に種投稿ID・既読ブルームフィルタ枠。
5. **公開ラベル説明に `BRAZIL_ELECTION_LEGAL` を追記**（選挙関連AI生成メディア／ブラジル国内でおすすめ除外）。
6. **キャッシュ再配信時のエンゲージメント数値の再取得を全候補に拡大**（従来は小規模著者の原投稿のみ）。
7. **著者ルール評価器 `AuthorRulesEvaluator`（156行）をこのリポジトリから削除し、非公開クレート `xai_feature_switches` へ移管**（透明性の後退）。
8. 残りは学習基盤（GPU埋め込みカーネル `row_emb` 新規約3,200行、Kafka 読み出しの再分配、チェックポイント暗号鍵クライアント）と計測ラベルの追加、および行末空白の一括除去。

## 変更点ごとの詳細

### 1. 新しい候補取得経路「SID retrieval」の新設（既定オフ／将来 MoE を置き換え）

**メカニズム（コード根拠）**

- 新規ファイル `home-mixer/sources/sid_source.rs`（112行）、`home-mixer/clients/sid_retrieval_client.rs`（246行）。パイプラインに組み込み済み（`home-mixer/candidate_pipeline/phoenix_candidate_pipeline.rs:326-338`）。
- 新パラメータ5件（`home-mixer/params/param.rs:604-633`）：

  | パラメータ | 既定値 | 意味 |
  |---|---|---|
  | `EnableSidSource` | **false** | 経路全体のオン/オフ |
  | `SidSourceMaxResults` | 800 | 1リクエストで取得する候補の上限 |
  | `SidSourceMaxSeeds` | 50 | 「種」にする投稿の最大数 |
  | `SidSourceMaxPerSeed` | 100 | 種1件あたりの候補上限 |
  | `SidSourceMinPrefixDepth` | 3 | 「意味ID」の先頭何段階まで一致を要求するか |

- **動作条件**（`sid_source.rs:58-64`）：トピック要求でない・フォロー内限定でない・キャッシュ再配信でない・**かつ閲覧者に投稿シグナル（反応履歴）がある**こと。
- **種の作り方**：`simclusters_source` の既存関数 `post_signal_ids()` を再利用（明示的エンゲージメント・暗黙的エンゲージメント・否定シグナル等をまとめた一覧）。先頭50件に切り詰める（`sid_source.rs:67-68`）。
- **返ってくる候補のスコア**：`shared_prefix_depth`（種の投稿と「意味ID」の先頭が何段階一致したか）をそのまま `retrieval_sources.score` に記録（`sid_source.rs:98`）。
- **served_type は既存の `ForYouPhoenixRetrievalMoe` を流用**（`sid_source.rs:94-96`）＝ MoE 経路と同じ札を付ける。
- **MoE 経路との排他**：`PhoenixMOESource::enable()` に `&& !sid_source_enabled(query)` が追加（`home-mixer/sources/phoenix_moe_source.rs:27`）。**SID を有効にすると MoE 経路は自動停止する。**
- 著者IDが解決できなかった候補は捨てる（`sid_source.rs:108`）。タイムアウトは **300ms**（`sid_retrieval_client.rs:23`）。
- 接続先は専用サービス `xai-recsys-sid-retrieval`（`sid_retrieval_client.rs:21-22`）。**サービス本体のコードはこのリポジトリに含まれていない。**

**X ユーザー／クリエイターへの影響**

- **現時点の影響はゼロ**（`EnableSidSource` 既定 false、`MockSidRetrievalClient` はテスト用に空応答）。
- **有効化された場合の性質**：
  - **「閲覧者が過去に反応した投稿と内容が近い投稿」が候補の主軸になります。** 現在の MoE（埋め込みベクトルの近傍検索）と目的は同じですが、**連続値ベクトルの距離ではなく「階層的なIDの接頭辞一致」という離散的な絞り方**に変わります。接頭辞3段階以上という条件は、**ベクトル近傍より「同じジャンルの塊」に寄る**方向に働くと読めます（**要確認**：「意味ID」の階層定義・各段階の粒度はこのリポジトリに含まれず、どの程度の絞り込みになるか定量評価できません）。
  - **クリエイター側の含意**：自分の投稿が「どの既存投稿の近縁として分類されるか」の比重が上がります。**内容の一貫性（同じテーマを継続して投稿する）が、経路上有利に働きやすい**構造です。逆に、ジャンルを頻繁に変えるアカウントは種との接頭辞一致を得にくくなる可能性があります。
  - **閲覧者側の含意**：**反応履歴が無い（または消した）閲覧者には、この経路が1件も動きません**（`sid_source.rs:63`）。新規アカウントの For You は従来どおり他経路（Thunder・SimClusters・コールドスタート枠）に依存します。
  - **候補上限 800件／シードあたり100件**は MoE 枠（200件）より大きく、**取得段での候補の幅は広がる**設計です。

### 2. コールドスタート・ブーストの「経路による除外」撤廃（既定で有効な実挙動変更）

**メカニズム（コード根拠）**

- 削除された関数 `is_arm_gated_retrieval()`：候補の `served_type` が `ForYouPhoenixRetrievalMoe` または `ForYouPhoenixRetrievalCold` かを判定していた。
- 変更前：`ViewerArm::Control` の閲覧者では `corpus == Control && !is_arm_gated_retrieval(c)` が条件。**＝MoE経路／コールド経路で拾われた候補はブースト対象外。**
- 変更後：`ViewerArm::Control => corpus == AuthorCorpus::Control` のみ（`home-mixer/scorers/author_cold_start.rs:203-207`）。**経路による除外が消えた。**
- 計測ラベル `is_moe` も削除（`author_cold_start.rs:107-115`）。テストも `cold_retrieval_keeps_its_score_in_every_arm` → `control_viewer_lifts_cold_retrieval_from_control_corpus` に差し替えられ、**「Control アームの閲覧者が、コールド経路由来の候補を持ち上げる」ことが期待される挙動として明示**されている。
- ブーストの他の条件（`cold_start_base_eligible`：返信でない・リポストでない・著者フォロワー数が上限以下、`author_cold_start.rs:163-170`）、鮮度条件、位置条件は**すべて不変**。

**X ユーザー／クリエイターへの影響**

- **フォロワー5万人以下の投稿者にとって、わずかな追い風です。** これまで「MoE経路／コールド専用経路で拾われた投稿は、Control アームの閲覧者に対してはブーストされない」という取りこぼしがあり、それが解消されました。
- 前回（10/1）レポートで報告したとおり、コールド専用枠は200件、MoE枠は通常0件・コールド200件に切り替わっています。**つまり「コールド経路で拾われた候補」は今の構成では主流**であり、**その主流経路がブースト対象から外れていた**という状態が是正された形です。**実効的には、今回の変更でブーストが初めてまともに機能する閲覧者層が増えると読めます。**
- **ただし「For You 1回の表示につき1件だけ」という上限は不変**です（`author_cold_start.rs:260-307`）。全体の露出量が増えるわけではなく、**誰がその1枠を取るかの公平性が改善した**変更です。
- **(要確認)** `PhoenixMoeCodivertViewerIsControl` / `...IsTreatment` はいずれも既定 false（＝全員 Holdout アーム）であり、**Control アームに実際どれだけの閲覧者が入っているかはX側の設定次第でコードからは分かりません**。Holdout アームでは従来から経路による除外はなかったため、**設定次第では今日の実効影響がゼロの可能性もあります。**

### 3. 可視性フィルタ：「リポストかどうか」の判定元データの移管

**メカニズム（コード根拠）**

- 述語 `IsRetweet` の読み出し元が変更：`IsRetweet reads Tweet => tweet.is_retweet()` → **`IsRetweet reads PureCore => source_tweet_id.is_some()`**（`visibility-filtering/rules/rule_spec.rs:662`）。
- `TweetFeatures` から `source_tweet_id` フィールドと `is_retweet()` メソッドを削除（`visibility-filtering/models/tweet.rs`）。`HydratedTweetCandidate` に `source_tweet_id` を追加（`visibility-filtering/models/mod.rs:59`）。
- `TES get_tweets` のデコーダから thrift フィールド7（`share`）の読み出しを削除（`visibility-filtering/hydration/tweet_source.rs:183`）。**＝リポスト情報はもう `get_tweets` から取らない。**
- 「リポスト非表示」設定（`MuteRetweets` エッジ）の照会キーが `PureCoreAuthor` → **`PureCoreRetweeter`** に変更（`visibility-filtering/hydration/plan.rs:200`）。`PureCoreRetweeter` は「**その投稿がリポストである場合に限り、その投稿の著者ID**」を返す（`visibility-filtering/hydration/store.rs:125-128`）。
- 効果は実行計画の期待値に明示：`mute_retweets-fwd[author]` → **`mute_retweets-fwd[retweeter]`**（`plan.rs:574, 582, 602`）。新テスト `only_retweeters_are_asked_for_the_mute_retweets_edge` が、**原投稿のみのバッチでは `MuteRetweets` 照会が1件も発行されない**ことを確認している（`visibility-filtering/hydration/execute.rs:682-724`）。
- 新テスト `pure_core_alone_says_a_post_is_a_retweet`：**`TES get_tweets` が失敗しても、PureCore だけで「リポストである」と判定でき、`viewer_mutes_retweets` が正しく適用される**（`visibility-filtering/filter.rs:356-399`）。
- 新テスト `without_a_pure_core_answer_a_post_reads_as_an_original`：**PureCore が失敗した場合は「原投稿」として扱われる**（`visibility-filtering/filter.rs:401-446`）。
