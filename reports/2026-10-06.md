## 変更サマリ

1. **可視性判定の種類が3種→4種に拡張。「NOTICE（注意書き付き表示）」を新設**し、FOSNRレベル1（暴言・侮辱）ラベル付き投稿を**フォロワーに注意書き付きで表示**するルールを追加（**実挙動変更・既定で有効**）。自動再生停止＋エンゲージメント誘導オフ。
2. **予測ヘッド 25 → 28。** `active_secs_5m_residual_norm` を廃止し、`video_continuation` / `user_video_continuation` / `profile_visit_secs` を新設。いずれも**「開く確率 × 開いた後の秒数」の積**で評価。**既定重みは3つとも `0.0`**。
3. **`post_unexplored`（新規投稿の後押し）をフォロー外にも適用できるスイッチを新設**（既定オフ）。
4. **`PopularPostsSource` を全面再設計**（既定オフのまま）。配信時の実時間取得 → 5分ごとのバッチ生成に変更。選定基準をフォロワー数 → **閲覧数を経過時間で割り戻した品質スコア（半減期8時間・24時間窓）**に変更。著者リストは手動CSV → **BigQueryから「直近7日のアクティブ投稿者の上位0.005%」を自動取得**。上限 500件／著者5件。
5. **可視性フィルタに新ルール3件**：コミュニティ内で非表示化された投稿のドロップ、コミュニティから著者が除名された投稿のドロップ（いずれも本人とモデレーターは例外）、未公開の記事（Article）のドロップ。
6. **トラステッドフレンズ投稿のルールを修正**：リストのメンバー／所有者には見えるよう条件を追加。Explore／没入型推薦にも同ルールを適用。
7. **`Under the Hood` 機能を新設**（既定オフ）：パイプライン各段の候補数・除外率・GitHubコードURL・全予測ヘッドのスコアをクライアントに返す。
8. **ルックアップ失敗時の扱いを整理**。判定結果を `Complete`（確定）/ `Partial`（一部データ欠損）/ `NotFound`（投稿が存在しない）/ `Failed`（取得失敗）の4状態に分離。**削除済み投稿は明確なドロップ、取得失敗は呼び出し元にエラーを返す**（従来は両者が混ざっていた）。
9. フォロー中（逆時系列）タイムラインにも広告ブランドセーフティの著者フォールバックを配線（既定オフ）。
10. 返信のメタデータも学習パイプラインに送出開始（`isReply` フラグ付き）。
11. 候補のKafkaログ上限 200 → 100,000。`VMRankerClusterId` が `Experiment6` → `Experiment1`。
12. `EnableHomeExcursionScores`（既定オフ）と新しい集約タイプ `DENSE_WITH_LONG_DWELL_HOME_EXCURSION` を追加。長時間滞在と「ホームからの寄り道」を見る学習系統の下準備。
13. 残りは Phoenix 学習基盤のデータ読み込み修正（Arrow のネスト配列処理）、可視性フィルタのキャッシュ設定の整理、計測の追加（上位10枠の著者別配信数、スコア済み候補数）。

- **判定の種類そのものが増えました。** `Verdict::Shown` に `notice` フィールドが追加され（`visibility-filtering/models/verdict.rs:10-14`）、README も「3つの答え」→「4つの答え」に書き換えられています（`README.md:207-211`）。

  ```
  ALLOW          普通に表示
  NOTICE         注意書きを付けて表示   ← 新設
  INTERSTITIAL   タップで解除できる覆いの裏に表示

  ```
- **新ルール `fosnr_abuse_insults_follower`**（`visibility-filtering/rules/tweet_rules.rs:626-638`）：

  - **投稿者本人は対象外**（`except_author`）。
- **注意書きの中身**（`visibility-filtering/rules/registry.rs:120-146`）：
  - `proactive: !labels.is_by_agent(label)` ＝ **ラベルが「エージェント（人／通報経路）由来」でなければ `true`**。つまり**Xが自動で検知したのか、誰かの通報によるのかが区別して表示されます**。
  - `appeal_submitted: labels.has_label(SafetyLabelType::FOSNR_APPEAL_SUBMITTED)` ＝ **投稿者が異議申し立て済みかどうか**。

  さらに `Avoid { brand_safety_risk_level: NORMAL }` が同時に付きます（`:50-56`）。

**Xユーザー／クリエイターへの影響**

- **影響を受ける層：FOSNRレベル1ラベルが付く投稿をする全アカウント、およびそのフォロワー。**
- **これまで：** レベル1ラベルの投稿は、**フォロー外の人のタイムラインからは消える**が、**フォロワーには普通に見えていた**（`fosnr_level_1_non_follower_drop`、`tweet_rules.rs:612-624`）。
- **今日から：** 同じ投稿が、**フォロワーの画面でも注意書き付き**になります。実質的に「レベル1ラベルの付いた投稿には、見える場所がもう残っていない」状態に近づきました。
- **具体的な損失：**
  - **動画の視聴数**が最も大きく落ちます（自動再生停止）。タイムラインを流し見している人は、再生されない動画をわざわざタップしません。
  - **エンゲージメント誘導UIが消える**ため、いいね・返信・リポストの発生率が下がります。
  - 注意書き自体が**心理的な抑止**として働くため、フォロワーからの反応全般が落ちます。
- **投稿者にできること：**
  - **攻撃的・侮辱的な表現を避ける**のが唯一の確実な対処です。
  - **誤判定だと思えば異議申し立てをする**。申し立て中であることが注意書きに表示されるようになったので、以前より意味があります。
- **判定基準そのものは非公開です（要確認）。** コード上にあるのはラベルの型（`AppealablePolicy::ABUSE`、レベル1）だけで、**何がレベル1に当たるかを決めているモデル／ルールはこのリポジトリに含まれていません。**

**影響度評価：大**（既定で有効・目に見える表示変化・エンゲージメントへの直接影響）

### 2. 予測ヘッドの入れ替え：「アプリ滞在」から「その投稿をどれだけ見たか」へ

**メカニズム（コード根拠）**

- **廃止：** `active_secs_5m_residual_norm`（5分間のアクティブ秒数・残差正規化）。proto の列挙から消え（`phoenix/.../recsys.proto:595-598`）、スコア送出からも削除されました（`home-mixer/side_effects/reranking_kafka_side_effect.rs:151-156`、`phoenix_experiments_side_effect.rs:217-223`）。
- **新設3ヘッド**（`xai-value-model/weights.rs:34-36`、`vm-ranker/params.rs:66-82`）：

  | ヘッド名 | パラメータキー | 既定重み | 計算式 |
  |---|---|---|---|
  | `video_continuation` | `rust_home_mixer_video_continuation_weight` | **0.0** | 動画を開く確率 × 開いた後の継続視聴秒数 |
  | `user_video_continuation` | `rust_home_mixer_user_video_continuation_weight` | **0.0** | 動画を開く確率 × **その視聴者の平均で正規化した**継続秒数 |
  | `profile_visit_secs` | `rust_home_mixer_profile_visit_secs_weight` | **0.0** | プロフィールをクリックする確率 × プロフィールでの滞在秒数 |

- **掛け算になっている点が重要**（`xai-value-model/scoring.rs:114-128`）：
  ```rust
  apply(product(scores.video_open_score, scores.home_video_continuation_secs),
        weights.video_continuation)
  ```
  `product` は**どちらか一方でも予測値が無ければ 0 を返す**実装です（`scoring.rs:61-63`）。「開かれる見込み」と「開いた後の長さ」の**両方**が揃って初めて点が入ります。
- **`user_video_continuation` の正規化**（`scoring.rs:141-157`）：そのリクエストの候補全体について `Σ(開く確率 × 継続秒数) ÷ Σ(開く確率)` を計算し、各候補をその値で割ります。**「この視聴者の平均的な動画視聴の長さ」を基準にした相対評価**です。
- **ヘッドの供給元**：`EnableHomeExcursionScores`（既定 `false`、`home-mixer/params/param.rs:278-283`）が有効なときだけ、Phoenix から `HOME_VIDEO_CONTINUATION_SECS` / `HOME_PROFILE_VISIT_SECS` の予測値を取り出します（`home-mixer/scorers/phoenix_scorer.rs:141-150`）。

**Xユーザー／クリエイターへの影響**

- **今日の影響はゼロです。** 重み3つとも `0.0`、供給元のフラグも `false`。
- **有効化されたときの影響（影響を受ける層：動画投稿者が最大）：**
  - **「冒頭で釣って離脱される動画」が明確に不利**になります。これまでの `video_quality_view`（一定秒数以上の視聴）は**閾値を超えたかどうかの0/1**でしたが、新ヘッドは**秒数そのもの**を見ます。**長く見られるほど線形に得点が増える**設計です。
  - **`user_video_continuation` は中小の動画クリエイターに有利**です。「普段あまり動画を見ない人が、この動画は最後まで見た」を拾うので、**既に動画をたくさん見ている層に最適化された大型アカウントの優位が薄まる**方向です。
  - **`profile_visit_secs` は「プロフィールを見に行かせる投稿」を評価します。** 自己紹介・固定投稿・プロフィール画面の作り込みが、**初めてスコアに繋がる可能性**が出てきました。ただし効くのは**投稿がプロフィールクリックを誘発したとき**なので、「この人は何者だろう」と思わせる投稿が有利ということです。
- **廃止された `active_secs_5m_residual_norm` の意味：** これは「その投稿を見た後、アプリに何秒留まったか」という**アプリ全体の滞在**を見る指標でした。これが消えて**その投稿自体の視聴時間**に置き換わったのは、**「とにかくアプリに留まらせる」最適化からの後退**とも読めます。良い方向の変化です。

**影響度評価：中（現時点では小・有効化されれば大）**

### 4. 「人気投稿」経路の全面再設計（既定オフ）

**メカニズム（コード根拠）**

**(a) 選定基準の変更**（`home-mixer/util/popular_posts.rs:48-86`）

```rust
pub fn quality(views: u64, age_hours: f64, config: &SelectionConfig) -> f64 {
    let lambda = ln(2) / config.half_life_hours;          // half_life_hours = 8.0
    let saturation = 1.0 - exp(-lambda * config.window_hours);  // window_hours = 24.0
    let elapsed = 1.0 - exp(-lambda * age_hours.max(config.floor_hours)); // floor = 0.5h
    views as f64 * saturation / elapsed
}
```
- 「**この投稿が24時間かけて集めるであろう閲覧数**」を、**半減期8時間の指数カーブ**で現在の閲覧数から外挿した値です。
- **投稿から0.5時間未満は0.5時間として扱う**（`floor_hours`）ため、投稿直後の極端な過大評価は抑えられています。
- **24時間を過ぎた投稿は対象外**（`:65`）。
- 著者ごとに上位 **5件**に絞ってから、全体で上位 **500件**（`:39-42,78-83`）。

**(b) 著者リストの自動化**（`home-mixer/util/popular_authors.rs:11,25-44`、`home-mixer/popular_authors_job.rs`）

- 前回は**運用担当者が `author_id,follower_count` のCSVを標準入力から流し込む**方式（`--import-popular-authors`）でした。今回それが**削除**され、BigQuery のテーブル `twttr-bq-timelines-prod.pulse.popular_posting_authors` から**1時間ごとに自動取得**するジョブに置き換わりました（`home-mixer/main.rs:33-44,141-166`）。

- 以前は**ユーザーのリクエストのたびに Thunder（フォロー中投稿サービス）を呼んで**いました。今は**5分ごとのバッチジョブ**（`--popular_posts_job_interval_secs` 既定 300）が Thunder と閲覧数サービスを呼んで完成リストを Manhattan に保存し、配信側は**それを読むだけ**です。

**Xユーザー／クリエイターへの影響**

### 8. 判定の確定度を4状態に分離（データ取得失敗時の扱い）

**メカニズム（コード根拠）**

- 旧：`EvaluationStatus { Evaluated, UnresolvedAuthor, Failed }` の3値（削除、`visibility-filtering/filter.rs:20-25`）。
- 新：`Evaluation` 列挙（`visibility-filtering/models/verdict.rs:160-173`）
  - `Complete { verdict }` — 全データが揃って確定。
  - `Partial { verdict, fail_open_defaults }` — **一部データが取れず、「取れなかったぶんは安全側の既定値で判定した」**。どのデータが欠けたかも記録。
  - `NotFound(lookup)` — **投稿／著者が存在しない**（削除された等）。
  - `Failed(lookup)` — **取得そのものに失敗**（タイムアウト等）。
- 配信側の扱い（`visibility-filtering/evaluate_tweets.rs:79-93`）：
  - `Complete` と **`NotFound` は判定結果を返す**（`NotFound` は「ドロップ」という確定した答え）。
  - `Partial` と `Failed` は**呼び出し元にエラー（`Failed`）を返す**。
- リポスト（リツイート）の合成（`visibility-filtering/retweet.rs:59-73`）：**元投稿の判定が `Complete` でないとき、リポストの判定も `Partial` に格下げ**されます。元投稿の判定が不確かなら、リポストの判定も不確かと扱う、という保守的な設計です。

**Xユーザー／クリエイターへの影響**

- **直接の行動指針はありません。** 内部の堅牢性の改善です。
- ただし意味のある変化が1点：**「削除済みの投稿」と「データ取得に失敗した投稿」が区別**されるようになりました。前者は確定的に非表示、後者は呼び出し元が再試行などの判断をできます。
- **安全側（fail-closed）の設計**が明確になっています。データが取れないときは**表示しない／エラーを返す**方向で、**取れないから表示する**という抜け道は塞がれています。可視性フィルタとしては望ましい方向です。

**影響度評価：小**
