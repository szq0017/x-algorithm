## 非IT精通者向け・運用方法のまとめ（行動指針）

- **今日は「投稿の作り方」に直結する変更が入りました。これまでで最も重要度の高い日のひとつです。** 推薦モデルに渡される情報として、**投稿の「見た目の形」そのもの**——動画があるか／写真があるか／メディアの枚数／動画の最長尺／本文の文字数（日本語は1文字=2カウント）／改行の数／外部リンクを含むか——が新しく追加されました（後述2）。これまでモデルは本文の意味やエンゲージメント履歴を中心に見ていましたが、**今後は「フォーマット」も学習・予測の材料になります**。
- **具体的な行動指針（フォーマット）**：
  - **外部リンクの有無がモデルの明示的な入力になりました。** リンク付き投稿が有利か不利かはコードからは決まらず（学習結果次第＝要確認）、ただし「リンクの有無で扱いが変わりうる」状態になったのは確実です。**重要な投稿はリンクを別の返信に分ける／本文だけで完結させる**という従来からの定番の使い分けを、今後は結果を見ながら意識的に検証する価値があります。
  - **改行の数もそのまま数えられています。** 改行を多用した「縦長ポエム型」の投稿は、**フォーマットとして識別される**ようになりました。有利／不利の方向はコードからは不明（要確認）ですが、「改行を増やせば安全」という前提は今後成り立たない可能性があります。
  - **文字数のカウントはXの公式ルール（日本語・絵文字は2、URLは一律23文字換算）と同じです。** 短文と長文が別扱いになりうるので、**普段と極端に違う長さの投稿は結果が振れやすい**と考えてください。
  - **リポスト（RT）と引用リポストの扱いが正確になりました。** リポストは元投稿の本文が、引用リポストは引用先の本文とメディア情報が、それぞれ正しくモデルに渡るようになりました（従来は取れていなかった／不正確でした）。**引用リポストは「引用先の中身込み」で評価される**ようになったので、質の低い投稿を引用するとその質が自分の投稿の評価に混ざります。逆に良質な投稿の引用はプラスに働きうる状態です。
- **一部の利用者だけタイムラインの傾向が意図的にズレる仕組みが入りました（既定はオフ）。** 「いいね重視」「返信重視」といった重み配分を、**利用者ごとにランダムに±方向へ少しずらす**機能が追加されました（後述1）。既定値はオフですが、有効化されると**同じ投稿でも人によって届き方が変わり**、しかもその「ズレ」はアカウント単位で固定されます。**「フォロワーAには表示されたのにフォロワーBには出ない」という現象が今後増えうる**、という理解でOKです。運用上の打ち手はありませんが、**日ごと・アカウントごとの数字のブレを「自分の投稿の失敗」と即断しない**ことが大事です。
- **返信欄の扱いが変わるフォロワー数の境界が 12万人 → 15万人 に上がりました。**
  - **フォロワー15万人以下のアカウント**の投稿の返信欄は、これまでの「返信のスコア付け（並べ替え）」ではなく、**「スパムかどうかの二値判定」の対象**になります。返信が細かく並べ替えられなくなる代わりに、**スパム判定に引っかかると返信が沈む**構図です。
  - **フォロワー15万人超のアカウント**の投稿の返信欄だけが、AIによる返信ランキング（0〜1のスコア付け）の対象として残ります。
  - **返信で伸ばす戦略を取る人は、絡む相手の規模で挙動が変わる**ことを意識してください。12万〜15万人のアカウントへの返信は、今日から扱いのグループが変わっています。
- **「連携スパム（複数アカウントでの示し合わせた返信）」の監視対象が狭まりました。** 従来はフォロワー5,000人以上のアカウントのスレッドが対象でしたが、**1万人以上**に引き上げられました。**フォロワー5,000〜1万人のアカウントのスレッドは、連携スパム検知の対象外**になります（返信欄が荒れやすくなる方向）。
- **長尺動画の「冒頭だけ差し替え」型の抜け道が塞がれました。** 30秒以上の動画で、いいね数が多い投稿については、**冒頭10秒を切り出して成人向けコンテンツの再判定**が走るようになりました。加えて、動画に薄く重ねられた隠しコンテンツを暴く「モーションリビール」処理が**常時・2倍の密度（16→32サンプル）で動く**ようになり、判定AIへの指示も「**表向きの映像がおとりで、暴かれた側がより悪質なら、暴かれた側で判定せよ**」と明確に強化されました。**動画で成人向け／規約違反コンテンツを紛れ込ませる手口は、今日から大幅に検出されやすくなっています。**
- **検索・推薦用の新しい「投稿の意味ベクトル（v8-search）」の生産ラインが稼働開始しました。** ここで作られる投稿の要約情報には、本文・画像・動画のフレーム・音声の書き起こしに加えて、**著者の認証バッジの色、パロディ等のアカウントラベル、NSFWフラグ、自己紹介文、フォロワー／フォロー数の階層、加入年、国、言語、サブスク階層**までが一緒に埋め込まれます（後述5）。**「誰が投稿したか」が、投稿の意味そのものに織り込まれる**方向です。プロフィール（自己紹介文・表示名）の整備は、今後これまで以上に効きます。

## 変更サマリ

1. ランキング重みを**利用者ごとにランダムに ±σ ずらす摂動機構**を新設（`WeightPerturbationSigma` 既定 0.0 ＝ 既定オフ）。26個の予測ヘッド全部が対象。重みの数値自体は14日連続で無変更。
2. 推薦モデル（Phoenix）への入力に **`ContentFeatures`（動画/写真の有無・メディア枚数・最長動画尺・重み付き文字数・改行数・外部リンク有無）を新設し、常時送信**。引用先の投稿についても同じ特徴量を送る。フィーチャースイッチによるゲートなし。
3. リポストの本文が**元投稿の本文**に修正され、引用リポストの**本文とメディア情報が新たにハイドレート**されるようになった（2の入力の正確性が大幅向上）。
4. grox の返信系フォロワー閾値を変更：スパム二値判定／返信ランキングの境界 120,000 → **150,000**、連携スパム検知の下限 5,000 → **10,000**。
5. 検索向け新埋め込み **v8-search** の生産ライン（リアルタイム／返信向け／バックフィル）を新設。著者のプロフィール・認証・安全性メタデータを含む形で投稿をレンダリングして埋め込む。バックフィルは負荷に応じて「いいね数の足切り」を自動調整（適応制御）。
6. 成人向けコンテンツの**長尺動画・冒頭10秒クロップ再判定フロー**を新設。モーションリビールを常時化・密度2倍化し、判定プロンプトを「おとり動画」対応に強化。
7. その他は挙動不変または基盤系：Phoenix retrieval MoE の推論クラスタ切替（`Experiment1Fou` → `Experiment2Memy04`）、FA4 アテンションカーネルの A100/H100 対応、モデルチェックポイントのバンドル読み込み、candidate-pipeline のメトリクスにステージ／コンポーネント名ラベル追加、VF クライアントのキャンセル計測。

## 変更点ごとの詳細（メカニズム → Xユーザー／クリエイターへの影響）

### 1. ランキング重みの「利用者ごとランダム摂動」機構を新設（実影響：既定オフだが、有効化時は大）

**メカニズム**

`home-mixer/scorers/ranking_scorer.rs:182-193`：

```rust
pub(crate) fn perturbed(mut self, query: &ScoredPostsQuery) -> Self {
    let sigma = query.params.get(WeightPerturbationSigma);
    if sigma <= 0.0 { return self; }
    let salt = query.params.get(WeightPerturbationSalt);
    for (head, weight) in self.weights_mut() {
        *weight *= (sigma * perturbation_sign(&salt, query.user_id, head)).exp();
    }
    self.recompute_sums();
    self
}
```

`perturbation_sign`（`ranking_scorer.rs:230-236`）は `md5("{salt}:{user_id}:{head}")` の先頭バイトの偶奇で `+1.0 / -1.0` を返す。つまり各予測ヘッドの重みが **`× e^{+σ}` か `× e^{-σ}` のいずれか**になり、その向きは**閲覧者IDとヘッド名で決定的**（同じ人・同じヘッドなら毎回同じ向き）。対象は `weights_mut`（`ranking_scorer.rs:195-228`）の **26ヘッド全部**——いいね・返信・リポスト・写真拡大・動画再生・クリック・リンク開封・プロフィールクリック・VQV・共有（DM/リンクコピー含む）・滞在・引用・引用先クリック・引用先VQV・滞在時間・クリック後滞在・5分アクティブ秒・著者フォロー・未探索ボーナス、および負のヘッド（興味なし・ブロック・ミュート・報告・非滞在）。

適用点は本番のスコアリング経路そのもの（`ranking_scorer.rs:713`：`ScoringWeights::from_params(&query.params).perturbed(query)`）。摂動後に `recompute_sums()`（`ranking_scorer.rs:151-180`）で正負合計を再計算するため、**正規化に使われる合計値も一緒にズレる**（＝スコアのスケールごと変わる）。

パラメータは `home-mixer/params/param.rs:485-499`：`rust_home_mixer_weight_perturbation_sigma`（f64・既定 **0.0**）、`rust_home_mixer_weight_perturbation_salt`（String・既定 空）。σ=0 以下なら即 return するので、**既定状態では完全に無効**。

**影響**

- 目的は明らかに**探索とオフポリシー学習**（重みを人為的にずらしたデータを集めて「重みを変えると指標がどう動くか」を推定する）。X が重み調整の高速化に舵を切ったことの表れ。
- 有効化（σ>0）されると、**同じ投稿でも閲覧者によって評価軸が体系的にズレる**。例えば σ=0.2 なら各ヘッドが約 ×1.22 か ×0.82 になり、ある人には「いいねされやすい投稿」が上位に、別の人には「返信されやすい投稿」が上位に来る。
- クリエイター側から見ると、**リーチのばらつき（分散）が増える**。「昨日と同じ内容なのに数字が半分」という日が構造的に増えうる。**A/Bを自分で検証する（同じ形式を複数回試す）ことの重要性が上がる**一方、単発の結果から結論を出すのは今まで以上に危険。
- σ の実運用値は公開コードからは読み取れない（`param.rs` はフィーチャースイッチの既定値のミラーで、本番の配信値は別管理）＝**要確認**。

### 2. 投稿の「フォーマット特徴量」がモデル入力に追加（実影響：大）

**メカニズム**

proto に `ContentFeatures` を新設（`phoenix/python/common/xai-proto/proto/recsys.proto:1220-1231`、serving 側も同内容）：

```proto
message ContentFeatures {
  bool hasVideo = 1;
  uint32 maxVideoDurationMs = 2;
  bool hasPhoto = 3;
  uint32 mediaCount = 4;
  uint32 weightedTextLen = 5;
  uint32 newlineCount = 6;
  bool hasUrl = 7;
}
```

`TweetInfo` に `contentFeatures`(36) と `quotedContentFeatures`(37) として追加。組み立ては `home-mixer/models/content_features.rs`、送信は `home-mixer/models/candidate.rs:295-296`（`as_tweet_info`、**条件分岐なし＝全リクエストで送信**）。

文字数カウント（`content_features.rs:44-65`）は X の公式 twitter-text ルース実装：全角・絵文字は 2、ASCII等（コードポイント 0-4351 ほか）は 1、URL は本数×23 固定、肌色修飾子・異体字セレクタは 0（`content_features.rs:74-88`）。メディア添付で自動付与される `t.co` URL は「外部リンク」から除外され（`content_features.rs:59`：`urls.saturating_sub(attachment_urls)`）、**本文中に自分で貼った外部リンクだけが `hasUrl=true`** になる。改行数は `tweet_text.matches('\n').count()`（`content_features.rs:17`）。

メディア側の実データは `MediaInfoHydrator` の拡張で供給（`home-mixer/candidate_hydrators/media_info_hydrator.rs:126-130`）：`has_photo` / `has_video` / `media_count` / `max_video_duration_ms` を新たに取得しキャッシュに載せる（従来は `has_media` と `min_video_duration_ms` の2値のみ）。

**影響**

- **モデルが「投稿の型」を直接見るようになった。** 従来もメディア有無は間接的に効いていたが、今回は「写真1枚か4枚か」「動画が15秒か3分か」「本文が20文字か280文字か」「改行が0か12か」「外部リンクがあるか」が**明示的な数値入力**になる。
- **有利／不利の方向はコードからは決まらない**（重みは学習で決まる）。ただし、モデルがこれらを入力に持つ以上、**フォーマットの選択がリーチに与える影響は今後「学習によって最適化された形」で強まる**。「メディアを付ければ有利」といった従来の経験則が、より細かい粒度（枚数・尺）に置き換わっていく。
- **外部リンクは特に注目すべき点。** 「リンク付き投稿は伸びない」という長年の通説が、初めて**明示的な特徴量として実装された**。今後は通説の真偽が検証可能になる一方、モデルがリンク付き投稿の低エンゲージメントを学習すれば、**通説が自己成就する**方向にも働きうる。
- **注意点（要確認）**：proto フィールドは新設されたばかりで、**現在稼働中の学習済みモデルがこの入力を実際に使っているかは公開コードからは分からない**。「配管は開通したが、モデル側の利用は次の学習サイクル以降」という可能性が高い。

### 3. リポスト／引用リポストの本文・メディアが正しく取得されるように（実影響：中〜大）

**メカニズム**

**(a) リポスト**：`home-mixer/candidate_hydrators/core_data_candidate_hydrator.rs:84-113`。候補の `source_tweet_id`（リポスト元）を集めて**もう一往復 TES に問い合わせ**、`source_text.unwrap_or_else(|| core_data.text.clone())` で**元投稿の本文を採用**するようになった。従来はリポストのレコード自身の text をそのまま使っていた。

**(b) 引用リポスト**：`home-mixer/candidate_hydrators/quote_hydrator.rs:72-131` に `get_quoted_content` を新設。引用先の**本文（TES）とメディア情報（MediaInfoCache）を 200ms タイムアウトで並列取得**し、専用キャッシュに載せる（`quote_hydrator.rs:175-186` の `apply` で `quoted_tweet_text` / `quoted_has_media` / `quoted_has_photo` / `quoted_has_video` / `quoted_media_count` / `quoted_max_video_duration_ms` を設定）。パイプライン側で `QuoteHydrator` に `media_info_cache_client` が渡されるよう配線（`home-mixer/candidate_pipeline/phoenix_candidate_pipeline.rs:333-340`、`phoenix_scores_pipeline.rs:144-146`）。

**影響**

- 上記2の特徴量が**リポスト・引用リポストでも正しい値になる**。これがなければ、リポストは「本文空・メディアなし」、引用リポストは「引用先の中身が見えない」状態で評価されていた。
- **引用リポストは「引用先の中身込み」で評価される。** 引用先の本文・写真／動画の有無・枚数・尺が `quotedContentFeatures` としてモデルに渡る。**低品質な投稿を引用すると、その低品質さが自分の投稿の評価材料に混ざる**構図。逆に、良質・メディア豊富な投稿の引用はプラスに働きうる。
- ミュートキーワードフィルタ（`home-mixer/filters/following_viewer_muted_keyword_filter.rs:61`）も `quoted_tweet_text` を参照しているため、**引用先の本文がミュートワードに引っかかると引用リポストごと消える**経路が、今回のハイドレート追加でより確実に機能する方向（従来は別のハイドレータ経由でしか埋まらなかった）。

### 4. grox：返信欄の扱いが変わるフォロワー閾値の変更（実影響：中）

**メカニズム**

`grox/flows/reply_spam/task_filter.py`：

| フィルタ | 変更前 | 変更後 | 条件の向き |
|---|---|---|---|
| `TaskSpamFilter`（スパム二値判定） | 120,000 | **150,000**（:17） | 返信先／スレッド根の著者フォロワー数が閾値**以下**なら対象 |
| `TaskReplyRankingFilter`（返信ランキング） | 120,000 | **150,000**（:185） | 返信先／スレッド根の著者フォロワー数が閾値**超**なら対象 |

スパム二値判定と返信ランキングは同じ数値で背中合わせの排他条件（`task_filter.py:78-90` と `:215-224`）。連携スパムは `root_user_follower_count < 閾値` で除外（`task_filter.py:158-162`）。

**影響**

- **フォロワー12万〜15万人のアカウントのスレッドが、返信ランキング（0〜1のスコア付けによる並べ替え）から、スパム二値判定へ移った。** この層の投稿の返信欄は、**細かい順位付けが効かなくなる代わりに、スパム判定に当たれば沈む**という粗い扱いに変わる。
- **返信で露出を稼ぐ運用**をしている人は、12万〜15万人規模のアカウントに絡むときの挙動が今日から変わっている。**「良い返信が上位に上がる」効果は期待しにくくなり、「スパム判定を避ける」ことが相対的に重要**になる。
- **連携スパム検知は 5,000〜10,000 フォロワー層のスレッドを対象外にした。** 中小アカウントのスレッドで、複数アカウントによる示し合わせた返信が**検知されなくなる**。この規模のアカウントは返信欄が荒れやすくなる方向。理由は明示されていないが、閾値の引き上げは通常「誤検知が多い／処理コストが高い」を意味する（＝要確認）。
- 副次的な変更として、返信ランキングスコアの Strato 書き込みと Kafka への発行が `publish_reply_ranking_score` に一本化され、**Kafka 発行 → Strato 書き込みの順序が保証**されるようになった（`grox/flows/reply_spam/strato_loader.py:34-53`）。挙動としては下流の整合性向上のみ。

### 5. 検索向け新埋め込み v8-search と、著者メタデータの取り込み（実影響：中／将来 大）

**メカニズム**

新規パイプライン一式：`plan_post_embedding_v8_search.py`（リアルタイム）／`_for_reply.py`（返信向け）／`_backfill.py`・`_backfill_batch.py`（過去投稿の遡り生成）。生成物は `StratoPostMultimodalEmbeddingMhSearchAi`（モデル版 `v8_search_1`、`grox/flows/mm_emb/constants.py:24-25`）へ書き込み、Kafka トピック `grox-multimodal-embedding-v8-search` に発行。

**埋め込み対象のレンダリング**が今回の要点（`grox/flows/mm_emb/renderer_v8_search.py`）。冒頭に指示文を置き（`:12`）：

> "Represent this X post (formerly Twitter) for recommendation: capture its topic, intent, key entities, and likely engagement."

続けて**著者ブロック**（`renderer_v8_search.py:216-278`）に以下を列挙：表示名と @ハンドル、**認証バッジ色**（Government→Grey / Business→Gold / Blue、`:281-310`）、**パロディ・論評・ファンアカウントのラベル**（`:312-319`）、鍵アカウントか、**NSFW フラグ**（`:321-329`）、**自己紹介文**（最大500字）、**フォロワー数／フォロー数（実数＋階層ラベル）**（`:77-112`：`<10`, `10-100`, ..., `>100M`）、サブスク階層、**加入年月**、**国コード**、**アカウント言語**、提携ビジネス名。その後に本文（最大4000字）、画像／動画フレーム（最大16枚・動画あたり4フレーム）、**動画の尺と画質バケット**（`:132-140`：5Mbps以上=Full HD / 1.5Mbps以上=HD / それ未満=SD）、**音声の書き起こし**（最大2000字）、記事タイトル、リンクカードのタイトルとドメイン、引用先の本文と引用先著者のフォロワー数階層（`:427-461`）。

バックフィルは負荷適応型：`AdaptiveMinFav`（`grox/flows/mm_emb/adaptive_min_fav.py`）が処理QPSを30秒窓で観測し、目標5QPSに対して**いいね数の足切り（初期20,000・上限20,000・下限0）を比例制御で自動上下**させる（`task_backfill_gate.py:16-19,26-48`）。既に埋め込み済みの投稿はスキップ（`task_backfill_gate.py:51-63`）。

**影響**

- **「誰が投稿したか」が「投稿の意味ベクトル」そのものに埋め込まれる。** 検索・類似投稿検索・推薦の候補生成で使われるベクトルに、認証バッジ・アカウントラベル・NSFWフラグ・フォロワー階層・自己紹介文が混ざる。これは「同じ内容でも、著者属性の似たアカウント同士が近いベクトルになる」ことを意味する。
- **プロフィールの整備の重要度が上がった。** 自己紹介文（500字まで）が投稿の意味ベクトルに毎回入るため、**自己紹介文に自分のテーマ・専門領域を明記しているかどうか**が、投稿単位の検索・推薦適合性に効きうる。表示名・ハンドルも同様。
- **パロディ／論評／ファンアカウントのラベル**が明示的に埋め込まれる。ラベル設定済みのアカウントは、本人アカウントとベクトル空間上で区別されやすくなる（なりすまし対策としては正常な方向）。
- **動画の画質・尺も埋め込みに入る。** 低ビットレート（SD）の動画は「SD」というラベル付きで埋め込まれる。**動画の画質を落として容量を節約する運用は、検索・推薦上不利に働きうる**（方向は学習次第＝要確認）。
- バックフィルは**いいね2万以上の過去投稿から順に**埋め込みを作り、余力があれば足切りを下げていく設計。過去の人気投稿から順に新しい検索対象になる、という時間差が生じる。

### 6. 長尺動画の成人向けコンテンツ再判定フローと、モーションリビールの強化（実影響：中〜大／安全性方向）

**メカニズム**

**(a) 冒頭クロップ再判定フロー**（新規 `grox/flows/ptos/plan_safety_ptos_adult_content_leading_frames.py`）。対象の絞り込みは `task_safety_ptos_adult_content_leading_frames_filter.py:26-73`：

1. いいね数が `deluxe_fav_count_threshold` 未満なら除外
2. 投稿本体または引用先に **30秒以上の動画**（`ADULT_CONTENT_LEADING_FRAMES_MIN_DURATION_SECONDS = 30.0`）がなければ除外
3. 既存の PTOS 判定結果がなければ除外／既に NSFW 判定済みなら除外（重複処理の回避）
4. 既存判定で成人向け違反が付いておらず、かつ**いいね数が 512 未満**（`ADULT_CONTENT_LEADING_FRAMES_UNCONDITIONAL_FAV = 512`）なら除外

通過した動画には `video.crop_seconds = 10.0`（`ADULT_CONTENT_LEADING_FRAMES_CROP_SECONDS`）が設定され、フレーム抽出が**冒頭10秒のみを対象**に行われる（`grox/core/data_loaders/media_loader.py:469,540,560` → `grox/libs/video_tools/video_frames.py:86-87`：`total_duration = min(total_duration, max_duration)`）。字幕も同区間に揃えられる（`media_loader.py:571`）。その後、カテゴリ判定 → ポリシー判定 → SafeModel → **Grok 4.5 クロスバリデーション**（`plan_..._leading_frames.py:32-45`）と、Deluxe 相当の重い判定パイプが走る。クロスバリデーションが例外を出した場合は Soft（制限側）にフェイルクローズする対象に、この新タスクタイプも追加された（`task_safety_ptos_adult_content_cross_validation.py:108`：`SPECIAL_VIDEO_TASK_TYPES`）。

**(b) モーションリビールの常時化・高密度化**（`grox/libs/video_tools/video_frames.py:23,92`）：

```python
# 変更前: _MOTION_REVEAL_DENSE_THRESHOLD = 12 / _MOTION_REVEAL_DENSE_SAMPLES = 16
#         if enable_motion_reveal and 0 < len(frames) < 12 and total_duration > 0:
# 変更後:
_MOTION_REVEAL_DENSE_SAMPLES = 32
if enable_motion_reveal and frames and total_duration > 0:
```

抽出フレームが12枚未満のときだけ走っていた高密度サンプリングが、**フレーム数によらず常時**、しかも **16→32サンプル**で走るようになった。

**(c) 判定AIへの指示文の強化**（`grox/core/lm/convo.py:23-30`）。変更前は「モーションリビールは色や動きを歪め、不透明な服が素肌に見えることがある。上のフレームに写っている人物は元のフレームだけで判断せよ」という**慎重寄り**の但し書きだった。変更後は：

> "Judge what they show as part of the video's actual content, as if it were shown openly, even when it is low-resolution, blurred, or partially obscured. The visible video may be a decoy: when the revealed content is more severe than the visible video, classify the post by the revealed content."

（暴かれた内容を、公然と表示されたものとして扱え。表向きの映像はおとりかもしれない。暴かれた内容の方が悪質なら、そちらで判定せよ）

**影響**

- **「冒頭だけ健全な映像を置き、途中から成人向けに切り替える」手口が、逆に冒頭10秒の精査対象になった**（このフローは冒頭を切り出して**より重い判定パイプに掛ける**もの。従来の通し判定では一様サンプリングのため冒頭の細部が薄まっていた）。
- **既に「成人向け違反」の前歴がある投稿は、いいね数が Deluxe 閾値を超えた時点で自動的に再判定される。** 前歴がない投稿でも**いいね512以上**なら無条件で再判定対象。**伸びた動画ほど再審査を受ける**設計。
- **薄い半透明オーバーレイで隠すタイプの回避手法は、常時2倍密度の検出＋「おとり前提で判定せよ」という指示強化により、大幅に検出されやすくなった。** 判定の慎重さ（誤検知を避ける但し書き）を意図的に外し、**検出漏れを減らす方向に振り切った**変更。
- 一般利用者・通常のクリエイターへの影響は限定的だが、**長尺動画（30秒以上）を投稿し、かつ大きく伸びた場合、再判定が走る**点は認識しておく価値がある。誤判定のリスクはゼロではない（Grok 4.5 のクロスバリデーションが例外を出した場合は**制限側にフェイルクローズ**する設計のため）。
- ポリシー判定のメトリクス集計が変更され、違反なしの再チェックはメトリクスに記録されなくなった（`task_safety_ptos_policy.py:152-160`）。運用計測上の変更で、利用者影響はなし。

### 7. その他（挙動不変または基盤系）

- **Phoenix retrieval MoE の推論クラスタ切替**（`home-mixer/params/param.rs:159-163`）：`Experiment1Fou` → `Experiment2Memy04`。候補生成に使われる MoE モデルの配信先が別クラスタに移った。**モデルの中身が変わったのか、単に配置換えなのかは公開コードからは判別できない（要確認）**。前者ならタイムラインの候補の傾向が変わりうる。
- **FA4 アテンションカーネルの対応GPU拡大**（`phoenix/xrex/models/recsys_attention.py:209-210,256-257`）：GB200/GB300 限定だったものが **A100/H100 でも動作**（varlen 版は H100 以降）。逆伝播カーネル（`flash_bwd.py` 等 約5,000行）も新規追加。学習・推論を旧世代GPUでも回せるようになり、**実験の回転が速くなる**方向。利用者への直接影響なし。
- **モデルチェックポイントのバンドル読み込み**（`phoenix/crates/serving/xai-recsys-engine/src/copy_port_client.rs:574-682`）：`export/MANIFEST.json` が全チャンネルに揃ったチェックポイントを新しい順に探し、揃っていなければ**より古い完全なチェックポイントにフォールバック**する。モデル更新時の事故（不完全なモデルの読み込み）を防ぐ変更。
- **candidate-pipeline のメトリクス強化**（`candidate-pipeline/candidate_pipeline.rs:37-49` ほか）：フィルタ／ハイドレータ／スコアラの統計に `stage` と `component` のラベルを付与。同一コンポーネントが複数ステージで使われる場合に区別できるようになった。挙動不変。
- **VF クライアントのキャンセル計測**（`visibility-filtering-client/vf_client.rs:397-435`）：可視性フィルタ呼び出しが完了／劣化／**キャンセル（呼び出し元のタイムアウト等で途中破棄）**のどれで終わったかを Drop ガードで計測。「フィルタが最後まで走らなかった」ケースが可視化される。挙動不変だが、**安全性フィルタの取りこぼしを検出するための計測**であり、今後の修正の前段と読める。
- **配線整理**：`home-mixer/bin/pipeline_components_json.rs` を削除（開発用ツール）。`xai_configlib` にクラス参照（`type`）の設定シリアライズ対応を追加（`__init__.py:241-242,515-517,537-550`）。VF の安全性ラベル proto 変換を参照渡しから所有権移動に変更（`visibility-filtering/safety_label_source/proto.rs`、割り当て削減のみ）。

## 不確実な点（要確認）

1. **重み摂動 σ の本番値**：`param.rs` はフィーチャースイッチ既定値のミラーであり、本番の配信値・配信率は公開コードから読めない。既定 0.0（無効）だが、実際に有効化されているかは不明。
2. **`ContentFeatures` を現行の学習済みモデルが実際に使っているか**：proto フィールドと送信配管は今回開通したが、モデル側が新入力を学習に取り込むのは次の学習サイクル以降の可能性が高い。**「今日からフォーマットが効き始める」とは断定できない**。
3. **各フォーマット特徴量の有利／不利の方向**：外部リンク・改行数・文字数・動画尺のどれが上げ要因でどれが下げ要因かは、学習結果に依存しコードからは決まらない。
4. **`deluxe_fav_count_threshold` の具体値**：長尺動画の再判定フローの1段目の足切りに使われるが、値は `grox_config`（コード外の設定）にあり不明。
5. **Phoenix retrieval MoE クラスタ `Experiment2Memy04` の中身**：モデルの差し替えか単なる配置換えか判別できない。前者ならタイムラインの候補傾向が変わる。
6. **v8-search 埋め込みが実際にどの機能で消費されるか**：書き込み先（`...MhSearchAi`）と Kafka トピックは分かるが、検索・推薦のどの経路が読み出すかは今回の差分に含まれない。「検索向け」は命名からの推定。
7. **連携スパム閾値引き上げ（5千→1万）の理由**：誤検知削減かコスト削減かはコードから判断できない。
8. **返信ランキング閾値変更の実効範囲**：12万〜15万フォロワー層のスレッドで返信欄がどの程度体感的に変わるかは、返信ランキングスコアが UI 上どう使われるかに依存し、本リポジトリの範囲外。
