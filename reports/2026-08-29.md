## 非IT精通者向け：今日から意識したい運用方法

- **今日は、Xの使い方として変えるべきことは何もありません。** 表示順・フィルタ・スパム判定・広告のいずれについても、実際に効く数値やルールの変更はゼロでした。昨日までのレポートで挙げた運用方針（返信は最初の1本を丁寧に、リンクカードの細工は大アカウントでも罰則対象、など）をそのまま継続してください。
- **ただし「同じ投稿でも人によって並び順が変わる」仕組みの下準備が入りました。** 誰にどの並べ替えモデルを当てるかを切り替えるスイッチが新設されています（今は全員が同じ「0番」で、実質オフ）。将来これがオンになると、同じ投稿への反応の伸び方が人によって差が出る可能性があります。今は何も起きません。
- **「なぜ自分の投稿が消えたのか」を判定する仕組みの検証が最終段階に来ています。** 投稿の非表示・年齢制限・ぼかし（閲覧注意）などを決めるルール群に、91通りのケースを固定した「答え合わせ表」が新設されました。ルール自体は1つも変わっていませんが、これは今後この判定エンジンが本番に切り替わっても挙動がブレないようにするための作業です。切替時に「急に見え方が変わる」リスクが下がる方向の変更なので、利用者にとってはプラスです。
- **ブラジル2026年選挙フィルタの数は今日は変わっていません。** README の日付表記が「8月25日更新」→「8月27日更新」に直っただけで、これは昨日レポートした 2,328 → 2,315 件の変更に対する説明文の追記漏れの修正です。対象アカウントの増減は今日ありません。
- **裏側の高速化が入りました（体感の変化はなし）。** 推薦モデルの重みを読み込む処理が速くなっています。モデルの更新頻度が上げやすくなる方向の投資ですが、今日時点でタイムラインの中身は変わりません。

## 変更点ごとの詳細

### 1. リランカー・ヘッド切替タグ `RerankerHeadTag` の新設【影響度：中（準備段階、既定オフ相当）】

**メカニズム**

新しいフィーチャースイッチが1本追加された。

```rust
// home-mixer/params/param.rs:246
param!(RerankerHeadTag, i64, "rust_home_mixer_reranker_head_tag", 0);
```

この値は、Phoenix への推論リクエストで **2箇所**に埋め込まれる。

- ユーザー行動シーケンス側（`home-mixer/util/phoenix_request.rs:150`）:

```rust
let mut sequence = query.scoring_sequence.clone().unwrap_or_default();
sequence.reranker_head_tag = Some(query.params.get(RerankerHeadTag) as u32);
request.sequences = vec![sequence];
```

- リクエスト直下（`home-mixer/scorers/phoenix_scorer.rs:115`）:

```rust
reranker_head_tag: Some(query.params.get(RerankerHeadTag) as u32),
```

proto 側の受け皿も同時に定義された（`phoenix/crates/serving/xai-recsys-proto/proto/recsys.proto:1316` の `UserActionSequence.rerankerHeadTag = 9`、同 `:1239` の `ScoreInfo.rerankerHeadTag = 6`）。Python 側 proto（`phoenix/python/common/xai-proto/proto/recsys.proto`）も同一内容で追従している。

応答で返ってきたタグは候補に書き戻される（`home-mixer/scorers/phoenix_scorer.rs:127`、フィールド定義は `home-mixer/models/candidate.rs:28`）。書き戻された値の出口は `as_score_info()`（`home-mixer/models/candidate.rs:213`）1本のみで、その唯一の呼び出し元は `home-mixer/side_effects/phoenix_request_cache_side_effect.rs:97` — **`LogSlateContext`（既定 `false`、`param.rs:245`）が真のときだけ**リクエストキャッシュへ書かれる。

**X ユーザー／クリエイターへの影響**

- **今日時点の影響はゼロ。** 既定値 `0` が全リクエストに乗るだけで、Phoenix 側が 0 を「従来どおり」として扱う限り並び順は変わらない。
- 意味するところは「**並べ替えモデルの最終段（リランカー）を、ユーザー単位・リクエスト単位で差し替えられる配線が通った**」こと。フィーチャースイッチ経由なので、実験バケットごとに別のヘッドを当てることが可能になる。
- これがオンになった場合、同じ投稿に対する露出量がバケット間で乖離し得る。クリエイター視点では「昨日と同じ内容・同じ時間帯なのに伸びが違う」の原因が1つ増えることになる。ただしそれは有効化後の話で、今日の差分では起きない。
- 併せて、タグが `ScoreInfo` に載って served history／リクエストキャッシュに記録される設計になっている＝**どのヘッドが出した推薦にユーザーがどう反応したかを、後から学習データとして紐づけられる**。オフポリシー学習の下ごしらえと読める。

**要確認**: リランカー・ヘッドの実体（タグ値 1 以降が何を指すか、リランカーがそもそも何を最適化しているか）は本リポジトリに含まれていない。上流の Phoenix モデル側実装は非公開のため、タグ値と挙動の対応は不明。また `reward_rerank_slot_prob`（`ScoreInfo` field 5）が今も `None` 固定である（`home-mixer/models/candidate.rs:212`）ことから、リランカー本体はまだ配信経路に入っていない可能性が高いが、断定はできない。

### 2. 可視性フィルタ（VF）にゴールデンコーパス91ケースを新設【影響度：小（挙動不変）／シグナルとしては中】

**メカニズム**

新規3ファイルが追加された。

- `visibility-filtering/rules/golden_corpus.rs`（1,039行・新規）: 「安全性レベル × 閲覧者 × 候補投稿」の組み合わせ91ケースについて、**期待される判定（Allow / Drop / Interstitial）とその判定を下したルール名**を固定するテスト。
- `visibility-filtering/rules/context.rs`（214行・新規）: これまで各ルールが `context.candidate()` / `context.viewer()` から生データを直接触っていたのを、`RuleContext` の意味付きアクセサ（`author_is_suspended()`、`media_restricted_in_viewer_country()`、`viewer_country_in()` 等）に集約。
- `visibility-filtering/rules/fixtures.rs`（116行・新規）: テスト用のビルダー（`candidate().with_label(...).with_media().build()` 等）。

特筆すべきは、コーパスに添えられた2本目のテストである。

```rust
// visibility-filtering/rules/golden_corpus.rs
#[test]
fn every_wired_rule_decides_a_corpus_case() {
    ...
    let missing: Vec<&&'static str> = wired.difference(&deciders).collect();
    assert!(
        missing.is_empty(),
        "rules wired in Policies but never the decider of any corpus case: {missing:?}"
    );
}
```

`Policies` に登録されている**全ルールが、少なくとも1件のコーパスケースで「決め手」になっていること**を強制する。今後ルールを追加したら、対応するケースを書かない限りテストが落ちる。

各ルールファイル側（`nsfw_age_gating.rs`、`socialgraph_rules.rs`、`tes_rules.rs`、`user_rules.rs`、`tweet_flag_rules.rs`、`user_label_drops.rs`、`nullcast_rule.rs`、`nsfw_interstitial.rs`、`tweet_label_drops.rs`）の変更は、いずれもこのアクセサ層への差し替えと、個別テストのコーパスへの移管である。**判定条件そのものは変わっていない**ことを個別に確認した。

なお `DropStaleTweetsRule` だけは一見条件が減っているが、等価である。

```rust
// 変更前（tes_rules.rs）
if !candidate.is_stale_tweet() { return Allow; }
if candidate.is_retweet() { return Allow; }
if candidate.tweet_features.core.source_tweet_id.is_some() { return Allow; }  // ← 削除された
Drop

// 変更後（tes_rules.rs:13）
if context.is_stale_tweet() && !context.is_retweet() { return Drop; }
Allow
```

削除された3行目は `is_retweet()` の定義そのもの（`visibility-filtering/models/mod.rs:94-96`: `self.tweet_features.core.source_tweet_id.is_some()`）であり、2行目と完全に重複していた。同様に `viewer.viewer_id().is_none()` → `context.viewer_is_logged_out()` の置換も、`viewer_id()` が `LoggedOut` に対して `None` を返す定義（`models/viewer.rs:9-14, 51-53`）から等価。

**X ユーザー／クリエイターへの影響**

- **今日の見え方は一切変わらない。** 投稿が消える／年齢制限がかかる／ぼかしが入る条件は1つも変更されていない。
- 意味は「**可視性判定の Rust 実装への切替が、退行検知の網を張り終える段階に来た**」こと。8/25 のレポートで触れた「VF新旧突き合わせハーネス（812行）」に続き、今回は新実装単体の挙動を91ケースで固定した。旧実装との突き合わせ（動的検証）と、期待値のピン留め（静的検証）が揃った形。
- 利用者側のメリットとしては、**本番切替時に「ある日突然、これまで見えていた投稿が消える／逆に見えるようになる」という事故の確率が下がる**方向。特に、著者本人には常に自分の投稿が見える（`is_author_viewer()` 免除）、フォロワーには FOSNR 系ラベルでも配信される、といった「例外の側」がコーパスに焼き込まれている点は、誤った巻き添えを防ぐ効果がある。
- 一方で、**判定ロジックが固定される＝現行の厳しさがそのまま引き継がれる**ということでもある。緩和も同時には起きない。

**要確認**: 91ケースのうち `expected_decided_by` に具体的なルール名が入っているのは65ケースで、残りは `Allow`（決め手なし）。コーパスがカバーしているのは `FilterAll` / `TimelineHome` / `TimelineHomeRecommendations` の3レベルのみで、8/19 に新設された「フォロー中」タブ専用ハイドレータ経路が別レベルを使う場合、そこはコーパス外の可能性がある。

### 3. Phoenix 埋め込みテーブル受信のパイプライン化【影響度：小（インフラのみ）】

**メカニズム**

`phoenix/crates/serving/xai-recsys-engine/src/emb_table.rs` の `send_entries` が書き換えられた。従来は gRPC のチャンクを受け取るコールバック内で、その場で `copy_nontemporal`（非テンポラル memcpy）と adler32 チェックサム計算を行っていた。変更後は、

```rust
// emb_table.rs
const GRPC_COPY_PIECE: usize = 4 << 20;   // 4MiB
let (tx, rx) = std::sync::mpsc::sync_channel::<bytes::Bytes>(2);
let copy_join = JoinOnDrop::new(tokio::task::spawn_blocking(move || {
    ...
    while let Ok(chunk) = rx.recv() {
        install_grpc_chunk(dest, &mut pos, &mut checksum, &chunk);
    }
    (pos, checksum)
}));
```

受信コールバックは 4MiB 単位に切って深さ2の同期チャネルへ流すだけになり、コピーとチェックサムは別スレッド（`spawn_blocking`）へ移った。RDMA 転送後の残余チェックサム計算も同様に `spawn_blocking` へ退避。`JoinOnDrop` は早期 return 時にもワーカーを確実に join させるための RAII ラッパで、`dest_ptr` を `usize` 経由で渡す `unsafe` の健全性（バッファの生存期間）を担保している。

`proto_parser.rs` には `Func::Bytes` バリアントが追加され、`chunk.slice(pos..pos+len)` で `Bytes` の参照カウント・スライス（コピーなし）を渡せるようになった。`copy_port_client.rs` の変更は `join_transfers` ヘルパ抽出（重複コード3箇所の共通化）とテスト名の整理のみ。

**X ユーザー／クリエイターへの影響**

- **なし。** 推薦のスコアリング結果は一切変わらない。モデル重みのロード時間が短縮されるだけ。
- 間接的な含意として、**モデル更新のデプロイ・サイクルが回しやすくなる**。8/14 以降のレポートで追ってきた「重みやヘッドの頻繁な入れ替え」を支える基盤投資と読める。
