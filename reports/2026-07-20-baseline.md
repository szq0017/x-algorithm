# 1. エグゼクティブサマリ

現行の「For You」アルゴリズムは、**手作り特徴量による多段ヒューリスティックから、Grok系トランスフォーマーによる完全ML化(two-tower検索 + マルチアクション予測)へ移行済み**であり、ユーザーが見るものは「MLが予測する行動確率 × 設定可能な行動別重み」を軸に、多様性・ネットワーク由来・価値モデル・広告配置のルールで再整形される構造になっている。候補は follow グラフ由来の in-network(Thunder)と、埋め込み類似度による out-of-network(Phoenix retrieval)の2系統から供給され、発見性は後者が担う。

ユーザー行動への最重要ポイント:

- **主要なパーソナライズ源はエンゲージメント履歴**: like/reply/repost/dwell(滞在)した投稿・著者・行動種別が平均プールされてユーザーベクトルになり、out-of-network の発見を直接方向づける。無視した内容からは遠ざかる。ただし「唯一の」入力ではない: ユーザー塔は user_hashes(ユーザーID埋め込み)や product_surface も含み、別途デモグラフィック/推定性別/IP のクエリハイドレータも存在する。
- **正の行動には正の重み、block/mute/report/not_interested/not_dwelled には負の重み**(home-mixer `ranking_scorer.rs`)。ネガティブシグナルは類似コンテンツを最下部へ沈める。ただし具体的な重み値は設定駆動で本リポジトリには存在しない(要確認)。
- **like が最重視される可能性**: Phoenix デモ実装の重み付け和は fav×1.0 > reply×0.5 > repost×0.3 > dwell×0.2 で like が支配的。本番の重みは設定次第(要確認)。
- **著者多様性・OON減衰・広告ブランドセーフティ**が最終順序を上書きし、1リフレッシュ内で単一著者の独占を防ぎ、フォロー外を相対的に減衰させる。
- **可視性はスコアより前に確定する**: block/mute/ミュートキーワード/既読・既配信はスコアリング前に絶対的に除去され、どれだけ関連性が高くても表示されない。

## 2. パイプライン全体像

リクエストは、汎用実行骨格である `candidate-pipeline` クレート(7つのステージ trait: QueryHydrator / Source / Hydrator / Filter / Scorer / Selector / SideEffect)の固定順序で処理される。実際の For You は2つのパイプラインが入れ子になっている。

1. **クエリ・ハイドレーション**: ユーザー文脈(フォロー一覧、topic_ids、アカウント年齢、行動履歴長など)を付与。
2. **候補ソース(並列取得、Err は暗黙に握りつぶし)**:
   - **Thunder(in-network)**: follow グラフのみを供給キーとし、フォロー中著者の直近投稿を**純粋な逆時系列(recency)**で返す。MLなし、著者別上限あり。retention 窓(コード上のデフォルトは2日=172800s、本番値は要確認)を過ぎた投稿は消える。
   - **Phoenix retrieval(out-of-network)**: two-tower モデル。ユーザー履歴を Grok トランスフォーマーで1本のユーザーベクトルに、各投稿を MLP candidate tower でベクトル化し、コーパス全体に対する cosine top-K(デフォルト200)で引く。follow グラフ非依存。加えて MoE / topics / tweet-mixer も供給。
3. **候補ハイドレーション**: 特徴量・ブランドセーフティ判定などを付与(キャッシュあり、ここでは候補を落とせない契約)。
4. **事前フィルタ(除去はここだけ)**: 年齢・自己投稿・blocked/muted 著者・ミュートキーワード・既読/既配信・重複などを順次適用。**スコアリング前**に categorically 除去。
5. **スコアリング(逐次)**: `PhoenixScorer`(行動別確率を推論)→ `RankingScorer`(確率×重みの線形和 + 著者多様性 + OON減衰)→ 任意で `VMRanker`(外部 gRPC 価値モデル + DPP 多様性、有効時はヒューリスティックスコアを置換)。
6. **選択**: `TopKScoreSelector` が単一 float スコアの降順で hard top-K を取り、残りは破棄。
7. **事後ハイドレーション/事後フィルタ**: 選ばれた top-K のみに可視性・安全性(VFFilter 等)チェック。ここで削られると補充なしでフィード枚数が K を下回りうる。
8. **外部パイプライン `ForYouCandidatePipeline`**: 上記のスコア済み投稿に、広告・who-to-follow・prompts・push-to-home を混ぜ、`BlenderSelector` が広告ブレンダーを介してブランドセーフティ隣接制約下で広告を挿入。
9. **SideEffect(fire-and-forget)**: 配信済み履歴を Kafka 等へ非同期書き込み(次リクエストの dedup 基盤)。

補足(コード上の重要事実): 独立ファイルの `weighted_scorer.rs` / `author_diversity_scorer.rs` / `oon_scorer.rs` は `scorers/mod.rs` に登録されておらず**未使用(デッドコード)**。実稼働の重み付け・多様性・OON ロジックはすべて `RankingScorer`(`ranking_scorer.rs`)に統合済み。なお、これらのファイルが `crate::util` / `crate::params` を import している点は「デッドの根拠」にはならない——ライブの `ranking_scorer.rs` / `phoenix_scorer.rs` も同じく `lib.rs` 未宣言の `params`/`util`/`clients` を import している(本リポジトリは `params`/`util`/`clients` を含まない部分公開スナップショット)ため、import の可否は死活判別に使えない。**判別基準は `scorers/mod.rs` への登録有無のみ**である。

## 3. ユーザー行動を左右する主要メカニズム

### 3.1 完全ML化・手作り特徴量の廃止

- **メカニズム**: 検索は two-tower(`recsys_retrieval_model.py`)、ランキングは Grok 系トランスフォーマー(`recsys_model.py` + `grok.py`)。**層数は設定駆動**で、README 同梱のミニモデルは 2 層・4 アテンションヘッド、デモスクリプトは `num_layers=2`(`run_ranker.py:51` / `run_retrieval.py:58`)、テストは `num_layers=1`。`num_layers=4` はリポジトリ内に一切存在しない(「4層」はアテンションヘッド数=4との取り違えに注意)。パーソナライズはハッシュ化されたエンゲージメント履歴埋め込みが主で駆動され、ユーザーベクトルは履歴トークン(投稿 + 著者 + 行動種別 + dwell)の**マスク付き平均プール**を L2 正規化したもの。手作りスコアの中心は消え、`RankingScorer` の線形和も「ML が出した確率」を束ねる薄い層になっている。
- **Xユーザー/クリエイターへの影響**: フィードは「どんな属性か」ではなく「あなたが実際に何にエンゲージしたか」に強く従う。プロフィール操作より**行動の蓄積**が効く。反面、モデルの系統的バイアスは temperature≈1e-6 の決定論的判定(grox)も相まって、全マッチ内容に一様に適用される。

### 3.2 マルチアクション予測 + 重み付けスコア

- **メカニズム**: Phoenix は行動ヘッドを sigmoid(=独立マルチラベル)で出す。**デモモデルと本番ランカーでヘッド集合が異なる**点に注意:
  - **Python デモモデル**(`runners.py` の `ACTIONS`、`num_actions=19`): favorite, reply, repost, photo_expand, click, profile_click, vqv, share, share_via_dm, share_via_copy_link, dwell, quote, quoted_click, follow_author, not_interested, block_author, mute_author, report, dwell_time の**19離散ヘッド**(19番目 dwell_time は離散位置)+ **連続8ヘッド**(`CONTINUOUS_ACTIONS`、`num_continuous_actions=8`)。`quoted_vqv` / `not_dwelled` / `click_dwell_time` は**含まない**。負のヘッドは `NEGATIVE_FEEDBACK_INDICES=[14,15,16,17]` の**4個**(not_interested, block_author, mute_author, report)。
  - **本番 Rust ランカー**(`ranking_scorer.rs` の `ScoringWeights`): 上記に加え `quoted_vqv`・`not_dwelled` と連続の `dwell_time`/`click_dwell_time` を**追加で消費**する(=本番モデルはデモと異なるヘッド集合)。`RankingScorer::compute_weighted_score` は `Σ P(action)×weight`。**負のヘッド**(not_interested, block_author, mute_author, report, **not_dwelled** の5個)は negative_sum として減算され、`offset_score` が net-negative 投稿を小さな正の帯に再スケールして最下部へ沈める(必ずしも削除はしない)。
- **重要な注記**: 負の減算は home-mixer の `ranking_scorer.rs` に実装されている。一方、Phoenix 側デモ `run_pipeline.py` の重み付け和(fav×1.0 + reply×0.5 + rt×0.3 + dwell×0.2)は**負のヘッドを一切減算していない**。デモモデルの負ヘッド 14–17 は推論はされるが、このスナップショットのデモ順序付けには使われない。本番のスコア式・重み値は設定駆動で本リポジトリには無い(要確認)。
- **Xユーザー/クリエイターへの影響**: モデルが「like/repost/share/reply/dwell されそう」と予測する投稿が押し上げられ、クリエイターはエンゲージメント最大化型の投稿(特に like を誘発する内容)へインセンティブづけられる。ユーザー側の block/mute/report/「興味なし」/スクロール(not_dwelled)は、類似コンテンツの抑制として効く(home-mixer 経路)。like 偏重が実際どれほど強いかは重み値次第(要確認)。
- **動画の条件付き加点**: vqv(video-quality-view)の重みは動画尺が閾値を**超過**(厳密に `video_duration_ms > MIN_VIDEO_DURATION_MS`)しない限り0にゲートされる。最低尺を満たさない短尺クリップは動画視聴クレジットを得られない。ただし本番の重み関数(`crate::util::candidates_util::vqv_weight` / `quoted_vqv_weight`)本体は本リポジトリに含まれず、ゲートの意図はデッドの `weighted_scorer.rs`(`> ? VQV_WEIGHT : 0`、厳密に `>`)から推定したもの(要確認)。

### 3.3 In-network(Thunder)と Out-of-network(Phoenix retrieval)の混合と発見性

- **メカニズム**: Thunder は follow グラフのみを供給キーとし、投稿は `author_id` で索引され、呼び出し側のフォロー一覧に含まれる著者からのみ候補になる。ランキングは recency のみで ML なし。対して Phoenix retrieval は follow グラフ非依存で、コーパス全体(デモは約537Kのスポーツ投稿。ただしこれは `phoenix/README.md` 記載の数値で、実データ `sports_corpus.npz` は約135バイトのプレースホルダ zip であり実体は非同梱)に対する post+author 埋め込み類似度で引くため、フォローしていないアカウントの投稿も浮上する。`RankingScorer::effective_oon_weight` が `in_network==false` の候補にのみ乗算し、OON を in-network 相対で再スケールする: 通常は `OonWeightFactor`、topic クエリでは `TopicOonWeightFactor`、条件を満たす新規ユーザーは `NEW_USER_OON_WEIGHT_FACTOR`(いずれも数値は要確認)。
- **Xユーザー/クリエイターへの影響**: フォロワーを増やすと in-network 供給が直接増える(Thunder はフォローされた分だけ配信対象が増える)。一方、フォロー外への到達は**エンゲージメントで学習された埋め込み類似度**が握るため、あるトピック/著者に反応が集まると look-alike 層へ増幅到達する。トピックフォロワーや新規ユーザーは OON 係数が異なり、発見コンテンツ対フォローコンテンツの比率が変わる。OON 係数の設定次第で「発見の窓」の広さが決まる(要確認)。

### 3.4 Author Diversity Scorer による多様性制御

- **メカニズム**: `RankingScorer::apply_author_diversity` は候補を重み付けスコア降順に並べ、各著者の N 番目の出現に `multiplier = (1-floor)×decay^position + floor` を掛ける。1本目はほぼ無減衰、同一著者の2本目・3本目…は幾何級数的に `floor` へ減衰する。OON 調整の前段で weighted score に適用。`decay`/`floor` は設定(値は要確認)。VMRanker 有効時は DPP(determinantal point process)多様性でさらに類似投稿を de-dup する。
- **Xユーザー/クリエイターへの影響**: 単一の多投稿アカウントが1回のフィード更新を独占できない。多投稿の限界効用は逓減し、リーチを稼ぐには「同一著者の連投」より「多くの著者にフォロー・エンゲージされること」が有利。ユーザー体験としては著者の多様性が担保される。

### 3.5 Ads blending(広告挿入・ブランドセーフティ)

- **メカニズム**: `BlenderSelector` が投稿/広告/who-to-follow/prompts/push-to-home に分割し、`AdsBlenderType` で `safe_gap`(SafeGapAdsBlender)か既定の `PartitionOrganicAdsBlender` を選ぶ(本番値は要確認、既定は後者)。いずれも**5投稿(MIN_POSTS_FOR_ADS)未満なら広告を挿入しない**。広告間隔は既定でおよそ3投稿ごと(min gap 2)、末尾広告は必ず除去され、フィードが広告で終わらない。ブランドセーフティ: 投稿の `BrandSafetyVerdict`(Unspecified/Safe/LowRisk/MediumRisk)で、MediumRisk(NSFW/gore/DO_NOT_AMPLIFY 等、または Grok 未採点、または PTOS カットオフ以降で未レビュー)に隣接する gap には広告を置かない。PartitionOrganic はさらに、広告自身の `AdAdjacencyControl`(BsrLow/BsrIas リスク、ブロックハンドル、ブロックキーワード)が隣接投稿と衝突する広告を落とす。
- **Xユーザー/クリエイターへの影響**: 広告は性的/暴力的/do-not-amplify コンテンツの隣には出ない。**Grok の内容理解ラベルを欠く投稿(または未レビューの新規投稿)は MediumRisk 扱い**となり、広告が避けるため、広告密度の高いフィードでは未分類・新規コンテンツが間接的に不利になりうる。push-to-home は index 0 固定、prompts と who-to-follow も固定位置に挿入され、エンゲージメントスコアに関係なく一等地を占める。

### 3.6 Grox によるスパム/安全性(PTOS)分類と可視性

- **メカニズム**: grox は Kafka ストリーム経由で投稿ごとに「プラン」を並列実行し、Grok VLM/埋め込みモデルで分類する。どのプラン/フィルタに乗るかで分析内容が決まる。オリジナル(非返信)かつ非保護の投稿は SAFETY_PTOS_DELUXE の対象になる(「人気」はコード上の deluxe ゲートではない——POPULAR トピックは POST_SAFETY にマップされる)。会話下の返信については、SPAM_COMMENT と REPLY_RANKING は同一の `PostStreamTaskGenerator`(CONTENT_UNDERSTANDING_REALTIME_UNIFIED_POSTS)から**両方注入**され、低/高フォロワーの振り分けは「どのストリームか」ではなく `task_filters.py` の `TaskSpamFilter`(会話両者がフォロワー閾値以下で対象)/ `TaskReplyRankingFilter`(いずれかが閾値超で対象)が行う。2段階の安全性 PTOS 分類(temperature=1e-6 の決定論)で7カテゴリ(暴力メディア/アダルト/スパム/違法規制行為/ヘイト・虐待/暴力的言論/自傷)を判定し、`isGore/isNsfw/isSoftNsfw/isSpam` などの boolean フラグとモデレーションラベルを付与する。フラグは既存注釈と OR マージされ**一度立つと固着**する。banger/品質スコア(quality_score >= 0.4 で正、slop_score は int フィールドだが値域の enforcement は可視コードに無く要確認)、reply ランキング(histogram バケット 0–3。「0.0=スパム扱い」の意味付けは可視コードに分岐が無く要確認)、domain 236 の grok topic エンティティ、1024次元マルチモーダル埋め込みを生成する。
- **Xユーザー/クリエイターへの影響**:
  - アダルト/gore/スパム/違法投稿は自動でフラグ + ラベルが付き配信が減る。誤ラベルはラベル削除なしには剥がしにくい。
  - **同一の返信でも会話の規模で扱いが変わる**: 低フォロワー同士の会話下ではスパム自動判定・ラベル対象になりうる一方、大アカウント会話下では 0–3 の品質スコアで序列化される(0.0 の意味付けは要確認)。大アカウントでは実質的な返信ほど有利、低努力ほど不利。
  - grox の付けたトピックカテゴリ(domain 236)が retrieval のマッチキーになる(`inferred_grok_topics_query_hydrator.rs` / PhoenixTopicsSource が消費)ため、**誤分類・過少分類はフォロー外到達可能な相手を変える**。
  - **保護アカウントは埋め込み対象外**。一方、**返信も埋め込みされ** Manhattan(strato sink)に書き込まれる: 主 V5 ストリームの sink(`TaskWriteMMEmbeddingSinkV5SkipKafkaForReplies`)では返信の **Kafka 公開のみスキップ**され、公開は専用の for-reply ストリーム(`PlanPostEmbeddingV5ForReply` / `MM_EMB_V5_FOR_REPLY`、sink は非スキップ)が担う。よって返信は埋め込みされ公開もされる(「返信は類似度検索での露出がオリジナルより少ない」はコーパス構成が本リポジトリに無いため裏付け不可=不明)。動画は ASR(音声書き起こし)が埋め込みに折り込まれ、話し中心の動画の発見性が上がる。
  - 各投稿は60秒に1回しか再分析されない(TTLCache)。連続編集・再投稿は窓内で再分類されず、最初に見られた状態が反映される。
  - 具体的なフォロワー閾値やラベル→可視性(hard filter / soft down-rank / interstitial)の対応は grox 外(Strato ラベルサービス / VFFilter)にあり、down-rank の大きさはコードからは導けない(要確認)。

### 3.7 Candidate isolation とスコアの一貫性/キャッシュ性

- **メカニズム**: ランキングトランスフォーマーの `make_recsys_attn_mask`(`grok.py`)は causal マスクから候補間ブロックをゼロにし、自己注意対角のみを再付与する。結果、各候補は user + history + 自分自身にのみ注意し、**同じバッチの他候補には注意しない**。よって候補のスコアはバッチ構成に依存しない。加えて `candidate-pipeline` の Selector は単一 float の降順ソート(NaN は Ordering::Equal で安定)。ハイドレーションはキャッシュ層あり。
- **Xユーザー/クリエイターへの影響**: スコアは競合独立で、バッチを混雑させて相対順位を操作することはできない。順序は再現的・安定的で、キャッシュ再利用も効く。ただし価値モデル(VMRanker)が有効な場合は、透明な線形スコアが不透明な外部スコア + DPP で置換され、公開重みでは説明できない順序・de-dup が生じる(EnableVMRanker が本番でオンかは要確認)。

### 3.8 フィルタ群(年齢・ミュート・既読/既配信・重複)による露出制御

- **メカニズム**: `candidate-pipeline` では**除去は Filter ステージだけ**で行われ、`run_filters` が各フィルタの生存者だけを次へ渡す逐次連鎖。最終集合は全フィルタの keep 集合の積。除去は**スコアリング前**に起き、切られた候補は二度と選ばれない。ハイドレータ/スコアラは候補を落とせない契約。事後(可視性・安全性)フィルタは選ばれた top-K のみに走り、削られると補充なしでフィードが縮む。具体的なフィルタ(AgeFilter, AuthorSocialgraphFilter, MutedKeywordFilter, PreviouslySeen/ServedPostsFilter, Dedup 系, VFFilter 等)の閾値・ロジックは home-mixer/filters/ 側(本コンポーネント外、要確認)。
- **Xユーザー/クリエイターへの影響**: block/mute した著者、ミュートキーワード、既読・既配信投稿は、どれだけ関連性が高くても**絶対に**表示されない(スコア減点ではなく除去)。ブロック/ミュートされたクリエイターはそのユーザーに到達できず、ユーザーのミュートキーワードは自分に対する恒久的な盲点を作る。配信済み履歴が非同期で書かれるため、セッションをまたぐと既配信が除外され新鮮な投稿が出続ける = クリエイターは**セッションあたり概ね1回の露出機会**。

## 4. クリエイター/ユーザーへの実務的示唆

**露出を増やす行動(クリエイター側):**

- **オリジナル投稿・トップレベル返信を優先する**: Thunder は返信・リポストを secondary バケットに落とし、返信は「親がオリジナル」か「会話ルート宛かつフォロー中ユーザー宛の1段深さ」でのみ生存。深いスレッド返信・見知らぬ相手への返信は落ちる。
- **エンゲージメント(特に like)を誘発する内容**: 最終順序は予測 like 確率に強く引かれる可能性(Phoenix デモでは fav 重み最大)。reply/repost/share/dwell も正だが、like 偏重の度合いは本番重み次第(要確認)。
- **最低尺を超える単一動画**: vqv クレジットは動画尺が閾値を**超過**(`> MIN_VIDEO_DURATION_MS`)する場合に得られる(本番の vqv 重み関数本体は本リポジトリ外、要確認)。Thunder の video バケットも最低尺ゲートを持つが、「単一動画のみ」という限定は本リポジトリのコードからは確認できない(要検証)。短尺・動画返信は動画扱いされにくい。話し中心の動画は ASR が埋め込みに入り発見性が上がる。
- **フォロワー会話規模を意識**: 大アカウント会話下の返信は品質スコア序列で substantive さが報われる。低フォロワー会話下の低品質返信はスパム判定されうる。
- **Grok 品質(banger)を満たす**: quality_score >= 0.4 で高品質フラグ、slop 判定を避ける。内容理解ラベルが付く(= 正しく分類される)ことは広告隣接・トピック到達の両面で有利。
- **投稿タイミングと頻度(in-network)**: Thunder は recency 決定・retention 窓(コード上2日、本番要確認)。フォロワーのアクティブ時間帯に、窓内で新鮮さを保つと in-network 供給に乗りやすい。ただし著者別上限があり、連投の限界効用は逓減。

**露出を減らす/自分の発見を狭める行動(ユーザー側):**

- **ネガティブシグナルは効く(home-mixer 経路)**: block/mute/report/「興味なし」/スクロールで見送る(not_dwelled)は、そのモデル経路で類似コンテンツを最下部へ沈める。ミュートキーワードは恒久的除去。
- **エンゲージメント履歴が発見を決める**: like/reply/repost だけでなく**滞在(dwell)だけでも**ユーザーベクトルに反映される。無反応に見ていた内容も学習される点に注意。行動種別ごとに(like と reply と repost で)ベクトルが違う方向へ動くため、どう反応するかが発見の方向を変える。
- **新規/低履歴ユーザー**: 別モデルクラスタ(cold-start)と別 OON 係数で最初のセッションから体験が異なる。

**注意(不確実性):** 重み値・OON 係数・多様性の decay/floor・retention 窓・Top-K・広告間隔・フォロワー閾値・安全性閾値・cluster ID などの**数値はすべて設定駆動で本リポジトリには含まれない(要確認)**。これらの定数・重み関数の多く(スコア重み、OON 係数、vqv 重み関数、各種閾値、cluster ID 等)は、`lib.rs` に未宣言でリポジトリ非収録の `params` / `util` / `clients` モジュールにあり、本コンポーネントは部分公開スナップショットである。上記の方向性は構造(コードの符号・分岐)から言えるもので、強度は本番設定に依存する。

## 5. 今後の監視観点(このルーティンが重視すべき変更)

このベースラインに対し差分を見るとき、以下が変わるとユーザー行動・クリエイター露出に大きく効く。優先度順に注視する。

- **スコア重み(最重要)** — `home-mixer/scorers/ranking_scorer.rs` の `ScoringWeights::from_params` と各行動重み(Favorite/Reply/Retweet/…/Report/NotDwelled)、`NEGATIVE_SCORES_OFFSET`。負のヘッドの符号・有無、like 偏重の増減。Phoenix 側 `run_pipeline.py:355-361` のデモ重み式に負ヘッドが加わるか。
- **OON 係数** — 同ファイルの `effective_oon_weight`、`OonWeightFactor` / `TopicOonWeightFactor` / `NEW_USER_OON_WEIGHT_FACTOR`。値が動くと「発見 対 フォロー」比率が直接変わる。
- **著者多様性** — `apply_author_diversity` / `diversity_multiplier` の `AuthorDiversityDecay` / `AuthorDiversityFloor`。連投の限界効用と著者集中度が変わる。
- **VMRanker の有効化と DPP** — `vm_ranker.rs`、`EnableVMRanker`、`DppParams{theta, max_selected_rank}`、`value_model_id`。オンになると透明な線形スコアが外部モデルで置換され、公開重みで説明できなくなる。有効/無効の切り替えは監視最優先の一つ。
- **Phoenix 予測ヘッドの増減** — `recsys_model.py` / `runners.py:ACTIONS`(デモは19離散ヘッド + 8連続)。新ヘッド追加・負ヘッドの扱い変更・ヘッド index マッピング変更(現状 `run_pipeline.py` と `runners.py` で index 順が不一致=要確認)。また本番 Rust ランカー(`ScoringWeights`)はデモにない `quoted_vqv`・`not_dwelled`・`click_dwell_time` を持つため、デモと本番のヘッド集合の乖離自体も追跡対象。
- **retrieval の Top-K とコーパス構成** — `recsys_retrieval_model.py:_retrieve_top_k`、`run_pipeline.py` の `top_k_retrieval`(デフォルト200)、candidate tower の入力(現状 post+author のみ)。K や tower 入力が変わると発見の幅が変わる。

差分評価の原則: **符号・分岐・ステージ順序の変化**(何が正/負か、除去がスコア前か後か、置換か減衰か)はユーザー行動への効き方を質的に変えるため最優先。**数値定数の変化**は方向は同じで強度が変わるため、値が本リポジトリ外(`params`/`util`/`clients` 等の非収録モジュールや設定)にある以上、差分がコードに現れたら「どの行動/どのネットワーク由来/どの安全性クラスが有利・不利に振れるか」を上記マッピングに照らして評価する。
