### 知っておくと良いこと（まだ効いていない準備段階の2件）

### 2. 候補専用packing領域と候補専用attentionカーネル（学習・推論の計算方式）

**メカニズム（コード根拠）**

- `phoenix/xrex/data/recsys/sequence_packing.py:157-166` で `SequencePackedLayout` に9つの新フィールド（`candidate_cu_seqlens` / `candidate_key_starts` / `candidate_key_counts` / `prefix_positions` / `candidate_token_to_slot` / `candidate_slot_to_token` / `token_to_source` / `source_to_token` / `dropped_candidate_slots`）が追加された。
- `sequence_packing.py:628-` の `_candidate_region_layout()` が、従来「ユーザーごとの区間に履歴と候補を混ぜて詰める」レイアウトを、**「履歴領域」＋「候補領域」の2ブロック構成**に組み替える。候補は16トークン単位（`CANDIDATE_TOKEN_ALIGN = 16`, `sequence_packing.py:173`）に整列して詰められる。
- `phoenix/xrex/cutedsl/ranker_candidate_attention_fa4.py`（新規369行）が候補領域専用のFlashAttentionカーネル。`ranker_candidate_attention_fa4()` 内の `candidate_inputs()` で、候補クエリに対するkey/valueを「そのユーザーの履歴キー（`key_starts` / `key_counts` で範囲指定）」と「自分自身のトークン（`k_self` / `v_self`）」に分離する。
- **候補間の相互参照がないことの根拠：** `ranker_candidate_attention_fa4.py:217-220` の `self_scores()` は `jnp.einsum("thd,thd->th", q, k_rep)` で**同一トークン位置どうしの内積のみ**を取る。候補クエリが見るのは「自分の1トークン」＋「そのユーザーの履歴」であり、他の候補投稿のキーは参照されない。
- H100でのみ有効（`ranker_candidate_attention_fa4.py` 内で `arch != 90` なら `NotImplementedError`）。
- `phoenix/xrex/models/recsys_feature_prep.py:1284-1298` で、新レイアウトの場合はユーザー・履歴・候補のトークンを `token_to_source` による一括gatherで組み立てる経路に切り替わる。勾配は `_gather_rows` のカスタムVJP（`recsys_feature_prep.py:1255-1273`）で逆写像 `source_to_token` 経由で戻す。
- `phoenix/xrex/models/recsys_model.py:3139` で `seq_starts` の算出を `layout.cu_seqlens[:, :-1]` から `packed_prefix_positions(layout)`（`sequence_packing.py:176-179`）に変更。新レイアウトでは区間先頭＝ユーザートークン位置ではなくなるための修正。
- `phoenix/xrex/models/transformer.py:765-782` で、新レイアウトのときに attn-loss / ffn-loss / act-l2-loss の記録値を `num_tokens / regular_num_tokens` 倍して補正。**トークン数が変わっても損失の記録値が旧レイアウトと比較可能になる調整**で、学習そのものの目的関数を変えるものではない。

**Xユーザー/クリエイターへの影響**

- **スコアの出し方の意味は変わらない。** 候補1件あたりの計算入力（その人の履歴＋その投稿自身）は従来と同じで、速くなっただけ。
- **「同じバッチの他の候補に影響されない」性質が維持されたことが明示的に確認できる。** リスト全体を見て順位を決める方式（listwise）への移行は**起きていない**。クリエイターにとっては「自分の投稿の採点は、同時に採点された他人の投稿の強さに左右されない」が今回も成立。
- 数値誤差レベルの差は生じ得る（attention計算の実装が別カーネルになるため）が、ランキング順位に体系的な偏りを生む変更は読み取れない。

### 3. 学習時の候補間引き（候補リストの後ろ側が落ちる）

**メカニズム（コード根拠）**

- `sequence_packing.py:579-626` の `_drop_candidates_over_budget(seq, slots_per_user, budget)`。
- 呼び出しは `sequence_packing.py:473-486`。`candidate_tokens_per_user` が指定されたときのみ動き、そこには **`assert dist is not None and transformer_candidate_seq_len > 0, "candidate_tokens_per_user is training-only and needs transformer candidates"`** という明示的な「学習専用」アサーションがある。推論経路（`model_runner.py`）では `num_microbatch` / `use_async_emb` / `seqpack_drop_empty_candidates` / `overlap_step_host_work` を設定から**取り除いている**（`phoenix/xrex/inference/model_runner.py:800-803`）。
- 間引きの順序：`sequence_packing.py:596-607` で `np.argsort(-slot_in_user[valid_slots], kind="stable")`、つまり**ユーザー内のスロット番号が大きい（＝候補リストの後ろの）候補から先に捨てる**。
- 捨てすぎた分は `sequence_packing.py:608-619` で、スロット番号の小さい順に予算が許す限り戻す。16トークン境界（`_aligned_candidate_tokens`）をまたがない範囲での戻しなので、**最終的にリストの後ろ側が落ちる傾向は残る**。
- 1ユーザーあたりの候補トークン枠は `[32, 128]` の2択（`phoenix/xrex/train/trainer_recsys.py:292`）。各ステップで必要量を全プロセスで `max` 合意してから（`trainer_recsys.py:424-442`、`candidate_tokens_per_user_needed()` は `sequence_packing.py:195-203`）小さい方で足りれば32を選ぶ。
- **履歴とのトレードオフ：** `trainer_recsys.py:408-412` の `_history_mean_len()` は、候補枠を128に広げたステップでは履歴の平均長を `128 - 32 = 96` トークン分**短くする**。固定長のパック列の中で候補と履歴が席を取り合う構造。

**Xユーザー/クリエイターへの影響**

- **影響度は小。ただし原理上はゼロではない。** 学習データの構成が変わるため、「候補リストの後ろに置かれがちな投稿」の学習事例が相対的に減る方向。候補リストの並び順が何で決まるか（retrieval側の順序か、無作為か）は今回の差分からは読み取れないため、**実際に偏りが生じるかは判断できない（要確認）**。
- 候補が多いステップでは履歴が96トークン短くなるため、**「長期の閲覧履歴に依存する予測」の学習事例がそのステップでは薄くなる**。ニッチな長期興味の学習に理論上わずかに不利に働き得るが、2段階の枠を動的に選ぶ設計（必要なときだけ128）なので、影響は限定的と読める。
- **推論（実際にフィードを作るとき）には適用されない**ため、「自分の投稿が配信時に予算切れで捨てられる」ことは起きない。
