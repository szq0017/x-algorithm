## 非IT精通者向け：今日の差分を踏まえた運用方法のまとめ

今日は**この監視を始めて以来、最も大きな「ランキングの設計思想の変更」**が入りました。まだ本番の既定ではOFFですが、**計算式そのものを足し算から掛け算に変える新方式**が、おすすめ（For You）に関わる3つの処理系すべてに実装完了しています。行動指針は以下のとおりです。

- **「とりあえず長く見てもらう」だけの投稿は、近い将来かなり弱くなる前提で組み替えてください。**
  これまでのスコアは「いいね確率×重み ＋ リプライ確率×重み ＋ … ＋ 滞在時間×重み」という**足し算**でした。足し算なので、いいね・返信・リポストがほぼ0でも、滞在時間が長ければスコアを稼げました。
  新方式は「**（スキップされにくさ）×（エンゲージ系の合計）×（1＋滞在時間）**」という**掛け算**です。掛け算なので、**エンゲージ系が0に近いと、滞在時間が何倍でも最終スコアはほぼ0**になります。
  → 長い画像・長文・引き伸ばし動画で「滞在時間だけ」を稼ぐ運用（いわゆるドウェル・ベイト）は、有効化されると急激に効かなくなります。逆に「**滞在もされ、かつ、いいね/返信/リポスト/ブックマークのどれかが実際に起きる**」投稿が、従来より強く伸びます。

- **「スキップされないこと」が、減点から“掛け率”に格上げされました。**
  従来は「読まれずに飛ばされた（not_dwelled）」が -0.02 という小さな減点でした。新方式ではこれが**全体にかかる掛け率**になります。つまり**冒頭で飛ばされる投稿は、他がどれだけ良くても評価が立ち上がらない**構造です。
  → 1行目・1枚目・最初の2秒の設計（フック）の重要度が、構造上はっきり上がります。

- **同じジャンルの連投が、「見た目が似ている」判定から「カテゴリが同じ」判定へと変わりつつあります。**
  これまでの「似た投稿を連続させない」仕組みは、投稿の埋め込みベクトル（＝見た目・文面の数値的な近さ）だけを見ていました。今日、**投稿に付いている意味ID（セマンティックID）の第1階層＝大分類が、直前に見た投稿と同じなら一律で加点ペナルティ**を与える仕組みが追加されました（既定OFF、専用の照会サービスも新設）。
  → 文面や画像を変えて「似ていないように見せる」回避は通りにくくなります。**大分類レベルで話題を散らす**ことが、今後の実質的な対策です。

- **広告の本数が、ユーザーの“使い込み度合い”別に間引けるようになりました（既定OFF）。**
  新規ユーザー〜ヘビーユーザーを8段階に分け、段階ごとに「広告枠を何％残すか（最低50％）」「広告の間隔を何投稿あけるか」を個別指定できる仕組みが入りました。**Premium / Premium+ は対象外**（もともと広告が少ないため）です。
  → 無料ユーザーのうち、ライト層・新規層の広告が減らされる可能性があります。広告出稿側は「同じ予算でも、届く層が偏る」前提で見る必要があります（配分値は公開コードに無いため **要確認**）。

- **Grokの「おすすめタスク」枠の「×（閉じる）」が、ようやく実際に効くようになりました。**
  これまでは、設定上の表示間隔が0時間だと**ユーザーが閉じた記録そのものが無視され、閉じても出続ける**状態でした。今日の修正で、閉じた記録は常に尊重されます。
  → この枠が邪魔だった人は、改めて「×」を押せば消えます。

- **多画像投稿の安全性審査は、昨日のレポートの想定より“対象が絞られました”。**
  5枚以上の画像を4枚ずつに分割してAI審査する仕組みに、**「いいね256件以上」または「過去にアダルト系の違反判定が付いている」投稿だけを対象にする**という条件が追加されました。すでにNSFW判定済みの投稿は対象外です。
  → 小規模アカウントの通常の多画像投稿は、この分割審査には回らなくなりました。昨日「エンゲージメントに関係なく対象」と書いた点は、**この分割審査フローについては取り消し**です。

- **「クリックしただけ」の長時間滞在が、検索・推薦の“お手本データ”から外れました。**
  候補を集めてくる段（リトリーバル）の学習ラベルで、「長く滞在した」を正解として扱う条件が厳しくなりました。**動画をしっかり見た場合を除き、10秒以上の滞在＋クリック/画像拡大以外の実エンゲージメントが必要**になります。
  → サムネや1枚目で釣って開かせるだけの投稿は、**そもそも候補として集められにくくなる**方向です。

- **今日は、スコア重み（いいね/返信/リポスト等の係数）・Thunderのリテンション窓・OON係数・著者多様性のdecay/floor・retrieval の Top-K の数値変更はありません。** 既存の運用方針の数値部分は、そのままで問題ありません。

## 変更サマリ

1. **掛け算型バリューモデル（multiplicative value model）を新設**。`score =（スキップ回避率）×（エンゲージ合計＋バイアス）×（1＋滞在時間）`。既定は従来の `"weighted"` のままだが、**CPU側（home-mixer）・vm-ranker・GPU側ページデコード（page_rl）の3経路すべてに同一式で実装完了**。
2. 掛け算モードでは**キャッシュ済みスコアを使い回さず必ず再計算**する分岐が全経路に追加（`weighted_score` をリクエストから除外）。
3. **DPP（多様性）に意味ID（SID）レベル1の同一カテゴリペナルティ `sid_lambda` を追加**。直前に配信した投稿の L1 コードを引くための **新サービスクライアント `vm-ranker/sid_client.rs`（gRPC、30msタイムアウト、1000万件キャッシュ、48hTTL、サーキットブレーカ付き）を新規追加**。既定0.0でOFF。
4. **広告量のユーザー状態別間引き `home-mixer/ads/user_load.rs` を新設**（8段階の user_state ごとに残存率50〜100%・間隔を指定、Premium系は除外、ForYou限定）。あわせて `UserDemographics` 照会を行う新クエリ水和器を For You パイプラインに追加。
5. **「広告のみのタイムライン」モードを追加**（ID許可リスト方式、既定OFF）。オーガニック投稿の取得自体を止め、広告だけを順に配信する社内検証用経路。
6. **Grokフレームの「×（ユーザーによる非表示）」が、表示間隔0時間の設定下でも効くよう修正**（従来は無視されていた）。
7. **grox の多画像安全性審査（many_media）を「いいね256件以上」または「過去にアダルト違反判定あり」に限定**。NSFW既判定は除外。あわせてチャンク審査を**逐次→最大5並列**に変更。
8. **`VMRankerSendDppHistory` が true → false に差し戻し**（昨日 ON になった本番既定のロールバック）。上限50件は維持。
9. **リトリーバル学習の長滞在ラベルから「クリック/画像拡大のみ」を除外**（`ld_label_exclude_clicks`、`xrecsys_two_tower_home_only` 構成で有効）。
10. **投稿→ユーザー方向のリトリーバル RPC `RetrieveTopKUsers` を新設**（Python実装は未実装、Rustホストの `--enable-post-to-user` 限定）。
11. 滞在時間予測（CREAD）のデコードに **`power`（0〜1の凹変換）/`scale`** を追加、リクエスト単位の上書きも可能に（既定 1.0/1.0 = 従来どおり）。
12. `RankingScoreWeights` に **`completionWeight`（tag 16）** を追加（home-mixer 側は 0.0 固定の配管のみ）。ページRL用の**クリティック単独学習モデル `page_critic_only.py` を新設**、配信時デコードに `mode: actor | critic` の選択肢を追加。

## 変更点ごとの詳細

### 1【大】スコアの合成が「足し算」から「掛け算」に切り替え可能になった（既定OFF・全経路実装完了）

**メカニズム**

- 新パラメータ 4 本（`home-mixer/params/param.rs:578-601`、`vm-ranker/params.rs:140-160`）:
  - `ValueModelMode`（`rust_home_mixer_value_model_mode`）既定 **`"weighted"`**。`"multiplicative"` で新方式に切替。
  - `NotDwelledPowerExponent`（既定 **0.0**）、`NotDwelledPowerOffset`（既定 **0.0**、下限 `1e-2` に丸め）、`MultiplicativeVmEngageBias`（既定 **0.0**）。
- 分岐点：`xai-value-model/scoring.rs:67-73` — `fuse_heads()` が `weights.multiplicative` で分岐。真なら `multiplicative_score()`。
- 新しい式（`xai-value-model/scoring.rs:101-114`）:

  ```
  engage = engage_sum(...) + engage_bias
  if engage < 0  → offset_score(engage)            // 負なら従来の負値処理にフォールバック
  else           → offset_score( skip × engage × time )
  ```
  - `engage_sum`（`scoring.rs:89-96`）= 従来の重み付き項の合計から **`dwell_time` と `not_dwelled` の2項を除外**したもの。つまり「いいね・返信・リポスト・引用・共有・ブックマーク・プロフクリック・VQV等」の合計。
  - `skip`（`scoring.rs:75-87`）= `(p_not_dwelled + offset)^exponent`。`exponent == 0.0` または `not_dwelled_score` 不在/非有限なら **1.0（無効）**。`offset` は `MIN_NOT_DWELLED_POWER_OFFSET = 1e-2`（`weights.rs:5`）で下限が効く。
  - `time`（`scoring.rs:97-99`）= `1.0 + max(dwell_time 重み付き項, 0.0)`。
- 正規化側も分岐（`xai-value-model/weights.rs:92-114`）：掛け算モードでは負値側の合計から `not_dwelled` を外し（`multiplicative_negative_sum()` は `not_interested + block_author + mute_author + report` のみ）、総和に `engage_bias` を加える。`offset_score`/`unoffset_score` は `offset_total_sum()` 経由で自動的に正しい分母を選ぶ（`scoring.rs:282-299`）。
- 設定の流し込み：`weights.set_multiplicative(mode, exponent, offset, engage_bias)`（`weights.rs:116-128`）を home-mixer（`home-mixer/scorers/value_model.rs:51-57`）と vm-ranker（`vm-ranker/scoring/value_model.rs:115-121`）の両方が呼ぶ。
- **GPU側（ページデコード／ページRL）にも同一式が実装**（`phoenix/xrex/models/page_rl.py`、`raw_mul = where(engage_b >= 0, skip * engage_b * time, engage_b)`）。プロトコルにも `notDwelledPowerExponent` / `notDwelledPowerOffset` / `engageBias` / `multiplicative` の4フィールドが追加（`phoenix/crates/serving/xai-recsys-proto/proto/recsys.proto:245-248`）。`home-mixer/scorers/page_decode_rerank_scorer.rs:24,36-41` で、掛け算モードのときだけこの4つを送る。
- 公式テスト（`xai-value-model/scoring.rs:603-640`）が式を明示：`favorite=0.5, p_fav=0.4, exponent=-0.5, offset=0.11, engage_bias=0.1, dwell=20, cont_dwell_time=0.1, p_not_dwelled=0.25` のとき期待値は `(0.36)^-0.5 × 0.3 × 3.0 + 0.001`。`report_score=0.05`（report重み -100）のケースはスコアが 0.002 未満に落ちることを確認している。

**Xユーザー/クリエイターへの影響**

- **最大の構造変化は「ゼロ掛け」**。従来の足し算では、エンゲージ予測が全部ほぼ0でも滞在時間項でスコアを積めました。掛け算では `engage ≒ 0` なら `skip × engage × time ≒ 0` です。**「見られるが何も起きない」投稿が、おすすめから事実上落ちます。**
- 逆に**相乗効果**が働きます。エンゲージ予測・スキップ回避・滞在のどれも「ほどほどに良い」投稿が、1項目だけ突出した投稿を上回りやすくなります。全方位に無難な投稿が有利、という方向です。
- **冒頭フックの価値が構造的に上がります。** テスト値のとおり exponent に負値（例 -0.5）を入れると、`skip = (p_skip + offset)^(-0.5)` は p_skip が小さいほど大きくなる **割り算型の掛け率**になります。スクロールで飛ばされる確率が高い投稿は、掛け率そのものが下がります。
- **ネガティブシグナルの殺傷力は維持**されます。`engage` が負（report / not_interested / block / mute の重みが効く）になった時点で掛け算を通らず、従来の負値処理に落ちます（`scoring.rs:103-105`）。通報されやすい投稿が救済されることはありません。
- **滞在時間は「ボーナス倍率」に格下げ**。`time = 1 + max(dwell項, 0)` は下限1.0なので、滞在が短くてもマイナスにはならず、長ければ倍率として乗る位置づけになります。「滞在を削られる」のではなく「滞在だけでは何も得られない」構図です。
- **既定はまだ `"weighted"`** なので、今日この瞬間のタイムラインは変わっていません。ただし**3経路すべてに実装が揃い、プロトコルのフィールドまで通った**状態は、A/B実験の直前段階と読むのが妥当です。

**メカニズム**

  - 候補に付いている `weighted_score` を**リクエストから落とす**（同 `:106-113`）、
  - さらに `debias` 入力の送信条件に `|| omit_cached_weighted_score` を追加（同 `:25-28`）。
- `home-mixer/scorers/vm_ranker.rs:67-71`、`xai-value-model/scoring.rs:412-418`、`vm-ranker/scoring/value_model.rs:187-189` — いずれも `Some(cached) if !weights.multiplicative => cached` という形に書き換えられ、掛け算モードではキャッシュを無視して再計算する。

**Xユーザー/クリエイターへの影響**

- おすすめタブは「前回ページ用に計算した候補」をキャッシュして再利用します。掛け算モードではこの再利用が止まり、**毎回スコアが引き直されます**。
- 結果として、**同じセッション内で下にスクロールしたとき・引っ張って更新したときの並び順が、従来より大きく動く**可能性があります。投稿のインプレッションが「最初のページに入れたかどうか」で固定されにくくなる、という意味ではクリエイターにとって再挑戦の機会が増える方向です。
- 一方で計算コストは増えるため、**本番適用時は Top-K など他のパラメータが同時に絞られる可能性**があります（公開コードに同時変更は無いため **要確認**）。

**Xユーザー/クリエイターへの影響**

- これまでの重複ペナルティは「埋め込みが近い＝文面や画像が実際に似ている」場合にしか効きませんでした。意味IDの L1 は**事前に学習されたカテゴリ（大分類）**なので、**書き方を変えても、画像を差し替えても、同じ大分類なら等しくペナルティ**になります。
- つまり「同じ話題を切り口を変えて連投する」という従来の回避策の効き目が落ちます。**有効な対策は、大分類そのものを跨ぐこと**に変わります。
- 影響範囲は**おすすめタブのみ**（DPP履歴送信は For You 限定のため）、かつ**直近に実際に配信された投稿との比較**です。フォロー中タブ・検索・プロフィールには効きません。
- ペナルティは `min(..., 1.0)` で飽和します。`sid_lambda = 1.0` だと「同一L1なら完全に重複扱い」になるため、**カテゴリ単位でページ内に1本しか入らないくらいの強さ**になり得ます。実運用値は不明（**要確認**）。
- 30msタイムアウト＋フェイルオープン設計のため、**照会が遅い/失敗したときは単に従来どおりの挙動に戻ります**。SIDが引けなかった投稿はペナルティ対象外になる＝取りこぼしは「緩い側」に倒れます。

- **引用投稿テキスト取得の条件化**：`QuotedPostTextHydrator` が **ミュートキーワードを設定しているユーザーにしか動かなくなった**（`home-mixer/candidate_hydrators/quoted_post_text_hydrator.rs:23-25`）。公式テストで明示（`:118-128`）。→ 引用テキストはミュート照合のためだけに取っていた、という設計の明文化。ミュート未設定ユーザーのレイテンシ削減。
- **候補のシリアライズ縮小**：`PostCandidate` の `Option` フィールド約60個に `skip_serializing_if = "Option::is_none"` を付与（`home-mixer/models/candidate.rs`）。公式テストで「省略」と「明示的null」が等価であることを検証（`:604-645`）。→ キャッシュ・ログのペイロード削減。**挙動変更なし**。
- **古さフィルタのリファクタ**：`AgeFilter` が `duration_since_creation_opt`（候補ごとに現在時刻を取得）から、**1回だけ `SystemTime::now()` を取って全候補に適用**する形に変更（`home-mixer/filters/age_filter.rs:20-31`）。ヘルパ実装が公開範囲外のため厳密な等価性は確認不能だが、挙動は同等と読める（**要確認**）。
- **多様性メトリクスの範囲修正**：クロスページ集計のウィンドウが現ページ内にしか掛からないケースを打ち切るよう修正（`home-mixer/side_effects/response_diversity_stats_side_effect.rs:396-400`）。**計測専用で、配信には影響しない**。
- **grox の同時実行数上限を撤去**：`TaskGeneratorConfig.max_in_flight` と `PriorityTaskGenerator._at_max_in_flight()` を削除（`grox/config/config.py:163`、`grox/core/generators/task_generator.py:71-113`）。→ 一部の grox フローの処理量上限が外れた。安全性判定のスループットに影響し得る（実運用の設定値が公開されていないため **要確認**）。
- **grox のGemma設定の整理**：`use_gemma: bool` を廃止し、`gemma_model_name: str | None` の有無で判定する形に統一（`grox/flows/ptos/classifier.py:477-492, 641-648, 727-735`、`grox/flows/ptos/task_safety_ptos_policy.py:33-55`）。`BACKFILL` のみ `None`。**判定ロジックは等価**（DELUXE は従来も Gemma を使わない経路に入るため）。

**Xユーザー/クリエイターへの影響**

- この節の項目は、いずれも**今日のタイムラインを変えません**。`completionWeight` と `mode: "critic"` は、**次に来る変更の予告**として記録しておく価値があります。
- 特に `completionWeight` は、**動画の「最後まで見たか」を独立した重みとして扱う準備**です。現在は `MinVideoDurationMs` / `VqvWeight` 経由で間接的にしか効いていません。これが0以外になった日は、動画クリエイターにとって大きな変更になります。

### 今日の差分全体から読み取れる方向性

**「滞在時間だけでは評価しない」という統一された意図**が、独立した3箇所から同時に入りました。

1. **ランキング側**（#1）：掛け算にすることで、エンゲージ0の投稿は滞在時間が何倍でもスコアが立たない。
2. **リトリーバル側**（#9）：クリック/画像拡大だけの長滞在は、学習ラベルから外す。
3. **滞在時間そのものの評価**（#11）：長滞在の価値を圧縮する凹変換を用意。

これは偶然の同時変更ではなく、**「ドウェル最適化の抜け道を同時に3方向から塞ぐ」という設計意図**と読むのが自然です。#1 と #11 はまだOFFですが、**#9 はすでに一部の学習構成でONです**。

クリエイターへの実務的な結論は単純です。**「開かせる」ことと「長く見せる」ことの価値が下がり、「実際に何らかの反応を起こさせる」ことの価値が上がります。** しかもそれは「反応が多いほど良い」という単純な加点ではなく、**「反応がゼロなら他が全部無駄になる」という掛け算の形**で入ります。

## 不確実な点（要確認）

- **掛け算モードの実際のパラメータ値**：`NotDwelledPowerExponent` / `NotDwelledPowerOffset` / `MultiplicativeVmEngageBias` はすべて既定0.0で、0.0 だと `skip = 1.0`（無効）になります。公式テストでは exponent = -0.5、offset = 0.11、engage_bias = 0.1 が使われていますが、**これがA/B実験で使われる値かは不明**です。式の形は確定していますが、効きの強さは確定できません。
- **掛け算モードが実験に入っているか**：`ValueModelMode` の既定は `"weighted"` です。公開されているのは**本番 feature-switch の既定値のミラー**であり、**特定のユーザー層に対する実験的な上書き（override）は公開範囲に含まれません**。したがって「既定OFF」は「誰にも適用されていない」ことを意味しません。
- **`DppWindowSidLambda` の実運用値**：既定0.0。項目8のとおり前提となる `VMRankerSendDppHistory` が今日OFFに戻ったため、現時点では SID ペナルティは**二重にOFF**です。
- **`sid_endpoint` の本番設定**：`--sid-endpoint` / `VM_RANKER_SID_ENDPOINT` が未指定なら機能自体が起動しません。本番で設定されているかは公開コードから判定不能です。
- **`AdsUserStateKeepPct` / `AdsUserStateSpacing` の実際の配分値**：既定は空配列。各 user_state にどの値が入るかは本番設定側にあり、公開されていません。また `AdsBlenderType` が本番で `"slot_spread"` かどうかも確定できません（他に5種類のブレンダーがあります）。
- **`AdsOnlyTimelineViewerIds` の中身**：既定は空リスト。実運用で誰が入っているかは不明です。
- **`ld_label_exclude_clicks` が本番モデルに効いているか**：有効なのは `xrecsys_two_tower_home_only` という学習構成です。これが現在配信中のリトリーバルモデルかどうかは公開コードから確定できません。他の two_tower 構成は既定 False です。
- **`RetrieveTopKUsers` が本番で有効か**：`--enable-post-to-user` フラグの状態は不明。Python 実装は明示的に未実装を返します。
- **Grokフレームの非表示期限**：テストでは30日（`NOW_MS + 30 * 24 * HOUR_MS`）が例示されていますが、実際の期限値は書き込み側（公開範囲外）が決めます。
- **`VMRankerSendDppHistory` の差し戻し理由**：ロールバックか実験の一時停止か、公開コードからは判定できません。3日分（11-13 → 11-16）の同期をまたいでいるため、途中の経過も見えません。
- **多画像審査の `get_fav_count()` のタイミング**：`favs >= 256` の判定が投稿後どの時点のいいね数を見るかは、呼び出し側の実装（公開範囲外）に依存します。投稿直後に判定されるなら、ほぼ常に `forced = False` 側に落ちます。
- **`AgeFilter` の厳密な等価性**：`duration_since_creation_opt` と `time_from_id_opt` の実装は公開リポジトリに含まれていません（`candidate-pipeline/component_library/utils.rs` が未公開）。性能リファクタと読めますが、未来日付の投稿・時刻スキュー時の扱いが完全に同一かは確認できません。
- **grox `max_in_flight` 撤去の実効**：撤去前にどの `task_generators` に上限が設定されていたかは本番設定次第です。安全性判定のスループットが上がる可能性はありますが、確定できません。
- **`completionWeight` / `mode: "critic"` の実運用**：前者は home-mixer 側で 0.0 固定、後者は新設の設定項目で、どちらも現時点で効果はありません。
