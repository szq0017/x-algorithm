## 非IT精通者向け・運用方法のまとめ（行動指針）

- **今日は「投稿の作り方を変えるべき変更」はありません。** ランキングの重み（何を評価してタイムラインを並べるか）は10日連続で無変更、広告の入り方も、grox のスパム／安全性判定の閾値も動いていません。昨日入った DMCA（著作権）テイクダウンの実効化と、多段返信スパム検知は**そのまま生きています**（撤回・緩和は入っていません）。昨日のレポートの行動指針はそのまま有効です。
- **小規模アカウント向けの「コールドスタート優遇」の対象が狭まりました。** フォロワーの少ないアカウントの新しい投稿を、いったん上位スロットに押し上げる仕組みがあります。この優遇を受けている実験グループの閲覧者について、**押し上げ対象が「Phoenix MoE という新しい推薦経路で拾われた投稿」だけに限定**されました。同じ小規模アカウントの投稿でも、従来の推薦経路で出てきたものは押し上げの対象外になります。
  - 実務的な意味：**小規模アカウントの投稿が「たまたま伸びる」経路が1本減りました。** ただしこれは限定的な実験（experiment）内の挙動で、全ユーザーの既定動作ではありません（実験の配信率は公開コードから読み取れません＝要確認）。
- **投稿を「作った直後の勢い」がスクロール中でも反映されやすくなりました。** タイムラインを下へ読み進めた（＝サーバ側でキャッシュ済みの投稿を返す）ときにも、小規模アカウントの投稿について**いいね／返信／リポスト／表示回数の最新値を取り直す**ようになりました。投稿直後に伸び始めた小さなアカウントの投稿が、以前より新鮮な数字でスコアリングされます。
- **一方で、コールドスタート優遇は「エンゲージメント数の取得スイッチ」が入っていないと動かなくなりました。** 従来はコールドスタートを有効にすれば数値取得も自動で走りましたが、この連動が切られました。運用側が片方だけ有効にすると優遇が無効化されます（利用者側の行動としては打ち手なし。優遇のオン／オフが以前より運用設定に左右される、という理解でOK）。
- **「ミュートワード（キーワードミュート）」が近くフィルタ側に来る予告が、コード中に明記されました。** 投稿本文が可視性フィルタまで運ばれる仕組みは既にあり、今日その本文フィールドに「今後のミュートキーワード規則のために保持」という注記が付きました。**現時点では何のフィルタにも使われていません**が、将来は本文の単語そのものが表示可否の判断材料になる見込みです（時期・仕様は未定＝要確認）。
- **A/Bテストの計測が正しくなる修正が入りました。** 利用者への直接の影響はありませんが、「この施策は効果があった」という判断の精度が上がるため、**今後リリースされる変更の質**に効いてきます。
- **X（プラットフォーム）側で、実験を切り替える配管が1本増えました。** 推薦モデルへのリクエストに実験設定を直接載せられるようになり、モデル側の実験の切り替えが今までより細かく・速くできます。体感としては「タイムラインの傾向が以前より短いサイクルで変わりうる」という意味になります。

## 変更サマリ

1. コールドスタート優遇（小規模アカウント押し上げ）の**対象条件を厳格化**：実験の treatment 閲覧者では、押し上げ対象が Phoenix MoE 経路の投稿に限定された。
2. コールドスタート実験の**バケット記録（impression logging）を両アーム同一化**。機能が無効な control 側でも記録が走るようになり、A/B 比較のバイアスが解消。
3. エンゲージメント数値ハイドレータの起動条件を整理：コールドスタートとの連動を切り、**キャッシュ済み投稿でも小規模アカウント分は数値を取り直す**ようになった。
4. Phoenix ↔ home-mixer 間の配管追加：`exactK` / `exactGap`（検索精度の診断値）と `experiment_overrides`（リクエスト単位の実験上書き）を proto に新設。
5. 可視性フィルタ（VF）：投稿本文フィールドに「**今後のミュートキーワード規則のため**」という保持理由が明記され、本文ハイドレーションのテストが追加。挙動変化はなし。
6. その他は挙動不変：VF のダークトラフィック（本番の複製リクエスト）を devel 環境にも流せるよう拡張、VF の公開APIを内部限定へ縮小、学習側の KMS リトライ・ログ整形・SIDインデックス定義のリファクタ。

## 変更点ごとの詳細（メカニズム → Xユーザー／クリエイターへの影響）

### 1. コールドスタート優遇が「Phoenix MoE 経路の投稿のみ」に限定（実影響：中）

**メカニズム**

`home-mixer/scorers/author_cold_start.rs:226-231`：

```rust
fn cold_start_corpus_eligible(arm: ViewerArm, c: &PostCandidate, corpus: AuthorCorpus) -> bool {
    match arm {
        ViewerArm::Holdout  => !is_phoenix_moe(c),
        ViewerArm::Control  => corpus == AuthorCorpus::Control && !is_phoenix_moe(c),
        ViewerArm::Treatment => corpus == AuthorCorpus::Treatment && is_phoenix_moe(c),  // ← && is_phoenix_moe(c) が新規
    }
}
```

従来 Treatment（優遇あり実験群）の条件は `corpus == AuthorCorpus::Treatment` のみで、**投稿の取得経路を問わなかった**。今回 `&& is_phoenix_moe(c)`（`author_cold_start.rs:167-169`：`served_type == ForYouPhoenixRetrievalMoe`）が加わった。

この関数が効く先が「押し上げ」本体である（`author_cold_start.rs:300-312`）。押し上げ対象は次を**全て**満たす候補：

- `cold_start_base_eligible`（`author_cold_start.rs:171-177`）：返信でない・リポストでない・著者フォロワー数 ≦ `ColdStartFollowerCap`
- 上記の corpus 条件（今回変更）
- 投稿の鮮度が `ColdStartMaxPostAgeSecs` 以内
- 現在の順位が「非ゼロスコア候補数 × `LowImpressionsMaxPositionRatio`」より上
- ホームでの表示回数が `ColdStartImpressionThreshold` 未満

条件を満たした1件のスコアが、上位帯からランダムに選んだ目標値（`cold_start_target`、`author_cold_start.rs:214-223`：ソート済みスコアの `slot_min..slot_max` から一様抽出）へ引き上げられる。

なお押し上げの直前に `apply_moe_ranking_policy`（`author_cold_start.rs:195-212`）が走り、**MoE 経路の候補は「treatment 閲覧者 × treatment コーパス著者」以外すべてスコア 0 に落とされる**。今回の変更は、この「残された MoE 候補」と押し上げ対象を一致させる整合修正にあたる。

**Xユーザー／クリエイターへの影響**

- treatment コーパスに入っている小規模アカウントの投稿でも、**従来の推薦経路（in-network、旧 retrieval など）で拾われたものは押し上げを受けなくなった**。小規模アカウントにとって「偶発的に上位に載る」経路が1本減る。
- 逆に、MoE 経路で拾われた投稿には押し上げが集中する。MoE 経路は投稿内容の意味的な近さで拾う経路であるため、**「ニッチだが内容が明確な投稿」のほうが押し上げに乗りやすい**構図が強まる。
- 閲覧者側は、treatment 群であれば「知らない小規模アカウントの投稿が突然上位に出る」体験の質が変わる（数は減るが、関連性は上がる方向）。
- ただし**これは実験内の挙動**であり、`EnableViewerColdStart` と co-divert 実験の配信率は公開コードに現れない（要確認）。

### 2. 実験バケットの記録を両アームで同一化（実影響：小／間接的には中）

**メカニズム**

`home-mixer/scorers/author_cold_start.rs:348-366`：

```rust
let params = ColdStartParams::read(query);
record_tracked_ids(candidates, &params.tracked_ids);
let corpus = match params.arm {           // ← enabled チェックより前に移動
    ViewerArm::Holdout => vec![AuthorCorpus::NotBucketed; candidates.len()],
    ViewerArm::Control | ViewerArm::Treatment => author_corpus(&self.author_rules, candidates),
};

if !params.enabled {                      // ← 早期 return がこの後ろへ
    return scores.to_vec();
}
```

`author_corpus`（`author_cold_start.rs:178-193`）は著者ごとの実験ルールを引く際に**バケット impression を記録する**。従来は `EnableViewerColdStart` が false（control 側の設定）だと早期 return してこの記録が走らず、treatment 側だけが記録される状態だった。新テスト `both_arms_log_the_same_codivert_impressions` と `both_viewer_arms_log_the_same_author_impressions` が、control/treatment 双方で impression 件数が一致することを固定している。

あわせて `viewer_arm` と `author_corpus` の分岐を `match (is_treatment, is_control)` へ書き換え、両フラグが同時に true のときの優先順位（treatment 優先）を明示。挙動は従来と同一。

**Xユーザー／クリエイターへの影響**

- 利用者への直接の影響はなし。
- 間接的には大きい：バケット記録が片側だけ走る状態では、**A/B の効果測定そのものが歪む**（記録された利用者集合が control と treatment で違う）。今回の修正で「コールドスタート優遇に効果があったか」の判定が正しく出るようになるため、**この施策が本採用されるか撤回されるかの判断が今後の数週間で下される**とみてよい。

### 3. エンゲージメント数値ハイドレータの起動条件変更（実影響：中）

**メカニズム**

`home-mixer/candidate_hydrators/engagement_counts_hydrator.rs:88-90`：

```rust
fn enable(&self, query: &ScoredPostsQuery) -> bool {
    query.params.get(EnableEngagementCountsHydration) || query.is_shadow_traffic
}
```

旧実装は `EnableViewerColdStart || (!query.has_cached_posts && (EnableEngagementCountsHydration || is_shadow_traffic))`。変更点は2つ。

1. **`EnableViewerColdStart` による起動が削除**：コールドスタートを有効にしただけでは数値取得が走らなくなった。押し上げ条件は `c.view_count_on_home.is_some_and(|imp| imp < threshold)`（`author_cold_start.rs:310-311`）であり、数値が未取得＝`None` なら **`is_some_and` が false になり押し上げは一切発生しない**。つまりコールドスタート優遇は `EnableEngagementCountsHydration` に従属するようになった。
2. **`!query.has_cached_posts` ゲートの削除**：キャッシュ済み投稿を返すリクエスト（スクロール継続・ページング）でもハイドレータが動くようになった。ただし取得対象は絞られたままで、`hydrate_from_client` 内の `fetch_counts = |c| !query.has_cached_posts || cold_start_base_eligible(c, follower_cap)`（`engagement_counts_hydrator.rs:118-121`）により、**キャッシュ経路では「フォロワー数が上限以下・返信でない・リポストでない」候補だけ**が取得対象になる。キャッシュ TTL は 60 秒（`engagement_counts_hydrator.rs:73-76`）。

**Xユーザー／クリエイターへの影響**

- **小規模アカウントの新しい投稿にとって有利**：タイムラインを下へ読み進めている閲覧者に対しても、いいね／返信／リポスト／ブックマーク／表示回数の最新値（最大60秒遅れ）でスコアリングされる。投稿直後の数分間に伸び始めた投稿が、その勢いを反映した状態で下位スロットにも届きやすくなる。
- 大きなアカウントの投稿はキャッシュ経路では数値を取り直さない（`cold_start_base_eligible` の follower cap で除外）。**数値の鮮度という点では小規模アカウント側に非対称に有利**な作りが維持・拡張された。
- 運用面のリスク：コールドスタート優遇と数値取得が別スイッチになったため、片方だけ有効な設定では優遇が黙って無効化される。実際の設定値は公開コードに現れない（要確認）。

### 4. Phoenix ↔ home-mixer の配管追加（実影響：小、ただし将来影響あり）

**メカニズム**

- `phoenix/crates/serving/xai-recsys-proto/proto/recsys.proto:1248-1249` および `phoenix/python/common/xai-proto/proto/recsys.proto` に `SlateContext` の新フィールド `optional uint32 exactK = 16;` / `optional uint32 exactGap = 17;` を追加。home-mixer 側も `SlateContext`／`PostCandidate` へ `exact_k` / `exact_gap` を通す（`home-mixer/models/candidate.rs:107-110, 131-132, 219-220`）。既存の `reconCosMilli` / `reconCountAbove` / `reconGapAbove` と並ぶ**近似最近傍検索の精度診断値**とみられる（用途は下流に現れず＝要確認）。
- `recsys.proto:119`：`PredictNextActionsRequest` に `map<string, string> experiment_overrides = 21;` を追加。2026-09-04 に home-mixer 側へ入った `PhoenixExperimentOverrides`（`k=v;` 形式のパラメータ）を**モデル推論リクエストへ実際に載せるための受け口**が揃った。

**Xユーザー／クリエイターへの影響**

- 現時点で表示結果は変わらない。
- ただし `experiment_overrides` の開通により、**推薦モデル側の実験をリクエスト単位で切り替えられる**ようになった。今後「タイムラインの傾向が短いサイクルで変わる」頻度が上がる方向の変更であり、クリエイター側からは「同じ投稿の伸び方が日によって違う」体感につながりうる。
- `exactK` / `exactGap` は検索の取りこぼし（近似検索が真の最近傍をどれだけ拾えているか）を測る値と読める。将来的に retrieval の品質改善に使われる下ごしらえ。
